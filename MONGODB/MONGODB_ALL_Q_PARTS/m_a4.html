What changed in protocol version 1 (PV1) compared with PV0, and why does it matter for failover?

PV0 was a variant of the Raft family with leader leases and a looser notion of consensus; elections could produce a new primary before the old one had definitively stepped aside, and the set relied on wall-clock-based leases to limit that window. PV1 (default since 4.0, and the only protocol in modern releases) replaced that with terms in the Raft sense: every election increments a monotonically increasing term, votes are granted at most once per term, and the old primary learns it has been superseded the moment it sees a higher term.

PV1 also introduced a well-defined majority commit point maintained through replication, catch-up takeover (a more up-to-date secondary can pre-empt the incumbent), and stricter oplog chaining. Practically, PV1 makes failover deterministic and eliminates the class of bugs where two members briefly both believe they are primary. You can still see the protocol with rs.conf().protocolVersion, and rs.status() reports the current term and electionId.

How does a candidate actually win an election, and what is a term?

A term is a logical epoch counter shared by the set: every election attempt gets a strictly higher number than any term a member has seen. When the primary disappears, eligible secondaries wait out electionTimeoutMillis (default 10 s) with randomised jitter, then one of them calls for an election via replSetRequestVotes, advertising its term, its last applied opTime, and its priority.

Other voting members grant the vote only if that candidate's term is at least theirs, their oplog is at least as up to date, and they have not already voted in that term. The candidate needs a strict majority of voting members — two of three, three of five — and then runs replSetElection followed by replSetUpdatePosition to publish itself. On success it writes a no-op oplog entry, which is how the new term becomes visible, and clients discover it through SDAM. A split vote simply means the next term starts and the jitter makes a repeat unlikely.

Why does a replica set want an odd number of voting members instead of leaning on an arbiter?

Majority arithmetic is what makes elections safe, so what matters is that the voting population is odd and small. Three voters tolerate one failure; four voters still need three votes and tolerate only one failure while costing an extra node — strictly worse than three. Five tolerate two. Adding voters without adding failure tolerance only lengthens elections and increases the chance of a split vote.

An arbiter fixes the vote count but not the durability. It holds no data, cannot become primary and cannot serve reads, so in a two-data-node-plus-arbiter set a majority (primary + arbiter) can acknowledge a write that exists on exactly one data-bearing node. That is a real data-loss window on failover, not a theoretical one. For genuine high availability you want an odd number of data-bearing voting members, ideally across failure domains, and an arbiter only as a deliberate cost compromise.

What does an arbiter do, and what does it explicitly not do?

An arbiter is a mongod started with replSetName that joins the set with arbiterOnly: true. It participates in heartbeats, stores the replica set config, votes in elections, and helps form a majority so an even number of data nodes can still elect a primary.

It does not store data, does not keep an oplog, cannot become primary, cannot serve reads or writes, and holds no copy from which to rebuild. It also cannot be a sync source, so a set of two data nodes plus an arbiter has exactly one usable replica of the data. Consequences worth stating in an interview: arbiters add latency to elections without adding durability, they still consume a host, and they must run the same major version as the data-bearing members. In modern deployments the honest advice is to prefer three data-bearing members; arbiters survive mainly in cost-constrained two-node setups and in DR configurations where the third site only needs a vote.

How does priority influence elections, and what happens when two members tie?

priority is a member setting from 0 to 1000 (default 1). It does not add votes; it biases who calls the election first and who wins. A member with higher priority triggers an election sooner after the primary is lost, and votes are only granted to a lower-priority candidate if no higher-priority eligible member is reasonably current. That is why a set with a preferred primary in the main region and a lower-priority DR member consistently comes back to the main region.

When priorities tie — the common case, all members at 1 — the tie is broken by oplog freshness and then by election jitter, so the winner is effectively arbitrary. Do not design around a specific winner. If you need determinism, set distinct priorities such as 5, 4, 3 rather than 1, 1, 1, keep the highest-priority nodes in the same low-latency failure domain, and remember that priority: 0 makes a member ineligible for election while it still votes and serves reads.

What do replSetStepDown and the freeze option actually do?

rs.stepDown(seconds) asks the current primary to relinquish leadership: it stops accepting writes, waits briefly for an electable secondary to catch up (bounded by secondaryCatchUpPeriodSecs), then closes client connections and campaigns for no election for seconds (default 60). During that window it is a normal secondary.

rs.stepDown(120)\n// or explicitly: db.adminCommand({ replSetStepDown: 120, secondaryCatchUpPeriodSecs: 15, force: false })

replSetFreeze is the same cooldown applied to a member that is not primary: db.adminCommand({ replSetFreeze: 300 }) prevents it from seeking election for 300 seconds, and { replSetFreeze: 0 } unfreezes. Use freeze to keep a node out of the race during maintenance, and stepdown to hand leadership to a specific node. Note force: true steps down even without a caught-up secondary — that trades a short write outage for a faster handover, so never use it casually in production.

How does secondaryCatchUpPeriodSecs shape a safe stepdown?

When a primary is asked to step down, it does not want to hand leadership to a node that is minutes behind, because that node would then serve state that is missing recent writes. secondaryCatchUpPeriodSecs (member-level, default 10) is the maximum time the primary waits for an electable secondary to reach its own opTime before giving up and stepping down anyway.

db.adminCommand({ replSetStepDown: 120, secondaryCatchUpPeriodSecs: 30 })

Raise it when the set is large, the oplog application is behind, or a replica is across a slow link and you would rather wait than lose freshness. Lower it when you care more about a fast handover than about the new primary being perfectly current. If no secondary reaches the threshold within the window, the primary still steps down unless force: false and it decides to stay — which is why an explicit stepdown during maintenance should always be followed by checking rs.status() for the new primary and its optimeDate.

What happens to writes that are in flight when the primary steps down?

Three distinct outcomes, and the distinction is what interviewers probe. A write that reached the primary and was applied to the oplog locally but not yet replicated may be rolled back if the new primary never received it: the old primary truncates that suffix into a rollback/ directory. A write that got a majority commit point is safe. A write that was still in the network or in the storage engine when leadership was lost is simply not acknowledged to the client, and the client sees a network error or NotWritablePrimary.

The primary does not wait for in-flight operations to finish: it closes the listener, kills in-progress operations after a grace period, and lets the driver retry. This is why w: 1 plus a retry loop can produce an acknowledged-then-vanished document, and why writes must be idempotent (deterministic _id, upsert with $setOnInsert) for retries to be safe. With w: "majority" a successful response means the write survived the stepdown.

Split brain: why can it not happen in a replica set, and what exactly guarantees it?

Two things. First, a member becomes primary only with votes from a strict majority of voting members, and each voter grants at most one vote per term — so two candidates cannot both collect a majority in the same term, because the two majorities would have to intersect in at least one voter. Second, an existing primary that cannot reach a majority of voting members for longer than the heartbeat timeout steps down voluntarily, so the minority side of a partition has no writable primary for long.

That intersection property is the whole guarantee: any two majorities of an odd set overlap. It also means the minority side is simply unavailable rather than divergent — availability is sacrificed, consistency is preserved. What can look like split brain is usually a stale driver view or a member that was reconfigured with force: true, which is the one operational way to manufacture two primaries. Duplicate primaries also appear when the same data directory is started twice.

How do majorities differ between 2 of 3 and 3 of 5, and what does that mean for availability?

A three-member set needs 2 votes: it survives one failure and loses writability if two members are down. A five-member set needs 3 votes: it survives two failures. In both cases you can lose floor(n/2) voters before writes stop, which is why the extra two nodes in a five-member set buy exactly one more tolerated failure at roughly 66% more cost.

The arithmetic also drives write latency: w: "majority" means the write is acknowledged once a majority has applied it, so in a five-member set spread across regions you need three acknowledgements, not two. And it drives election resilience: with five voters a single partition that isolates two members still leaves a majority, whereas in a three-member set isolating two members leaves one node that can never be primary. Choose the size from your failure-domain model and your budget, not by reflex — and remember that adding voters without adding data-bearing members changes nothing about durability.

What does settings.catchUpTakeoverDisabled change about elections?

By default, a secondary whose oplog is demonstrably ahead of the primary (it has applied writes the primary has not seen, typically after a former primary rejoined) can trigger a catch-up takeover: it forces an election rather than waiting, precisely because it is the better candidate. catchUpTakeoverDelayMillis controls how long it waits before doing so.

Setting settings.catchUpTakeoverDisabled: true in the replica set configuration turns that behaviour off, so a more current secondary waits for the normal election timeout and competes on priority instead of pre-empting. The practical use is environments where you want leadership to stay where you put it — for example a set with a strong regional preference — and importantly in some arbiter configurations, where catch-up takeover could otherwise push leadership onto an unexpected member. The price is a longer window after failover in which the best candidate is not yet primary. It is a rare, deliberate setting, not a default you should flip for convenience.

What happens when the region holding most of the voting members goes offline?

If the surviving members are fewer than a majority, the set has no primary at all — not a slow primary, no primary. Writes fail with NotWritablePrimary or a server-selection timeout, reads with readPreference: primary fail too, and secondaries keep serving only if the client explicitly allows secondary reads. Nothing recovers automatically: this is by design, because promoting a minority would risk losing committed data.

Recovery requires restoring enough voters to form a majority. That usually means bringing the failed region back, or performing a forced reconfiguration from the surviving side with rs.reconfig(cfg, {force: true}) to remove the unreachable members and lower the majority requirement. Forced reconfig is an operator decision with real consequences: the removed members still believe they are members, so when they return they must be wiped and resynced, and any writes they had that were not replicated are lost. This is the scenario to rehearse in a game day rather than discover at 3 a.m.

How do heartbeatIntervalMillis and electionTimeoutMillis determine failure detection?

Members exchange heartbeats every settings.heartbeatIntervalMillis (default 2000 ms). A member marks a peer as unreachable after roughly heartbeatTimeoutSecs (default 10) of silence. When the primary is unreachable, an eligible secondary waits settings.electionTimeoutMillis (default 10000 ms) after detecting loss of the primary before calling for votes — and the wait is jittered by the protocol so candidates do not collide.

rs.conf().settings\n// { heartbeatIntervalMillis: 2000, electionTimeoutMillis: 10000, ... }

So the practical failover window is heartbeat detection plus election plus driver discovery, typically 10–30 seconds end to end. The numbers are a trade-off: shorter timeouts detect real failures faster but mistake GC pauses, snapshot stalls or transient packet loss for death, producing unnecessary elections. Longer timeouts trade availability for stability. Both are replica set settings and changing them requires a reconfig that all voting members accept.

Why can raising electionTimeoutMillis be the right call in a multi-region set?

Because the cost of a spurious election in a multi-region set is much higher than the cost of a slightly slower real failover. Cross-region round trips can be 100–250 ms, and a node under heavy write load may briefly stop responding to heartbeats because of cache eviction, a checkpoint stall or a long index build. With a 10-second timeout that pause becomes an election; the new primary is in another region, latency for your users triples, and when the old node returns it may trigger catch-up takeover and another election.

Raising electionTimeoutMillis to, say, 20–30 seconds means a real failure takes an extra 10–20 seconds to detect, but you avoid election churn from transient stalls. Pair it with a driver serverSelectionTimeoutMS comfortably above the new detection window, otherwise clients give up before the new primary is known. The setting must be accepted by all voting members, and it does not shorten the rollback risk window, so it is not free.

What is replSetGetStatus, and which fields do you read first during an incident?

rs.status() is the wrapper around db.adminCommand({ replSetGetStatus: 1 }), and it is the single most informative command in a failover. Read it in this order: top-level myState and term; members[].stateStr to see who is PRIMARY, SECONDARY, RECOVERING or (ARBITER); members[].health, where 1 means reachable; members[].optimeDate and members[].replicationLag to quantify staleness; and members[].lastHeartbeatMessage, which often names the actual problem.

rs.status().members.map(m => ({ name: m.name, state: m.stateStr, health: m.health, lag: m.optimeDate }))

Then look at optimes.appliedOpTime, durableOpTime and lastCommittedOpTime to see whether the majority commit point is advancing, plus electionDate and setVersion. If setVersion differs between members you have a partially applied reconfiguration, which changes the whole diagnostic path.

How do you force a reconfiguration when the primary is unreachable, and what is the risk?

Connect to a surviving member, take the current config, edit it, and reconfig with force: true, which skips the requirement that a majority of the old configuration acknowledge the change:

cfg = rs.conf()\ncfg.members = cfg.members.filter(m => m.host !== \"m3.example.com:27017\")\nrs.reconfig(cfg, { force: true })

The risk is that you are unilaterally rewriting history: any writes the isolated members had that never replicated are gone, the set version increases so those members cannot simply rejoin, and if the "unreachable" primary is actually alive and serving clients on a partition, you have two primaries writing divergent data until the old one is fenced off. Treat force: true as a last resort after confirming the missing members are truly down, wipe and resync them afterwards, and record the exact config you applied. In Atlas you cannot do this at all; support-driven recovery replaces it.

What is inside an oplog entry, and why is each entry idempotent?

An oplog entry is a BSON document in local.oplog.rs with the fields ts (the BSON timestamp that defines order), t (term), h (hash), v (version), op (i, u, d, c, n), ns, ui (collection UUID), o (the payload) and, for updates, o2 (the query that selected the document). Transaction operations add lsid, txnNumber, stmtId and prevOpTime.

Idempotency comes from expressing changes as absolute state rather than as intent. An insert carries the whole document, a delete carries the _id, and an update records the specific fields it changed in o.$set or o.$unset rather than replaying the original operator tree, with o2 letting the applier find the target if the document moved. Applying the same entry twice therefore converges to the same state. That is what allows a secondary to retry a batch after a crash without corrupting data — It is also why $inc replays safely here but not in your own change stream consumer.

How does the ts field give the oplog a total order, and why does that matter?

ts is a BSON timestamp: 4 bytes of seconds since the epoch plus a 4-byte ordinal that increments within that second. The primary assigns it when it appends the entry, and because appends are serialised under a lock the resulting sequence is a strict total order — there are no ties, and no two entries share a ts.

That single ordered log is the backbone of the whole system: secondaries apply entries in ts order, the majority commit point is a position in that order, change stream resume tokens are derived from it, and point-in-time recovery replays it up to a chosen ts. Comparisons are cheap and lexicographic, which is why ranges like { ts: { $gt: lastTs } } are the natural way to tail the oplog. It also explains why you cannot reorder or hand-craft oplog entries safely, and why the ordering is logical rather than wall-clock: wall exists as a separate field for human debugging, and clock skew never reorders replication.

How is an oplog entry applied on a secondary?

The secondary's oplog fetcher pulls batches from its sync source with a query on local.oplog.rs filtered by ts greater than its last applied position, typically using an awaitable tailing cursor so new entries arrive without polling. The batch is applied by writer threads that perform the actual document changes in parallel for independent namespaces, then a barrier ensures the entries are inserted into the secondary's own oplog in exactly the original order. That is why secondaries keep an oplog of their own: it is the history they have applied, and it is what other members chain from.

Application is idempotent, so after a crash the node re-reads from its last durable position and reapplies, possibly duplicating work but not data. Two positions matter: appliedOpTime (what has been applied, possibly not yet durable) and durableOpTime (journaled). Monitoring serverStatus().metrics.repl.apply exposes batch counts and total apply time, which is where you look when applying rather than fetching is the bottleneck.

How do you compute the real oplog window from oplogSizeMB and your write rate?

Do not use the configured size as a proxy — measure the window. rs.printReplicationInfo() reports the first and last oplog entry timestamps and the resulting time span; that span is the true window, and it shrinks as write volume grows. To project forward, measure how much oplog the primary generates per hour and divide:

// window_hours = oplogSizeMB / oplog_MB_per_hour\n// e.g. 51200 MB / (1200 MB/hour) = 42.6 hours

Get the rate from db.serverStatus().oplog (logSizeBytes divided across a time range) or by differencing the ts of the first and last entries over a known period while watching metrics.repl.buffer and actual throughput. Then account for peak, not average: a nightly bulk load can consume a day's window in an hour. A comfortable target is at least 24–72 hours at peak, so a weekend outage or a broken sync source does not force a full resync.

Why does a short oplog window break change streams and point-in-time recovery?

Both features read the same log. A change stream resumes from a resume token that encodes an oplog position; if the consumer was down long enough for that position to roll off the end of the oplog, the server cannot reconstruct what happened in between and returns an error such as ChangeStreamHistoryLost (or a resume error naming the missing token). There is no backfill — the events are simply gone, and the consumer must resynchronise from a full read of the collection and reconcile.

Point-in-time recovery has the same constraint from the other direction: restoring to a moment requires a base backup plus every oplog entry from that backup's position forward. If the oplog no longer covers the interval, the restore target is unreachable and you are left with the base snapshot plus whatever later full backup exists. The design rule is therefore blunt: size the oplog for your worst consumer downtime and your backup cadence, not for the average write rate, and alert on window as a first-class metric.

How does replSetResizeOplog work at runtime, and what should you watch?

replSetResizeOplog changes the oplog's maximum size without restarting the member, and it must be run on every member individually — it is not a replica set setting:

db.adminCommand({ replSetResizeOplog: 1, size: 102400 })  // size in MB

Growing is safe and cheap: the collection's maximum size is raised and WiredTiger allocates as entries accumulate. Shrinking is the dangerous direction — MongoDB must truncate the oldest entries immediately to fit, which can cut the window from days to hours in one command and break change streams or PITR coverage that was relying on it. There is also a minimum size (roughly 990 MB) below which the command is rejected.

Because the oplog is a capped collection, space is not returned to the filesystem after a shrink; it is reused later. Run the change during low write volume, verify the new window with rs.printReplicationInfo() on that member, and remember that a resize does not propagate — a forgotten member keeps the old size and eventually has a different window than its peers.

How do the majority commit point and appliedOpTime differ, and why does the gap matter?

appliedOpTime is how far a member has applied the oplog locally. lastCommittedOpTime — the majority commit point — is the newest entry that a majority of voting members have durably written, as tracked by the primary. They are different clocks: a secondary can be fully applied and yet the commit point has not moved, because some other member is behind.

That gap is exactly the window in which w: "majority" writes wait, so a single lagging member delays every majority write on the primary even though the primary itself is current. It also bounds what reads with readConcern: "majority" can see: they see only committed data, so they can appear to go backwards relative to a local read. And it bounds rollback: only entries above the commit point can be rolled back. When latency spikes with no CPU or IO pressure, compare rs.status().optimes.lastCommittedOpTime against each member's optime — that comparison usually names the culprit.

What causes a rollback, and how do you actually recover the documents?

A rollback happens when a member's oplog contains entries that the new primary's history does not: the member was primary, accepted writes that never reached a majority, lost leadership, and must now discard that suffix to converge. The node transitions to ROLLBACK, finds the common point with its sync source, and writes the discarded documents to <dbPath>/rollback/ as BSON files named after the namespace and timestamp.

ls /var/lib/mongodb/rollback/\nbsondump <db>.<coll>.<timestamp>.bson | head

Those files are the only record; MongoDB does not merge them back. You inspect them, decide which documents are legitimate business writes, and reapply manually or with a script. Rollbacks are bounded by the oplog window and by rollbackTimeLimitSecs; beyond that the node cannot roll back and requires a full resync. Preventing them is a write concern decision: w: "majority" writes cannot be rolled back, which is the honest answer to "how do I avoid this".

Why does w:1 allow losing writes the client already saw as successful?

With w: 1 the primary acknowledges as soon as it has applied the write locally. Nothing has been replicated yet. If the primary dies in the next few milliseconds, the surviving members elect a new primary from the data they have, the old primary's unsent suffix is discarded on rejoin, and the client's successful write never existed — a rollback, visible as a missing document.

The failure is worse than "we lost the last write": the client has already emitted a receipt, an email, a payment confirmation. Recovery means reconciling application state against a database that disagrees with it, which is why rollback files matter.

The fix is not exotic: use w: "majority" for anything a user was told succeeded. If the latency is unattractive, the honest engineering work is on topology and network placement, not on lowering the guarantee. w: 1 combined with an aggressive retry policy is a data-loss generator, because the retry can duplicate a write that was in fact rolled back.

What does writeConcernMajorityJournalDefault control?

It is a field in the replica set configuration (settings.writeConcernMajorityJournalDefault, default true) that decides whether w: "majority" also implies journaling on each acknowledging member. With the default, a majority write is acknowledged only after those members have written the entry to their on-disk journal, so it survives an OS crash or power loss, not just a process crash.

rs.conf().settings.writeConcernMajorityJournalDefault  // true

Setting it to false makes majority writes in-memory (j: false semantics): faster, and still safe against a mongod crash because WiredTiger can recover from its own log, but not safe against machine-level failure. The per-operation writeConcern: { w: "majority", j: true } still overrides it upward. Change this only with a clear durability story, and note that it is a set-wide setting applied by reconfiguration, so it affects every client at once — including ones that never asked for the looser behaviour.

What is flow control (enableFlowControl), and when does it limit the primary?

Flow control is a mechanism that throttles the primary's write rate when secondaries fall too far behind. The primary continually measures the replication lag implied by its majority commit point; if that lag exceeds flowControlTargetLagSeconds (default 10 s), it starts injecting small delays into write tickets, and it logs a warning once lag passes the warning threshold.

db.adminCommand({ setParameter: 1, enableFlowControl: true })\ndb.serverStatus().metrics.operationCounters  // plus metrics.repl for lag context

It is enabled by default in recent versions and it is a back-pressure mechanism, not a fix: it buys the secondaries time to catch up by slowing the source, which shows up as increased write latency while lag stays flat. That pattern — rising latency, stable lag, low CPU — is the signature. The right response is to find why the secondaries are slow (IO, cache, network, missing indexes on the primary's hot path) rather than disabling flow control, which just lets the oplog window burn faster.

How do multi-document transactions appear in the oplog?

A transaction is not one entry. Each statement inside it produces an oplog entry carrying the session and transaction identifiers — lsid, txnNumber — plus a stmtId, and consecutive entries are chained with prevOpTime so a secondary can tell whether it has the whole chain. Entries are written as partial transaction operations; only the commit (or abort) entry makes the group visible.

Consequences you should be able to state. First, a transaction of 500 writes adds roughly 500 entries and consumes oplog space in proportion, so large transactions shorten the effective window. Second, replication of a transaction is atomic from the reader's point of view: a change stream does not emit half a transaction. Third, oplog size and majority commit position are evaluated across the whole chain, so an uncommitted transaction's entries cannot be part of the commit point. Fourth, the 16 MB per-entry limit still applies, but the transaction total is bounded by the transaction lifetime and resource limits, not by one entry.

Can a reconfiguration truncate the oplog, and what breaks if it does?

A normal rs.reconfig does not rewrite history — raising setVersion changes membership, not the log. Truncation happens through three real paths. A member that must roll back truncates the divergent suffix at the common point with its sync source. Shrinking the oplog with replSetResizeOplog deletes the oldest entries immediately and can cut the window to hours. A member that is removed and re-added starts with an empty oplog and resyncs from scratch, so its window restarts at zero.

What breaks is anything anchored to an absolute oplog position: change stream resume tokens whose position is gone fail with a history-lost error, point-in-time restore targets before the new first entry become unreachable, and a replica trying to catch up from a point that no longer exists on any peer is forced into a full initial sync. This is why reconfigurations that touch votes or membership should be done one change at a time, with the oplog window and every change stream consumer's checkpoint verified before and after.

Can you read from a member with votes: 0, and what are the limits?

Yes. A non-voting member is a full replica: it keeps an oplog, applies writes, can be a sync source for other members, and serves reads. What it cannot do is vote in elections or count toward the majority, so it neither helps nor hurts the set's ability to elect a primary, and it does not count toward the majority required by w: "majority".

cfg = rs.conf()\ncfg.members[2].votes = 0\ncfg.members[2].priority = 0\nrs.reconfig(cfg)

The typical use is a disaster-recovery copy in a third region: it costs replication bandwidth and a host, but you deliberately do not want it participating in elections, because a slow link would add latency to every vote and every majority write. Limits to remember: a set allows up to 50 members and at most 7 voting members, changing votes changes the majority arithmetic and should be a separate reconfiguration from changes to priority or host names, and a votes:0 node with priority above 0 is rejected.

Logical initial sync versus file-copy-based initial sync: how does MongoDB choose?

Historically initial sync was logical: the new member builds indexes from the config, copies every collection by scanning it, then applies the oplog tail accumulated during the copy. It works everywhere but is slow and hammers the sync source with reads.

Since 5.0 there is also file-copy-based initial sync: the source streams its data files while writes continue, then the new member applies the oplog from the captured start position. It is dramatically faster on large datasets because it moves files instead of documents and does not rebuild indexes one document at a time. Conditions matter: both nodes must use WiredTiger, the source must be a healthy member of the same set, and if the copy cannot be validated or the engines differ, MongoDB falls back to the logical path. Either way the new member must not serve reads during sync and must not be electable — set priority: 0 and hidden: true before rs.add(), so a half-synced node cannot win an election.

What does an initial sync load on the primary, and what can go wrong?

Nothing blocks writes — the primary keeps serving — but a syncing member can hurt in four ways. It performs full collection scans on its sync source, which by default may be the primary, consuming IO and cache. If it builds indexes logically, that is index-build load on the new node, not the primary, but the read pressure is real. It also requires the primary to retain oplog entries for the entire sync: if the sync takes longer than the oplog window, the process restarts from zero, potentially forever. And if the new member is eligible, it may be elected while still syncing.

Mitigations: pre-create the member as hidden with priority: 0; point it at a dedicated sync source if you have one (initialSyncSourceReadPreference, or by placing the source deliberately); grow the oplog before large syncs; and run the sync in a low-traffic window for large collections. Watch rs.status() for the STARTUP2 to RECOVERING to SECONDARY transition and confirm the lag reaches zero before promoting.

How do you add a new member without letting it disturb the existing primary?

Stage it as a passive node and promote it only after it is caught up. Create the config entry with the safe flags rather than accepting defaults:

rs.add({ host: \"m4.example.com:27017\", priority: 0, hidden: true, votes: 0 })\n// wait for stateStr: SECONDARY and lag to settle, then:\ncfg = rs.conf(); cfg.members[3].priority = 1; cfg.members[3].hidden = false\ncfg.members[3].votes = 1; rs.reconfig(cfg)

hidden: true keeps drivers from routing reads to it, priority: 0 keeps it out of elections, and votes: 0 means the initial sync cannot change the majority arithmetic mid-flight. Note buildIndexes: false is another option for pure DR nodes, but such members can never become primary and must stay at priority 0 and votes 0. Change one dimension at a time: promoting votes and priority in the same reconfiguration as the addition is how people accidentally create a set where the new, still-warm node is one of the three voters.

What are the real causes of replication lag, in the order you should investigate them?

Start with the secondary's ability to apply, not with the network. The usual order: IO saturation on the secondary (slow disks, competing backup or snapshot jobs) shows as high apply batch time; CPU or cache pressure, where the working set no longer fits and WiredTiger evicts constantly; missing or badly designed indexes, so each applied update triggers a collection scan; large write bursts on the primary, including bulk loads and big transactions; and network throughput or latency between members, which shows as a slow fetcher while apply time stays low.

The diagnostic split is fetch versus apply. db.serverStatus().metrics.repl.buffer tells you whether entries are queued waiting to be applied; metrics.repl.apply.batches.totalMillis tells you how long applying takes. If the buffer is empty and lag persists, the fetcher or network is the problem. If the buffer grows, the applier is the bottleneck — that is IO, CPU or index work, and it will not be fixed by adding bandwidth.

How do you measure lag with rs.status() and with serverStatus().metrics.repl?

rs.status() gives you the operational view: per-member optimeDate and a computed replicationLag in seconds, plus syncingTo so you can see the replication chain. rs.printSecondaryReplicationInfo() formats it readably. The caveat is that these are sampled at the moment you call it and derived from timestamps, so a momentarily idle primary can make lag look like zero.

rs.printSecondaryReplicationInfo()\ndb.serverStatus().metrics.repl\n// apply.batches.num, apply.batches.totalMillis, apply.ops,\n// buffer.count, buffer.sizeBytes, preload

metrics.repl is the counter view for monitoring systems: buffer depth tells you backlog, apply batch timings tell you applier health, and deltas over time reveal a trend rather than a snapshot. Alert on sustained lag — five minutes above threshold — not on a single spike, and alert separately on buffer.count growth, which precedes visible lag and is the earlier warning.

How does secondaryDelaySecs work, and what does it actually protect against?

secondaryDelaySecs (member setting, the replacement for slaveDelay as of 5.0) makes a member apply oplog entries only after they are that many seconds old — typically 3600 for an hour of protection. The member must be priority: 0 and hidden: true, because it is intentionally stale and must never serve as primary or receive normal reads.

cfg = rs.conf()\ncfg.members[2].secondaryDelaySecs = 3600\ncfg.members[2].priority = 0\ncfg.members[2].hidden = true\nrs.reconfig(cfg)

What it protects against is a logical error that replicates fast: a bad migration, an errant deleteMany, a bug that overwrites a field. You notice within the hour, stop the delayed member before the damage reaches it, and use it as the recovery source. What it does not protect against is hardware loss of the primary plus the other replicas, or an error nobody notices for longer than the delay.

Why is a delayed member not protection against a drop that replicates an hour later?

Because the delay is a scheduling device, not a veto. secondaryDelaySecs: 3600 means "apply each entry one hour after its timestamp"; the node still receives the oplog continuously and will apply the drop or deleteMany as soon as its clock passes the threshold. If nobody intervenes, the delayed member becomes identical to the others — including the damage.

The protection only exists if you act inside the window: detect the incident, then stop the delayed member (shut it down or block replication) before the entry is applied, verify its data is pre-incident, and treat it as the restore source. That requires monitoring and a documented runbook, because the window is measured in the delay you configured. The other real gap is that a delayed member cannot help with a failure that happens before the delay elapses: if the primary and the other secondaries are lost, the delayed node is an hour behind with no source to catch up from.

What does replSetFreeze do, and how does it differ from a stepdown cooldown?

replSetFreeze tells a member not to seek election for a number of seconds. It is the tool for keeping a node out of the election race — during maintenance, while you are validating a rebuild, or when you want a specific region to hold leadership:

db.adminCommand({ replSetFreeze: 600 })   // stay secondary for 10 minutes\ndb.adminCommand({ replSetFreeze: 0 })     // unfreeze immediately

A stepdown's cooldown is the same idea applied to the member that just gave up leadership: rs.stepDown(120) both hands over and prevents that node from re-winning for 120 seconds. The difference is the starting state and the intent: stepdown moves leadership away from a primary that is currently serving; freeze suppresses a candidacy that has not started. Both are temporary by design — they do not persist across restarts and they do not survive a reconfig. Freezing every member by mistake leaves the set with no eligible candidate, so apply it to the nodes you want to exclude, and record when it expires.

What is apply backlog, and what does the secondary's yield behaviour have to do with it?

Apply backlog is the gap between what the secondary has fetched and what it has applied. It is visible as metrics.repl.buffer.count and buffer.sizeBytes, and it is the leading indicator of lag: the fetcher can be keeping up perfectly while the applier falls behind.

The applier takes locks on the namespaces it writes, and it yields those locks so that user reads on the secondary are not starved. That politeness is exactly why heavy read traffic on a secondary slows replication: each yield is progress lost, and with a large read workload the applier can spend most of its time waiting to reacquire locks. Long-running reads, unindexed queries and background analytics on the same node all make it worse. Countermeasures are structural — keep reporting off members that must stay current, use read preference tags so real-time reads go elsewhere, ensure the secondary's queries are indexed, and check apply.batches timing after any change in read traffic. You cannot tune yielding away; you can only stop competing with the applier.

Why do secondaries crash with OOM while applying the oplog, and how do you fix it?

Usually because the secondary's workload is different from the primary's, not because replication is heavier. A secondary that also serves reads carries the WiredTiger cache plus query working sets. Applying a large burst — a bulk load, a big transaction, an index build — forces cache eviction, and eviction pressure plus concurrent reader allocations can push the process past the container limit. In containers the classic failure is that the cgroup limit is lower than what cacheSizeGB assumes, so the kernel OOM-kills mongod before WiredTiger evicts.

Fixes: size storage.wiredTiger.engineConfig.cacheSizeGB for the container, not the host; leave headroom for query memory and connections; remove analytics from members that must stay current; avoid unbounded $in and huge batch reads; and watch cache evicted pages and cache bytes read into cache in FTDC. A node killed repeatedly will resync, which loads it even more — a loop worth breaking early.

How much latency does w:majority actually add, and where does it come from?

It adds one replication round trip plus the journal write on the acknowledging members, so the floor is roughly the latency to the majority position, not to the farthest node. In a three-member set with two members in the same datacentre, that is a local network hop plus fsync — single-digit milliseconds. Spread three members across three regions and the majority includes a cross-region hop, so 80–200 ms per write becomes normal.

The second component is the tail: w: "majority" waits for the slowest member that completes the majority, so one lagging replica can hold up every write even though the others are current — the commit point is a minimum, not an average. This is why latency spikes with flat CPU usually mean a replication problem, not a query problem. Measure with serverStatus().metrics.getLastError.wtime and compare lastCommittedOpTime to each member's optime before blaming the network.

What is the trap in readPreference: nearest?

nearest means "lowest network latency among members that are eligible", and it includes the primary. It says nothing about freshness, load or role. The traps follow directly: in a low-latency local network the "nearest" member may be a secondary that is 30 seconds behind, or it may be the primary, so your read distribution is not what you assumed; and because latency is measured by the driver's own round-trip samples, the choice can flip between members and give you inconsistent results across consecutive reads.

If what you want is "spread reads across secondaries", say so with secondaryPreferred. If you want "read from a nearby secondary but not a stale one", combine it with maxStalenessSeconds, which filters out members whose estimated lag exceeds the limit. If you need read-your-writes, nearest is the wrong tool entirely — use primary or causal consistency with afterClusterTime. And always test with a realistic topology, because nearest behaves very differently in one datacentre than across three regions.

When a partition heals, how does the driver decide where to reconnect, and what makes it slow?

The driver's SDAM layer keeps a topology description built from its own monitoring connections: each server has a type (RSPrimary, RSSecondary, RSArbiter, Unknown) and a round-trip time. After a partition heals, monitoring resumes, servers transition from Unknown back to their real types, and server selection then picks a member matching the read preference — preferring lower RTT among eligible candidates, and requiring a primary for writes. Reconnection is therefore driven by the monitor's heartbeatFrequencyMS (default 10 s, minimum 500 ms), not by the application's retry rate.

What makes it slow: the driver must wait for a server to be rediscovered and for a primary to exist; if the partition caused an election, that is a second wait. A large maxPoolSize then opens many connections at once on the newly discovered primary, which can look like a second outage. That is why minHeartbeatFrequencyMS, pool sizing and a serverSelectionTimeoutMS longer than the expected failover window are all part of the same design decision.

How do heartbeats produce false positives, and how do you reduce them?

A heartbeat that arrives late is indistinguishable from a member that is gone, so anything that pauses a process produces the same signal as a crash: a long GC pause in a client-side proxy, a checkpoint or eviction stall, a hypervisor snapshot, a saturated NIC, a CPU steal event on a shared host. If the pause exceeds the heartbeat timeout, peers mark the member unreachable and may elect a new primary; when it returns, the set churns again.

Reduce them by removing the causes rather than by shortening timeouts: keep mongod off oversubscribed hosts, avoid storage snapshots during peak, keep the working set inside cache, and monitor serverStatus().metrics.repl alongside host metrics so you can correlate a lag spike with a disk stall. If pauses are inherent to your platform, raising electionTimeoutMillis is the correct lever. And do not run members across links where packet loss is routine: heartbeats are small and cheap, but they are also the only evidence of liveness you have.

What does the driver's SDAM layer actually do when the primary disappears?

Server Discovery and Monitoring maintains a topology description and a monitor per known server. When the primary's monitoring connection fails, its type becomes Unknown, the topology emits a description change, and any in-progress selection fails or blocks. The driver keeps monitoring all seeds and all discovered members; when a secondary is promoted, the next heartbeat identifies it as RSPrimary, the topology becomes usable for writes again, and the connection pool for that server is created and warmed on demand.

Two behaviours matter operationally. First, operations already sent to the old primary fail with a network error or a "not primary" error; the driver does not silently move them. Second, retryable writes (with retryWrites=true) get exactly one retry after a fresh server selection, which usually lands on the new primary. Everything else — non-retryable commands, transactions mid-flight, reads outside a session — is your application's problem, which is why serverSelectionTimeoutMS must exceed the election window and why applications need their own retry policy with idempotent operations.

What is the typical error during serverSelectionTimeoutMS, and what does it tell you?

You see MongoServerSelectionError (Node.js and others) or a Timeout naming the topology, with a message listing each server and why it was rejected — "connection refused", "server is in state RSSecondary", "not primary". That detail is the diagnostic: it tells you whether no primary existed, whether the hosts were unreachable, or whether your read preference could not be satisfied.

// connection string\nmongodb://h1,h2,h3/db?replicaSet=rs0&serverSelectionTimeoutMS=20000

The default is 30 seconds, which is generous for elections but not for a region-level outage. If timeouts cluster exactly at the timeout value, clients are waiting the full window — that is an availability problem, not a slow query. If they cluster earlier, you are hitting a pool or socket timeout instead. Read the full error string before changing anything: raising serverSelectionTimeoutMS hides the symptom while requests pile up, and lowering it turns a 12-second election into a burst of application errors.

What makes an operation safe to retry after a failover, in concrete MongoDB terms?

An operation is safe to retry when applying it twice has the same effect as applying it once, and when the retry cannot be confused with a different logical request. In MongoDB terms that means: a client-supplied deterministic _id on inserts so a duplicate-key error tells you the first attempt succeeded; upserts with $setOnInsert rather than plain inserts; updates that set absolute values rather than incrementing; and a natural idempotency key stored in the document so a replayed request is detectable.

db.payments.updateOne(\n  { _id: requestId },\n  { $setOnInsert: { amount, currency, status: \"pending\" } },\n  { upsert: true })

Note the asymmetry: retryable writes protect the database from double-applying, but they cannot know whether your side effect — an email, a charge — already happened. And a rolled-back w: 1 write is the worst case, because the retry legitimately re-creates something the client already treated as done.

How do you run a failover drill without a maintenance window?

Make the drill a normal, reversible operation and run it during business hours with observers. Preconditions: w: "majority" on critical writes, retryable writes enabled, idempotent handlers, dashboards on lag and election counts, and a rollback plan that is just "step down again". Then, in ascending order of realism, run rs.stepDown(60) on a secondary first as a no-op sanity check, then on the primary while measuring client error rate and p99 latency through the handover. Escalate in staging to kill -9 of the primary process, and to a blocked port (iptables) to simulate a partition rather than a clean exit.

db.adminCommand({ replSetStepDown: 60, secondaryCatchUpPeriodSecs: 15 })

Record time-to-new-primary, time-to-first-successful-write, connection storm size, and whether any write was lost. A drill that only verifies "a new primary appeared" teaches nothing; the value is the client-side timeline. Announce it, keep it short, and never drill during a backup or index build.

How do you perform rolling maintenance on a replica set node by node?

Never touch two members at once, and always leave the primary for last. The loop is: pick a secondary, confirm rs.status() shows it healthy and caught up, confirm the other two are healthy, stop it, do the work, restart it, watch it return to SECONDARY and reach zero lag, then move on. When only the primary remains, either step it down so the work happens on a secondary-turned-primary, or restart it and accept one election.

rs.status().members.map(m => [m.name, m.stateStr, m.health])\nrs.stepDown(120)

Guardrails that prevent most incidents: check the oplog window before starting, because a node offline longer than the window forces a full resync; verify the majority still exists at every step (in a three-member set, one node down is your entire budget); pause backup jobs and index builds; and keep a written abort criterion — for example "if lag exceeds 60 s or a second member becomes unhealthy, stop". Rolling maintenance is a sequencing discipline, not a technical trick.

rs.stepDown() versus killing the mongod process: what is the difference in practice?

rs.stepDown() is a cooperative handover. The primary stops accepting writes, waits for an electable secondary to catch up, then relinquishes leadership; the set elects a new primary in seconds, usually with no rollback because the successor is current. Connections close cleanly and the old primary becomes a secondary that immediately starts applying.

Killing the process (kill -9, OOM kill, host failure) is an uncooperative failure. No handover, no catch-up wait: peers detect the loss by heartbeat timeout, the election starts later, in-flight writes are simply lost, and the primary's unjournalled suffix may be rolled back when it restarts and recovers through WiredTiger. It is also the only way to test crash recovery and the driver's real behaviour.

So: use stepDown for planned maintenance — it is faster and cleaner. Use process kills deliberately in drills and chaos tests, never as a shortcut during maintenance. And remember stepDown does not simulate the case where the primary is unreachable rather than polite, which is the failure mode that actually hurts.

How do you add or remove members without ever losing the majority?

Do the arithmetic before the command. A set needs a strict majority of voting members to elect and to commit w: "majority" writes; in a three-voter set that is two, so one member can be down. During any change, count how many voters would be unavailable if the change goes wrong.

Adding: add the member with votes: 0 and priority: 0 first, let it sync, then raise votes in a separate reconfiguration, one change at a time. Removing: remove non-voting members first, and never remove a member whose departure leaves the set with an even, undersized voting population mid-flight. Use rs.remove() only from the primary, and if the primary is unavailable use rs.reconfig(cfg, {force: true}) knowing it is a last resort.

rs.add({ host: \"m4:27017\", votes: 0, priority: 0 })\nrs.remove(\"m4:27017\")

Remember the limits: at most 50 members and 7 voting members. And verify after each step that rs.status() still has a primary.

How do you change the hostnames of replica set members?

Host names live in the replica set configuration, not in the data, so the operation is a reconfiguration — but the sequencing matters because members address each other by the names in the config. Prepare DNS first: every new name must resolve, from every member and from every client, to the right host, and it must be the name the member itself will use as its bindIp/advertised identity.

cfg = rs.conf()\ncfg.members[1].host = \"m2.newzone.example.com:27017\"\nrs.reconfig(cfg)

Change one member at a time, connect to the primary through a name that is not changing, and expect a brief window where heartbeats to that member fail until DNS and the member agree. You cannot change the _id of a member, and you cannot set a host that another member already uses. If you are changing the primary's name, step it down first so you are not reconfiguring the node you are connected to. Finally, update connection strings and any monitoring that keys on host names in the same change window.

How do you use a hidden member for reporting without hurting replication?

Hidden members have priority: 0 and hidden: true: they replicate and vote, but cannot become primary and are not selected by normal read preference modes. That makes them a reasonable home for reporting only if you accept the coupling: every analytics query competes with the oplog applier for cache and IO on that node, and a saturated reporting member falls behind.

Practical setup: give the node more memory than the others, keep its queries indexed and bounded, put a hard maxTimeMS on reports, and pin reporting clients to it deliberately — most drivers will not send secondary reads to a hidden member, so either connect with directConnection=true or use a tag set that matches only that member and confirm your driver's selection rules.

cfg.members[2].tags = { role: \"reporting\" }\n// client: readPreferenceTags=role:reporting

The alternative worth mentioning in an interview is a dedicated analytics path (Atlas Analytics node, or a change-stream-fed store) so reporting never shares fate with replication.

How do you control read preference and secondary reads inside mongosh?

mongosh connects with readPreference: primary unless the URI says otherwise, so rs.secondaryOk() — the legacy shell helper — or the modern equivalent is needed to read from a secondary:

db.getMongo().setReadPref(\"secondary\")\ndb.getMongo().setReadPref(\"secondary\", [{ region: \"us-east\" }])\ndb.getMongo().getReadPref()

Two things surprise people. First, the setting is per connection, so a new shell or a new URI resets it. Second, some operations simply refuse to run on a secondary regardless of preference: writes, $out/$merge stages, and anything requiring a primary. If you get "not primary and secondaryOk=false", you are on a secondary with the default preference — not a permissions problem. For diagnostics it is often better to connect directly to a specific member (directConnection=true) so you know exactly which node answered, rather than relying on preference-based routing.

Which replication metrics would you alert on, beyond lag?

Lag alone is a late signal. A defensible set: sustained lag above threshold for several minutes; oplog window (as a duration, from rs.printReplicationInfo()) trending below your recovery objective; election frequency, because more than a couple per day means instability, from db.serverStatus().metrics.repl.electionMetrics (elections called, successful elections, average election time) and the stepdown counter; member state flapping, counted as transitions per hour rather than a snapshot; apply backlog (metrics.repl.buffer.count) growing; and write concern latency (metrics.getLastError.wtime) p99, which is the client-visible symptom of a lagging majority.

Also alert on "no primary" as a distinct page, and on a member in RECOVERING or ROLLBACK for more than a few minutes. Every one of these should be a rate or a duration, not an instantaneous value — a single sample of lag is noise, and paging on noise trains people to ignore pages.

How does failover differ between Atlas and a self-managed replica set?

The mechanics are the same — majority vote, election, new primary — but the operational surface is different. Atlas runs a three-node replica set (or a sharded cluster) on managed infrastructure, keeps an odd number of voters, performs rolling maintenance and version upgrades for you, and exposes failover through a documented "Test Failover" operation rather than rs.stepDown(). You do not get rs.reconfig or replSetStepDown privileges, so forced reconfiguration and topology surgery become a support-assisted recovery.

What Atlas gives you: automated backups and PITR, alerts on replication lag and elections, multi-region and global clusters with zone-based placement, and a connection string that abstracts the member list. What it does not give you: control over election timing, arbitrary member types, or the ability to inspect rollback files. Self-managed gives you all of that plus the obligation to rehearse it. The interview point is that failover design is about the client and the write concern, not about who runs the nodes — a badly designed client fails over badly on either platform.

How do you recover a member whose data files are corrupt?

Do not try to repair it in place on a live set. The reliable path is replacement: stop the member, confirm the other members are healthy and hold a majority, then remove it from the configuration (or leave it there while it is down if a majority still exists), wipe its dbPath, and restart it so it performs a fresh initial sync.

// on the primary, only if a majority remains\nrs.remove(\"bad:27017\")\n// on the failed host: stop mongod, move the old dbPath aside, start clean\nrs.add({ host: \"bad:27017\", priority: 0, hidden: true, votes: 0 })

Before wiping, preserve the old files: if the corruption is logical, they may be the only copy of a write that never replicated, and mongod --repair or a bsondump salvage can recover documents — but only offline and only as a last resort, never as a step towards rejoining. Validate afterwards with db.collection.validate() if you suspect storage-layer corruption, and check the host's disk and RAM, because a node that corrupts once will do it again.

How do you plan capacity after losing an entire region?

Model the surviving state explicitly: with a 3-2-2 or 2-2-1 layout, losing a region leaves fewer members than before, and if the lost region held a majority of voters there is no primary at all until a forced reconfig. Capacity planning therefore has two parts — votes and resources.

Votes: ensure the remaining regions can still form a majority, which usually means the two data-bearing regions must each hold enough voters, or you accept an operator-driven forced reconfig with a documented time budget. Resources: the surviving members must absorb the full read and write load, so check headroom for 100% traffic: RAM for the working set, IOPS, and connections. Also re-evaluate w: "majority" latency, because the majority now spans a longer path, and re-check oplog sizing since the surviving primary writes everything.

The honest test is a game day: take a region out, measure time-to-writable and throughput, and write down what broke. Numbers from a spreadsheet are not a capacity plan.

Why is two data nodes plus an arbiter a fragile design?

Because it looks redundant and is not. You have two copies of the data, so a single host failure leaves you with one copy and no redundancy; the arbiter supplies the third vote but no third copy. Elections work, which is what makes the design seductive, but the durability story is unchanged from a single node.

The specific hazard is w: "majority". In a PSA (primary-secondary-arbiter) set, the majority is two votes, and the primary plus the arbiter satisfy it — so a write can be acknowledged as majority-committed while existing on exactly one data-bearing member. If that member then fails before replicating, the write is rolled back, which contradicts what "majority" is supposed to mean. Add the practical costs: arbiters add election latency, cannot serve reads, cannot be a sync source, and must be upgraded in lockstep, so they are operational overhead with no data benefit.

The credible alternatives are three data-bearing members, or accepting a two-node design explicitly as non-HA with a documented RPO above zero.

What is wrong with running all three members in the same availability zone?

It protects against one failure mode — a mongod process or host dying — and against nothing else. An AZ failure, a rack power event, or a control-plane incident takes all three members at once, so you have the cost of a replica set and the availability of a single node.

The mismatch is between the failure domain you replicate across and the failure domain your SLA names. If the business cares about AZ-level events, members must be in distinct AZs; if it cares about region-level events, you need a cross-region member, which then changes latency and w: "majority" cost. A common compromise: two members in the primary AZ for low-latency majority writes, one in a second AZ with priority: 0, and an explicit statement that a primary-AZ loss means a manual or scripted recovery. Whatever you choose, verify that the placement is enforced and not just documented — a node that drifts back into the same AZ during a rebuild silently breaks the design.

Why can analytics on secondaries end up degrading the primary?

The obvious damage is local: reporting queries evict the working set from the secondary's WiredTiger cache, the oplog applier yields its locks to those reads, and the node falls behind. The non-obvious damage is on the primary, through the majority commit point. w: "majority" waits for a majority of voting members to durably apply each write, so a secondary that is 90 seconds behind reporting load becomes the slowest member of every majority — and every write on the primary inherits that latency.

So a reporting job can present as "the primary is slow" with the primary's own CPU and IO flat. The diagnostic is to compare lastCommittedOpTime with each member's optime; the offender is the one holding the commit point back. Mitigations: keep heavy analytics off voting members, use a dedicated hidden member with more RAM, bound queries with maxTimeMS and indexes, or feed analytics from change streams into a separate store. Do not solve it by lowering write concern — that trades latency for data loss.

What is wrong with w:1 in a payments system?

It makes "confirmed" a lie. A payment recorded with w: 1 can be rolled back after the client has been told it succeeded, leaving an external charge with no matching record. The failure is silent and asymmetric: the ledger says it never happened, the provider says it did, and reconciliation is manual.

The correct write concern for money movement is { w: "majority", j: true }, on the same operation that changes the balance, ideally with a unique index or transaction ensuring the invariant. If the latency is unacceptable, the design changes, not the guarantee: keep the majority in one low-latency region, write a local intent record with w: 1 plus a domain event confirmed durably by another process, and let the state machine tolerate a pending state. What you must never do is tell the user "paid" on the basis of an uncommitted write.

Also, retryWrites will happily retry a rolled-back write and double-charge unless the operation carries an idempotency token: the retry layer is not a substitute for durability.

Why is readPreference: secondary dangerous for reads that need freshness?

Because secondary says nothing about how current the data is. Replication is asynchronous, so a secondary can be seconds or minutes behind, and the driver will happily serve a read from the most available secondary. The user writes a profile, reloads, and sees the old value — the classic read-your-writes violation, which looks like a caching bug and is not.

Three fixes, in increasing strength. Use primary for anything that must reflect a just-completed write. Use readConcern: "majority" so at least the data is committed, though that still permits staleness relative to your own write. Or use causal consistency: a session that carries afterClusterTime guarantees the secondary waits until it has applied everything the primary had when your write was acknowledged.

const session = client.startSession({ causalConsistency: true });\nawait coll.updateOne({ _id }, { $set: { name } }, { session });\nawait coll.findOne({ _id }, { session, readPreference: \"secondary\" });

Also remember maxStalenessSeconds is a bound, not a guarantee of freshness.

What goes wrong with a replica set in containers with no persistent volumes?

Every restart is a full data loss for that member. A pod rescheduled onto another node starts with an empty dbPath, so it performs an initial sync — expensive, and impossible if the rest of the set is unavailable. Worse, if all three members restart at once, they come up empty, have no oplog and no data, and there is nothing to sync from: the deployment is simply gone.

The related failure is identity. Replica set membership is keyed on host names, so with ephemeral pod names every restart requires a reconfiguration, which is exactly the operational burden a StatefulSet with stable network identities and a PersistentVolumeClaim per replica exists to remove. Checklist: a PVC per member, stable DNS names, podManagementPolicy: Parallel only when you understand election timing, resource limits above the WiredTiger cache, and a readiness probe that checks replication health rather than just port availability. And back up independently of the volumes — a storage class that loses its backing disk is not a backup strategy.

How does a misconfigured DNS name in the connection string present itself?

As a server-selection problem that looks like a database outage. Symptoms: MongoServerSelectionError or a topology timeout, application startup failures, and a message listing hosts that could not be reached — while the cluster is perfectly healthy and reachable from another network.

Frequent causes: the URI lists a hostname only resolvable inside the VPC; a mongodb+srv record whose SRV targets are private; a member's configured host name pointing at an internal name that clients cannot resolve; certificate names not matching the name used; or split-horizon DNS where the container resolver differs from the host's. Remember that a replica set's members address each other using the names in rs.conf(), so a client can connect but still fail to discover the primary if the discovered names are unresolvable.

nslookup m2.example.com\nmongosh \"mongodb://h1:27017/?replicaSet=rs0\" --eval \"rs.status().members.map(m => m.name)\"

Fix by using names that are resolvable from every client and every member, and verify from inside the same network namespace the app runs in.

Why is retryWrites a safety net rather than a design?

retryWrites=true (default in modern drivers) retries a single write once, after a fresh server selection, when the error is retryable and the deployment supports it. That covers the common blip — a primary stepping down between the write and its acknowledgement. It does not cover a down primary for 60 seconds, a write that failed for a validation or duplicate-key reason, a non-retryable command, or anything outside a session-aware write path.

Design implications: the write must still be idempotent for the cases retryable writes cannot see, such as a w: 1 write that was rolled back, or a client crash after the server applied the write but before the response arrived. Give inserts a deterministic _id, use $setOnInsert upserts keyed by an idempotency token, and never build business logic that assumes exactly-once execution. Retryable writes reduce error rates; they do not make an operation idempotent, and they cannot protect a side effect like an email or a card charge that lives outside the database.

"The primary is alive but won't accept writes" — how do you diagnose that?

First separate the two meanings: it is not primary, or it is primary and refusing. Check rs.status().myState and db.hello().isWritablePrimary. If it is not primary, you have an election problem — look at term, electionDate and whether a majority is reachable. If it says primary but writes fail, the errors name the cause: NotWritablePrimary after a stepdown, a WriteConcernFailed timeout from a lagging majority, or a disk-full error.

db.hello()\ndb.serverStatus().wiredTiger.cache\ndb.currentOp({ active: true })\nrs.printReplicationInfo()

What causes election loops, and how do you break one?

Repeated elections mean the set keeps changing its mind about who should lead. Typical causes: an unstable network where heartbeats fail intermittently; electionTimeoutMillis set too low for the platform's pause behaviour; nodes too overloaded to respond within the timeout; members whose oplog is far behind, so a candidate can never win and the vote repeats; and priority configurations that make two members compete evenly while the third keeps abstaining.

Diagnose by reading metrics.repl.electionMetrics and the server log for "election succeeded/failed" reasons, then correlating with host metrics. Breaking the loop: raise electionTimeoutMillis so transient stalls stop triggering votes, fix the underlying IO or CPU saturation, give one member a clearly higher priority so leadership is deterministic, and make sure all voting members can actually reach each other. In a multi-region set, also confirm the two low-latency members are the likely candidates, since electing the far member adds latency to every subsequent write.

What is the risk of upgrading MongoDB without reading the compatibility notes?

You discover behaviour changes in production. Between majors, MongoDB changes defaults, removes deprecated commands and options, bumps index versions, and — most importantly — ties new features to the feature compatibility version. If you raise setFeatureCompatibilityVersion before every member and every driver path is ready, you lose the ability to downgrade, because the on-disk format is already the new one.

The disciplined sequence: read the release notes for removed and deprecated behaviour, check driver and tool versions, upgrade secondaries one at a time, step down the primary, upgrade it last, then raise FCV as a separate deliberate step after the set has been stable. Watch for silent changes — default write concern, slaveDelay becoming secondaryDelaySecs in 5.0, telemetry and logging additions. Test the upgrade on a restored copy of production, not on an empty cluster, because the failures that matter are data-shape and query-planner failures. Treat a downgrade path as a requirement, not a luxury.

Why is a single mongos or a single app server a hidden single point of failure?

Because the database's redundancy stops at the cluster boundary. A sharded cluster with three-member replica sets per shard is still unavailable if the only mongos process is down, or if the single application host is down, or if the load balancer in front of them has one target. The replica set protects data and provides failover; none of that helps when there is no router to send the request through.

The fix is mundane and often skipped: run at least two mongos routers per application, list multiple hosts in the connection string (host1,host2 using topology discovery), put them behind a load balancer with health checks, and don't let the routers share a host or AZ. On the application side, run more than one instance and make the readiness probe depend on a database round trip, so a broken instance leaves the pool instead of receiving traffic. Any place where a single process is the only path to data is a SPOF, regardless of how many replicas exist behind it.

What does w:majority cost in a multi-region deployment, and what are the alternatives?

The cost is one cross-region round trip per write, plus journaling, with the majority defined by member placement. Three regions with one member each means every write needs an acknowledgement from another continent: 100–250 ms p50 and much worse at p99. The same guarantee with two members in the primary region costs a local hop, because the majority is satisfied locally.

Alternatives, in order of preference. Place two of three voting members in the primary region and keep the third as a priority: 0 DR member, so majority latency is local while durability still spans regions. Reduce the number of operations needing majority: batch writes, use transactions for multi-document invariants instead of per-document round trips, and reserve strict concern for state transitions rather than telemetry. Consider w: "majority" with j: false only if you understand the difference between process and host failure. What you should not do is quietly drop to w: 1 on financial data — that moves the cost from latency to reconciliation.

Walk me through how MongoDB actually commits a multi-document transaction: who decides, and where is that decision written?

There is no monolithic BEGIN on the server. startTransaction() is client-side bookkeeping; the first statement assigns a txnNumber and registers the transaction. From then on one node is the coordinator: the mongos the session is pinned to in a sharded cluster, or the primary in a plain replica set.

Commit is two-phase. Phase one, prepareTransaction goes to every participant: each shard takes its locks, persists a prepared record and refuses to rewind. Phase two, the coordinator durably writes the decision — commit or abort — into config.transactions, and only then tells participants to commit. That ordering is the guarantee: once the decision exists, the outcome is fixed, and a crash mid-broadcast is recoverable by replaying it. Participants hold their own record until the decision reaches them.

What exactly is stored in config.transactions, and why is the record kept after the commit?

config.transactions is an ordinary replicated collection, and that is the design: the decision must survive failover like any other data. Each document is keyed by lsid plus txnNumber and carries the state (prepared, committed, aborted), lastWriteDate, and for prepared entries the oplog slot and write concern the coordinator committed with.

Records are not deleted at commit. A cleanup thread removes one only when no further message about that transaction can plausibly arrive — anchored to the majority commit point plus a grace period, tunable through transactionRecordMinimumLifetimeMinutes (30 minutes by default). That retention window is what makes a retried commit safe: the second commitTransaction finds the record, returns the stored outcome, and applies nothing twice. On a sharded cluster the coordinator's record lives with the config server, and each participant shard keeps its own.

Snapshot isolation: what anomalies does it actually eliminate, and which one does it leave open?

Every transaction reads from one WiredTiger snapshot taken at its first read, and its writes become visible only at commit. That eliminates dirty reads, non-repeatable reads and phantoms inside the transaction — re-running the same query returns the same rows — and it eliminates lost updates on documents you actually write, because a concurrent modification of a document you hold produces a WriteConflict and aborts you.

What survives is write skew. Two transactions can read overlapping sets, each check an invariant, and write disjoint documents. Nothing conflicts, both commit, the invariant is broken. MongoDB never takes predicate or range locks, so it cannot notice that the two read sets intersected. Serializability is not offered, and no isolation level setting buys it. The engineering consequence: invariants must be materialized onto a document that both transactions must write.

Show me write skew in a schema you have actually seen. How do you make it impossible?

Constraint: at least one engineer per team stays on call.

// T1 and T2 run concurrently, both read onCall: 2
const n = await coll.countDocuments({ team: "pay", onCall: true });
if (n > 1) {
  await coll.updateOne({ _id: myId }, { $set: { onCall: false } });
}

T1 takes Alice off, T2 takes Bob off. Different documents, so no conflict, both commit, nobody is on call.

Three honest fixes. Move the invariant onto a document both must write: a { team, onCallCount } row they $inc with $expr guarding the floor, so the second one gets WriteConflict and retries. Or hold an explicit lock document per team for the critical section. Or restate the rule so a unique index can enforce it. Retrying harder does nothing — the anomaly is logical, not a race the engine can see.

What happens at the 60-second transaction limit, and what does the client actually receive?

transactionLifetimeLimitSeconds defaults to 60. A background cleanup task, running on a fixed interval, finds transactions past their lifetime, aborts them and releases their locks and snapshot. In a sharded cluster the parameter must be set on every shard replica set member, not just on mongos, or shards disagree about who is still alive.

The client does not get a clean "timeout". The next statement on that session fails with NoSuchTransaction (code 251), which carries the TransientTransactionError label. A driver running the standard retry loop will therefore silently start the whole transaction over. That is correct for a transaction that was simply too big, and pathological when the transaction was slow because it was queueing behind a lock: the retry has the same footprint and will hit the same wall at t+60s, forever. Alert on repeated retries of the same txnNumber chain.

Your retry block failed again, this time inside commit. How do you tell whether the data actually landed?

You cannot tell from the error, and that is precisely what UnknownTransactionCommitResult means: the commit may have been applied and the reply lost. Three defences, in order of value:

  1. Retry the commit only — never the body — while the label is UnknownTransactionCommitResult, with w: "majority" and a bounded maxTimeMS. When the budget is exhausted you are in genuinely unknown territory.
  2. Make the body idempotent through a natural key, so a blind replay cannot double-apply.
  3. Read back with readConcern: majority on the key you wrote. That is the only authoritative answer.

Note the asymmetry: a TransientTransactionError arriving after a commit that already returned ok: 1 is noise — the commit reply is final.

Does a transaction have a 16 MB limit? Explain where the limit really sits.

The aggregate cap is gone. The server writes as many oplog entries as necessary to describe a transaction, so a 40 MB transaction is not rejected for total size the way pre-4.2 folklore claims. What remains is the per-entry BSON limit: each applyOps entry must stay under 16 MB, and the server splits the write set across entries to respect that.

Size still bites in three places. A single statement whose write set cannot fit one entry — a giant $push or a huge bulk update inside the transaction. The WiredTiger cache ceiling: a transaction too large to ever fit aborts with TransactionTooLargeForCache, which is a cache error wearing a size costume. And replication: secondaries replay those entries one at a time, so one enormous transaction becomes a catch-up burst on every member rather than a single atomic step.

Can you create a collection or an index inside a transaction? Explain the restriction precisely.

The premise is stale. Since 4.4 you can create collections and indexes in a transaction, with hard conditions: the transaction must not be a cross-shard write transaction, and the collection must not be capped. So on a replica set it works; in a sharded cluster it works only while the transaction stays on one shard.

Cross-shard DDL is forbidden for good reasons. A metadata change has no document identity to conflict on, so there is nothing for the two-phase machinery to lock per participant; the catalog write would have to be visible to other sessions watching that namespace, which breaks the snapshot the transaction is built on; and a failing build would have to be rolled back on shards that already published the namespace. The practical rule stands: create the namespace first, with w: "majority", before you open the transaction that uses it, or the transaction can fail to acquire its lock.

Why does readConcern snapshot cost memory, and who pays for it?

WiredTiger is MVCC: it keeps old versions of changed documents so a reader holding an older snapshot can still find them. The transaction's snapshot pins that point in time. Any document the transaction may still read cannot have its obsolete versions discarded, and the pages holding them cannot be evicted freely.

So the cost is indirect but real. Updates made by other sessions accumulate in the history store for as long as your snapshot lives, and cache that would hold hot working-set pages is spent holding versions nobody will read again. Long transactions therefore degrade the whole node, not just themselves — you see rising cache pressure, more eviction, friendlier-looking latency for everyone else. That is why the docs tell you to abortTransaction() rather than simply abandon a session, and why the 60-second lifetime limit exists at all: it is a cache-protection mechanism before it is a fairness mechanism.

In a sharded cluster, what does the mongos coordinator own that a replica set primary does not?

A replica set commit is one-voter: the primary writes the decision into its own config.transactions and the oplog does the rest. A distributed commit has independent failure domains, so mongos becomes an actor in its own right.

The coordinator — chosen at the first statement, and sticky for that transaction — drives prepareTransaction to each participating shard, so each holds its locks in a prepared state; persists the decision on the config server; then broadcasts commit and cleans up. It also owns recovery: if the mongos dies mid-commit, the decision already on the config server lets another mongos finish the job after the client retries commit. Two practical consequences follow. Every statement in a sharded transaction costs extra round trips, and losing the mongos between prepare and commit is a real latency spike, not a theoretical one. Also, all participating shards must be up in the same window — a shard down means the transaction cannot prepare.

What does maxTransactionLockRequestTimeoutMillis control, and when do you touch it?

It bounds how long an operation inside a transaction waits for a lock before giving up. Default is 5 milliseconds, and the failure surfaces as a write conflict carrying TransientTransactionError. Setting it to -1 means wait indefinitely, which is almost always wrong.

You raise it for one recognizable pattern: a fast metadata operation, a short index build or a create that momentarily holds a collection lock, aborts every in-flight transaction that touches the same namespace. Bumping the value to a few tens of milliseconds lets those transactions ride out the blip instead of retrying.

But be honest about the trade. This parameter only delays the abort; it does not resolve deadlock, and a large value turns a fast failure into a slow one, which is worse under load because lock queues grow. It also has to be at least as long as the in-progress transaction plus the pending DDL needs, otherwise transactions waiting behind the DDL abort anyway.

Can a transaction read a value another transaction wrote but has not committed? Be exact about what it can read.

No. Uncommitted writes are private to their transaction: they are not in any snapshot another session can acquire, so a dirty read is structurally impossible rather than merely discouraged. Snapshot visibility is taken at commit.

What a transaction can do is read stale data, and this trips people up because it looks like the opposite failure. Because the snapshot is fixed at the first read, a write that commits outside your transaction after that point is invisible to you for the rest of the transaction. The documented version of this is stark: another session deletes a document, and your transaction still reads it happily. If a read must see the latest committed state, take a write lock with a findOneAndUpdate that touches the document — that both refreshes visibility and makes the conflict explicit.

Separately, readConcern: local outside a transaction can return data that is later rolled back. That is not a dirty read either; it is uncommitted-by-majority data.

Why does one long-running transaction hurt sessions that have nothing to do with it?

Because MVCC cleanup is global. WiredTiger cannot discard an old document version while any active snapshot might still need it. One transaction holding a snapshot from ten minutes ago forces the engine to retain every version of every document touched since then, in the history store, on disk and in cache.

The symptoms look unrelated to transactions: cache fill ratio climbing, eviction pressure, reads that suddenly need disk, write latency creeping up as updates must chase older versions. Teams spend hours tuning indexes for a problem caused by an abandoned session in a debugger.

Operationally: always abortTransaction() in a finally block, keep transactionLifetimeLimitSeconds at a value you can defend, and treat "open transactions older than N seconds" as a first-class alert rather than a curiosity. The limit exists to cap this blast radius.

Someone proposes transactionLifetimeLimitSeconds: 600 to stop retries. Argue both sides.

The case for it: if legitimate transactions genuinely need 90 seconds — a batch reconciliation, a report that aggregates then writes — then a 60-second abort is a coin flip that produces retry storms and duplicate work.

The case against, which usually wins: the limit is a proxy for cache protection, and raising it multiplies the history-retention cost described above across every concurrent transaction. Ten-minute transactions on a busy primary will show up as cache pressure and secondary lag, not as clean errors. Worse, a longer limit converts fast failures into slow ones: a transaction stuck behind a lock now occupies a session slot for ten minutes instead of one.

My answer in a design review: keep 60, and move the long work out of the transaction — precompute in a staging collection, then commit a small delta. If the parameter must move, change it on shards and coordinator together and re-measure cache pressure afterwards.

Inside WiredTiger, what has to be true for an update to fail with WriteConflict?

Three conditions converge. The updater holds a snapshot, and the target document's current version was committed after that snapshot. The engine walks the update chain for the key, finds a version newer than the reader's snapshot, and cannot legitimately apply the change without violating isolation. It returns WT_ROLLBACK, which mongod translates into code 112, WriteConflict.

Two nuances separate seniors from people who have read one blog post. First, the storage engine retries certain conflicts internally before surfacing one — so the error the application sees means repeated attempts already failed. Second, behaviour differs by context: inside a transaction the conflict aborts the transaction and is labelled TransientTransactionError; outside a transaction the server retries the operation itself a bounded number of times, which is why a non-transactional $inc rarely reports one. The document lock itself is short — conflicts come from snapshots, not from lock hold time.

What are concurrency tickets, and how do they turn into latency you can measure?

WiredTiger admits only a fixed number of concurrent operations into the storage engine — the classic defaults are 128 read tickets and 128 write tickets, and the server exposes them under serverStatus().wiredTiger.concurrentTransactions with available, out and totalTickets.

Tickets are a throttle, not a lock: an operation that cannot get one queues in the server, invisible to the query plan. That is why a node can show low CPU, no lock waits worth mentioning, healthy disk, and still serve 200 ms reads — the time is spent waiting for admission. The signature is available pinned at zero with out at the ceiling during the slow window.

Do not "fix" this by raising the ticket count casually. More concurrency into a saturated cache or disk usually lowers throughput. Read it as evidence that you have more concurrent work than the node can service, then attack the real cause: too many connections, unindexed scans holding tickets longer, or hot documents serializing writes.

What does yielding mean in MongoDB's concurrency model, and why does it make updates less predictable?

An operation that would otherwise hold a lock for a long time periodically releases it so others can make progress — the classic triggers are a page fault that forces a disk read, or a large number of documents modified in one statement. The engine must then verify nothing changed underneath before resuming; if it did, the operation can be rolled back and retried.

The observable cost: numYields in the profiler and in slow-query logs. A high yield count means the statement kept surrendering its position — typically a scan without a supporting index, or a mass update racing other writers.

The correctness lesson matters more than the metric. Because an update can yield mid-flight and be retried, an operation is atomic per document, but two operations on the same document are not ordered the way wall-clock logs suggest. Never infer ordering from application timestamps; use a monotonic counter or the server's own ordering to reason about "which write won".

Two updates hit the same document at the same instant. Walk me through what the server does.

They serialize, necessarily. WiredTiger takes an exclusive lock on the document (internally, on the update chain for that key) for the duration of the modification. The second updater blocks on that lock — but only briefly, because the critical section is short: append a new version, release.

The interesting part is what happens next. Once it acquires the lock, the second updater re-examines the document against its own snapshot. If the first write is now newer than that snapshot, the second cannot apply blindly, and it either retries with a fresh snapshot (non-transactional path, server-side) or aborts with WriteConflict (transactional path).

So "serialized" does not mean "both applied in order". One of them may fail and be retried, and an operation that read the document earlier in the same transaction will be aborted rather than allowed to write over newer data. That is the mechanism behind lost-update protection on a single document.

Show me the retry loop you put around a transaction in production, and justify every line.

async function runTxn(fn, { attempts = 5 } = {}) {
  for (let i = 0; i < attempts; i++) {
    const session = client.startSession();
    try {
      let out;
      await session.withTransaction(async () => {
        out = await fn(session);
      }, {
        readConcern: { level: "snapshot" },
        writeConcern: { w: "majority" },
        maxCommitTimeMS: 5000
      });
      return out;
    } catch (e) {
      if (!e.hasErrorLabel("TransientTransactionError")) throw e;
      const base = Math.min(2 ** i * 50, 1000);
      await sleep(base / 2 + Math.random() * base); // jitter
    } finally {
      await session.endSession();
    }
  }
  throw new Error("transaction retry budget exhausted");
}

Why each piece: withTransaction retries the commit on UnknownTransactionCommitResult for you, so your loop only handles the body. Jitter prevents every replica of your service retrying in lockstep and re-creating the same conflict storm. A bounded attempt count stops the pathological case where the transaction is simply too contended. A fresh session per attempt avoids inheriting a poisoned transaction state.

How do you separate an error worth retrying from a bug you should page someone about?

Trust the labels, not the message. TransientTransactionError means "the world moved, the same transaction could work now": write conflicts, lock timeouts, NoSuchTransaction, a stepdown during the transaction, TransactionTooLargeForCache when contention inflated the working set. UnknownTransactionCommitResult means "commit outcome indeterminate" and only the commit is retried. RetryableWriteError is the non-transactional sibling.

Everything else is logic: DuplicateKey from a real duplicate, schema validation failures, NamespaceNotFound, BSONObjectTooLarge, "cannot use $expr here", anything you can reproduce deterministically. Retrying those is a latency amplifier that hides the defect.

The trap is a transaction that always conflicts under some traffic shape: it is labelled transient, so the loop spins, and you get 500s only after the budget drains. Log the attempt count. A transaction that needs three retries is a design smell, not bad luck.

How do you make a retried write idempotent when you have no _id to key on?

You invent a natural key from the request, and you let a unique index enforce it. The idempotency key should be stable across retries and distinctive per logical operation — derived from something the caller supplies, not from a timestamp or a random UUID generated inside the retry block, which would defeat the whole exercise.

// unique index: { accountId: 1, requestId: 1 }
try {
  const r = await coll.insertOne({ accountId, requestId, amount, status: "posted" });
  return { created: true, id: r.insertedId };
} catch (e) {
  if (e.code !== 11000) throw e;
  return { created: false, doc: await coll.findOne({ accountId, requestId }) };
}

The duplicate key error becomes the success path for a replay. Two details: the index is the mechanism, not a hint — without it you get two documents; and the document must be written in the same statement as the state it describes, otherwise a crash between operations leaves the key recorded and the work undone. For multi-document effects, the key belongs inside the transaction.

Concurrent upserts: where exactly is the race, and what does a unique index change about it?

The race is that upsert is not omniscient. The server matches the filter, finds nothing, and inserts. Two concurrent upserts on the same filter can both observe "no match" before either insert lands. Without a constraint on the filter fields, you get two documents and no error — the worst outcome, because it looks like success.

With a unique index on the fields the filter matches, one insert wins and the loser gets DuplicateKey (11000). That error is not a bug, it is the coordination primitive: catch it and retry the same upsert, which now takes the update path. That is the documented, safe pattern, and it is why "use upsert" without an index is bad advice.

Note the subtlety inside transactions: a duplicate key error inside a multi-document transaction kills the transaction, so you must retry the whole transaction, not just the statement. And the filter must match the index exactly, or the constraint does not apply.

Use findOneAndUpdate as a lock primitive. What must the filter contain to be safe?

const now = new Date();
const lease = new Date(now.getTime() + 30_000);

const doc = await locks.findOneAndUpdate(
  { _id: "invoice:42", $or: [ { owner: null }, { expiresAt: { $lt: now } } ] },
  { $set: { owner: workerId, expiresAt: lease, fence: { $add: ["$fence", 1] } } },
  { returnDocument: "after", upsert: false }
);
if (!doc) throw new Error("lock held by someone else");

The filter must express ownership and expiry in the same predicate — that single atomic compare-and-set is the entire lock. returnDocument: "after" gives you the lease you actually hold rather than the one you hoped for. The fence increment is what makes the lock usable: downstream writes must carry the fence value they were granted, so a worker that lost its lease cannot overwrite the new owner's work.

Keep upsert: false. An upsert here would happily create a second lock document under a different filter shape, or resurrect a deleted one. Provision the lock rows in a migration instead.

Why is a MongoDB-based distributed lock fragile enough that you should not build correctness on it?

Because it inherits every failure mode of a lease, and adds a few of its own. Three killers:

  • Process pause. A GC pause, a VM freeze, a SIGSTOP. The worker wakes up believing it holds a lease that expired two seconds ago and writes over the new owner's work.
  • Clocks. Lease expiry compares timestamps. Skewed client clocks make a holder expire early or never. Never send new Date() from the app for expiry arithmetic; use $$NOW or $currentDate so the server's clock is authoritative.
  • TTL is not immediate. A TTL index deletes on a background sweep, roughly every 60 seconds, so "the lock expires at T" is really "somewhere after T".

The mitigation is fencing, not tighter timing: monotonically increasing tokens that the resource itself validates, rejecting stale writers. If the destination cannot validate a fence, MongoDB is the wrong lock. Use a system that offers consensus semantics, or redesign so the operation is idempotent and the lock is only an optimization.

Show me a lost update caused by $set, and the two ways to fix it.

The application reads, computes, writes back:

const acc = await coll.findOne({ _id: "A" });   // balance 100
// ... 40 ms of business logic, another writer deposits 50 meanwhile
await coll.updateOne({ _id: "A" }, { $set: { balance: acc.balance - 30 } });
// balance becomes 70, the +50 is gone

The $set carries a value computed from a stale read, so it overwrites whatever happened in between. The document was never concurrently written while the update ran — there was no conflict to detect. That is why this bug survives load testing.

Fix one, express the delta: { $inc: { balance: -30 } } — server-side arithmetic on the current value, atomic, no stale input.

Fix two, guard the write with $expr so it only applies when the precondition still holds: { $expr: { $gte: ["$balance", 30] } } with $inc. Check matchedCount to learn whether the guard held. Both keep the decision on the server, which is the actual fix.

Implement compare-and-set with a version field so the API distinguishes "wrong version" from "not found".

const res = await coll.updateOne(
  { _id: id, version: expected },
  { $set: { status: next }, $inc: { version: 1 } },
  { writeConcern: { w: "majority" } }
);

if (res.matchedCount === 0) {
  const exists = await coll.countDocuments({ _id: id }, { limit: 1 });
  return exists ? 409 : 404;          // conflict vs missing
}

The version lives in the same document as the state it protects, so the check and the write are one atomic operation. Increment always, never set the version to a literal — that reintroduces the race you are removing.

The follow-up read is honest only because "not found" is stable: a document that exists cannot spontaneously become the wrong version for long, though it can be deleted between the two calls. If that distinction matters, wrap both in a transaction with readConcern: snapshot. Also note matchedCount vs modifiedCount: a no-op update can match without modifying, so branch on matched.

Why must the outbox insert share the transaction with the business write? What breaks otherwise?

Because you are trying to make a database commit and a message publication agree, and they are different systems with independent failure modes. Write the order, then insert the outbox row, and a crash between them loses the event. Insert the outbox row first and a rolled-back order emits a phantom event.

await session.withTransaction(async () => {
  await orders.insertOne({ _id: orderId, ... }, { session });
  await outbox.insertOne({
    _id: new ObjectId(), topic: "order.created", payload: { orderId },
    createdAt: new Date(), status: "pending"
  }, { session });
}, { writeConcern: { w: "majority" } });

One transaction, one commit point: either both documents exist or neither does, and the relay can never publish something that did not happen. This is the one place where a transaction buys you something a change stream cannot — a change stream on orders has no way to know a second write was supposed to accompany it.

When is a saga the right answer instead of a transaction, and what do you owe the design?

A saga is right when the work spans services or genuinely cannot fit in one transaction's time and cache budget: charging a card at a third party, provisioning in another system, migrating ten thousand documents. Holding a MongoDB transaction open across a network call to a payment provider is the anti-pattern that produces 60-second aborts and locks held for no reason.

The price is that you no longer have atomicity, you have compensations, and every one of them must be designed, tested and idempotent. Concretely you owe: a persisted saga log with a state per step, forward recovery that resumes from the log after a crash, compensating actions for each completed step (a refund, not a "delete the charge"), and a monotonic guard so a compensation cannot fire after the saga already succeeded.

Also decide the semantics out loud. Between steps the system is visibly inconsistent; someone will query it. Either hide that state from readers or make it legitimate in the model.

What does a logical session actually guarantee, before any of the consistency features on top of it?

Very little on its own, which is why the name misleads people. A session is a server-side identity — the lsid UUID — that lets the server correlate operations from one client over time, across connections and across failover. That correlation is the substrate for everything else: retryable writes, causal consistency, transactions.

Without opting into causal consistency, a session guarantees no ordering across members. It does not pin you to a server, it does not hold a snapshot, and it does not create a transaction. What it does give you is a stable handle the driver can re-send operations under so the server can recognise a retry.

The lifetime is worth memorising: sessions expire server-side after logicalSessionTimeoutMinutes, 30 minutes by default, and the driver refreshes activity on use. A session idle for longer is silently forgotten — this is why a long-parked session's txnNumber history no longer protects you.

How does afterClusterTime actually deliver read-your-own-writes?

The mechanism is a timestamp, not a routing trick. Every write returns an operationTime. In a causally consistent session the driver remembers the highest one seen and attaches it to subsequent reads as readConcern: { level: "majority", afterClusterTime: <ts> }.

The receiving member then refuses to answer until its applied oplog timestamp reaches that value. A secondary that is 300 ms behind will wait 300 ms, not return stale data. That is the whole guarantee, and it is a floor, not a snapshot: you get "at least as new as what I wrote", not "a consistent point in time across all my reads" — that needs snapshot.

const s = client.startSession({ causalConsistency: true });
await coll.insertOne({ _id: 1 }, { session: s });
await coll.findOne({ _id: 1 }, { session: s }); // waits for the write

Cost: you have traded a stale read for a blocking wait, so a lagging secondary converts into tail latency. Alert on it.

How does the timestamp travel between operations in a causal session?

Two channels, and conflating them causes real bugs. First, operationTime: a per-operation value in the reply that the driver advances its session watermark with. Second, $clusterTime: a cluster-wide gossip value that members exchange in every reply and every heartbeat, so time-like knowledge propagates even without client traffic.

The driver's rule is simple — take the max it has seen and send it on the next read as afterClusterTime. It never needs to reason about which node served what.

What breaks causality in practice: doing part of the work outside the session. If one statement runs on a session-less implicit session, its timestamp never enters the watermark, and the following read can legally return a state that predates it. The same applies when you hand a write's result to a different session or a different client instance. Causal consistency is a chain, and every un-sessioned call is a broken link.

Implicit sessions: what is the driver doing behind your back, and when does it bite?

Every operation you issue without a session still gets one — the driver creates an implicit session, uses it for that single operation (or that cursor's lifetime), and returns it to a pool. That is what makes retryable writes work by default: without an lsid and txnNumber, the server could not recognise a duplicate.

It bites in three places. Cursors: an implicit session is attached to the cursor, and if the cursor lives long, the session is held, which matters on servers with a low session pool. Read-your-own-writes: implicit sessions are independent, so operation two has no idea what operation one wrote — you need one explicit session spanning both. And transactions: a transaction requires an explicit session, full stop.

Explicit sessions are cheap, so the senior habit is to pass one session through a request's unit of work rather than sprinkling session-less calls and hoping causality sorts itself out.

What happens on endSession, and what happens if you never call it?

endSession() returns the session to the client-side pool and, on client close, the driver sends endSessions to the server so records can be reclaimed promptly. It does not abort an open transaction; if you end a session with a live transaction, the server eventually expires it, but until then it holds locks and a snapshot.

If you never call it: nothing dramatic at small scale, because sessions expire after logicalSessionTimeoutMinutes (30 by default) and the server reclaims them. At scale, the failure is a session-pool squeeze — leaked sessions per request exhaust the pool, and new operations block waiting for one, which presents as unexplained latency under concurrency.

Two habits: always endSession() in a finally block, and prefer withSession/withTransaction helpers that do it for you. If you ever lower logicalSessionTimeoutMinutes, remember the driver caches session state for that window — a mismatch between driver and server values causes retryable writes to silently stop being retried.

Which operations and which errors make a write retryable — and which look retryable but are not?

Retryable by the driver: single-document writes — insertOne, updateOne, replaceOne, deleteOne, findOneAndUpdate and friends, plus insertMany and bulk writes with ordered: false. Not retryable: multi-document updates and deletes, and ordered: true bulk inserts, because the driver cannot prove partial application is safe.

Errors: anything the server labels RetryableWriteError — primary stepdown, NotWritablePrimary, InterruptedDueToReplStateChange, shutdown in progress — plus network errors where the write may or may not have arrived. A WriteConcernError is not a reason to re-send the write; the write landed, only the acknowledgement is short.

The trap: a retry can turn a timeout into a duplicate if the operation was not idempotent. Retries protect you from transport, not from design. And a retryable write still needs w: > 0, a replica set, and a server that has not expired the session record.

Why does w:0 switch retryable writes off entirely?

Retry safety needs an acknowledgement. With w: 0 the driver fires and forgets: there is no reply carrying the lsid/txnNumber outcome, so nothing distinguishes "the server applied it and the reply was lost" from "the socket died before it arrived". Re-sending would risk a duplicate, so the driver refuses to retry at all — and the server cannot help, because the whole dedup mechanism is keyed on a statement it already recorded.

Consequences people miss: w: 0 also silently disables transaction support (a transaction needs an acknowledged commit), and it gives you no operationTime, which breaks causal consistency on that session.

Where it is legitimate: high-volume telemetry or metrics where losing a sample is acceptable and latency dominates. Even then, ask whether w: 1 with retries is not simply the better trade — the failure mode of w: 0 is silent data loss, which nobody ever alerts on.

If a write with $inc is retried, is it applied twice?

Not if the driver retried it as a retryable write. The server records the lsid plus txnNumber of the last applied statement, and a repeat of the same pair returns the cached result without re-executing. So $inc: { count: 1 } stays at one increment even though the command went over the wire twice. This is a genuinely non-idempotent operation made safe by bookkeeping.

It breaks in exactly these cases: the driver has retryable writes disabled (retryWrites=false in the URI), the deployment is a standalone, w: 0 was used, the operation is a multi-document update, or your code retried — an application-level catch that re-issues the updateOne gets a fresh txnNumber and does double-count.

So: $inc plus driver retries is safe; $inc plus your own retry loop is a double-count waiting for a slow network. Wrap app-level retries in a documented key or a transaction.

Transaction commits and retries: what exactly is the driver retrying, and with what settings?

withTransaction maintains one commit attempt loop. If commitTransaction fails with UnknownTransactionCommitResult, it re-sends only the commit — the body is never re-run, because the body may already have been applied. It retries until the error stops carrying that label.

Practical settings worth setting explicitly: writeConcern: { w: "majority" } on the transaction so a commit that returns really is durable on a majority, and maxCommitTimeMS so a commit that is stuck behind replication lag cannot hang the request thread indefinitely. A commit that times out is not a failure — it is an unknown, which is a third state your code must handle.

The senior point: the retry is safe because the server remembers the decision in config.transactions. If you "helpfully" add your own commit retry around the driver's, you can interleave commits from two code paths on one session, which is the kind of bug that only appears during a failover test.

lsid and txnNumber: what does the server actually remember, and for how long?

lsid identifies the session; txnNumber is a monotonically increasing counter per session, allocated by the driver, distinguishing one logical retryable unit from the next. For retryable writes the server also tracks a statement id inside the transaction number, so a multi-statement retryable sequence is deduplicated statement by statement.

For single writes, the memory is the last applied txnNumber per session — cheap. For transactions, it is the record in config.transactions described earlier, which is why a transaction can be recovered after a stepdown and a plain write cannot be resumed mid-flight.

Retention is bounded by session lifetime (30 minutes idle) and by transaction-record cleanup. Both matter to you: a client that pauses longer than the session timeout and then replays a write is issuing a new write as far as the server is concerned. Any idempotency guarantee beyond that window has to come from your own unique key, not from the driver.

What does causal consistency cost you across regions, and when is that cost unacceptable?

It converts replication lag into client latency. A read carrying afterClusterTime must wait until the serving member has applied through that timestamp. Write in Frankfurt, read in Singapore, and the read blocks for one inter-region round trip plus whatever the primary needs to replicate — not because the data is unavailable, but because causality says "not yet".

It is unacceptable on user-facing paths where the reading region is far from the writing region and the value written is the only thing that matters. The alternative is not "stale reads"; it is scoping the dependency: keep writes and their immediate reads in the same region, use a local cache keyed to the write, or move the read to the primary for the short window after a write.

What you should never do is enable causal consistency globally because it sounds safer. It is a per-session contract, so enable it on the sessions that own a read-after-write dependency, and leave analytics and listings on plain secondary reads with a bounded maxStalenessSeconds.

You write to the primary and immediately read from a secondary. What can go wrong, and what fixes it?

The secondary may not have applied the write yet, so you read the old value. With a 200 ms replication lag and an immediate read, this is not a rare edge — it is the normal case during any write burst.

Four fixes, in increasing cost. Use readPreference: primary for the read-after-write path — correct and boring, and the right default for anything user-facing that immediately confirms an action. Use a causally consistent session so the read waits for the required timestamp — correct but turns lag into latency. Use readConcern: majority without causality — helps only if the write itself was majority-committed and you are willing to read from a member that has reached the commit point. Or restructure so the client already has the value it wrote and does not need to read at all.

The wrong answer is hoping. Catching the user's "I saved it and it's gone" ticket after launch is far more expensive than routing one query to the primary.

readConcern majority: what is it really promising, and what does the majority commit point have to do with it?

majority promises you only see data that has been acknowledged by a majority of voting members, so it cannot be rolled back later. The mechanism is the majority commit point: the highest oplog timestamp that a majority has durably written. A read with this concern waits for the serving member's applied timestamp to reach that point before answering.

Consequences worth stating in an interview. It prevents dirty reads from the durability side — a write that could still be rolled back by an election is invisible. It costs latency equal to however far the commit point trails the primary, which is usually small and occasionally not. It does not give you a consistent snapshot across several reads; each read may see a different commit point unless you use snapshot or a transaction.

Also note majority and w: "majority" are opposite sides of one coin: a read threshold and a write acknowledgement. Mixing w: 1 writes with majority reads is fine, and buys less than you think.

Can you use readConcern snapshot outside a transaction, and what is the catch?

Yes, on find, aggregate and distinct, since 5.0. The point is repeatability across a single operation, and the ability to pin a read to a specific point in time with atClusterTime — which is how you take a coherent multi-collection read without opening a transaction: read once, capture atClusterTime from the cursor, then read the second collection at that same timestamp.

const c1 = db.orders.find({}, { readConcern: { level: "snapshot" } });
// capture the timestamp, then reuse it
db.orderLines.find({}, { readConcern: { level: "snapshot", atClusterTime: ts } })

The catch: it is not a transaction. Each statement sees its own snapshot unless you pass atClusterTime, there is no isolation from concurrent writes appearing between them in a way you can lock against, and you cannot write. And the same MVCC cost applies — a long-lived snapshot for a big aggregation pins history just as a transaction would. Use atClusterTime deliberately, and keep the window short.

Why does $inc scale under high concurrency where read-then-$set collapses?

Because $inc removes the round trip that creates the race. The application never carries a value into the write; the server applies an arithmetic delta to the current version of the document under the document lock. Nothing can be lost, because no stale number ever leaves the server.

Two further effects explain the throughput difference. First, the update is in place in the storage engine — WiredTiger appends a new version of one small document rather than rewriting a large one, so the critical section is short and the write path stays compact. Second, a single-document update is atomic and retryable, so the driver can absorb a stepdown without the application re-reading.

What $inc does not fix is contention: every increment to the same document still serializes on that document. Throughput plateaus at whatever one hot document can absorb, and past that you see WriteConflict under transactions or a lock queue without them. That is a schema problem, not an operator problem — which is why hot counters get sharded.

How do you shard a single logical counter, and still read a correct total?

Split the counter into N documents and add them up when you read. Writes pick a bucket pseudo-randomly, so contention is divided by N and the hot document disappears.

// N bucket docs: { _id: { c: "page:42", b: 0..N-1 }, n: NumberLong(0) }
await buckets.updateOne(
  { _id: { c: "page:42", b: Math.floor(Math.random() * N) } },
  { $inc: { n: 1 } }
);

const [ { total } ] = await buckets.aggregate([
  { $match: { "_id.c": "page:42" } },
  { $group: { _id: null, total: { $sum: "$n" } } }
]);

The trade-offs are real: a read now costs an index range scan plus a group instead of one lookup, the read is only eventually consistent unless you wrap it in a snapshot read, and you pay N times the storage for many counters. Choose N by measuring per-document write throughput, not by taste — and never delete a bucket, or the total silently drops.

Why is $currentDate the right way to stamp a lease, and what breaks if the application supplies the timestamp?

Because the comparison that decides expiry must use one clock. If the app writes expiresAt: new Date(Date.now() + 30000), that value came from the application host, and the next claim compares it against another host's clock. Two machines 400 ms apart is enough for workers to disagree about who holds a lease — and container clocks drift after suspend far more than that.

const job = await jobs.findOneAndUpdate(
  { _id: jobId, status: "pending" },
  { $currentDate: { startedAt: true }, $set: { status: "running", worker: id, leaseUntil: { $add: ["$$NOW", 30000] } } },
  { returnDocument: "after" }
);

$currentDate and $$NOW are evaluated server-side at execution, so every writer and every comparison shares the primary's clock. It also removes a subtle bug: with a client-supplied timestamp, a retried operation rewrites "now" as the old now, and the document records a start time that never happened.

Two workers poll the same jobs collection at the same instant. Show me exactly what stops both from taking the job.

One atomic find-and-modify on a predicate that encodes the precondition. The second worker's filter no longer matches, so it gets null and moves on.

const job = await jobs.findOneAndUpdate(
  { status: "pending", runAt: { $lte: "$$NOW" } },
  { $set: { status: "running", worker: workerId },
    $currentDate: { startedAt: true },
    $inc: { attempts: 1 } },
  { sort: { priority: -1, runAt: 1 }, returnDocument: "after" }
);
if (!job) return; // nothing to do

The critical property is that match-and-modify is a single document-level atomic operation. A find followed by an updateOne has a window in which both workers read the same pending job — that pattern is the bug, not a detail.

Two supporting pieces: the worker must be idempotent, because a crash after claiming means the job runs again on lease expiry; and the claim predicate must include every condition the handler depends on, or you will dispatch work whose dependencies changed.

Design a reservation that can never oversell. Where does the atomicity live?

In one document, one statement. Keep per-SKU availability in a single document and make the decrement conditional on the condition that must hold:

const res = await stock.updateOne(
  { sku: "A-1", available: { $gte: 3 } },
  { $inc: { available: -3, reserved: 3 } },
  { writeConcern: { w: "majority" } }
);
if (res.matchedCount === 0) throw new Error("insufficient stock");

The filter carries the invariant, so the check and the decrement cannot be separated by another writer. No transaction is needed for the reservation itself — and that matters, because a transaction here would just add the same document lock with more overhead.

Where you do need a transaction: reserving several SKUs at once, where partial success would strand inventory. Then all the decrements go in one transaction with w: "majority", and a conflict on any document aborts the whole set cleanly.

Also model release explicitly: reserved plus available sums to a constant you can assert on, so a leaked reservation is detectable instead of invisible.

Use $expr to update only when there is stock. What does it buy you over a filter, and what does it cost?

$expr lets the update predicate compare two fields within the document, which a normal filter cannot do:

await items.updateOne(
  { sku, $expr: { $gte: ["$stock", "$requested"] } },
  { $inc: { stock: -1 } }
);

The obvious filter form, { stock: { $gte: requested } }, requires the app to read requested first — and that read is the race. $expr evaluates server-side against the current version, so the decision is atomic with the write.

The cost is index support. An $expr comparing two fields is generally not indexable, so the predicate is evaluated per candidate document after the index narrows what it can. Always pair it with an indexed equality on the same filter (sku above) so you scan one document, not a collection. If you check explain and see a broad scan, the fix is a different filter, not a different expression. And verify matchedCount, since zero matches here is a business outcome, not an error.

Map optimistic versioning onto HTTP with ETag and If-Match. Where do teams get it wrong?

The resource exposes an ETag derived from the document's version — a strong ETag built from _id and version, not a hash of the representation, which changes for cosmetic reasons. GET returns it; the client sends If-Match: "<etag>" on PUT or PATCH.

const r = await doc.updateOne(
  { _id: id, version: etagVersion },
  { $set: patch, $inc: { version: 1 } }
);
if (r.matchedCount === 0) return res.sendStatus(412);  // Precondition Failed

Common mistakes. Returning 200 on a lost race instead of 412, so the client believes it won. Accepting a missing If-Match and silently doing a blind write — that is the lost update coming back through the front door. Computing the ETag from a timestamp with second granularity, so two edits in the same second share a version. And forgetting that the response must carry the new ETag, otherwise every client retries with a stale one. Return 428 if you want to require the header explicitly.

Deduplicate events by eventId with a unique index, without turning duplicates into 500s.

The unique index is the deduplication — not a findOne first, which reintroduces the race you are trying to close.

// unique index on { eventId: 1 }
try {
  await inbox.insertOne({ eventId, type, payload, receivedAt: new Date(), state: "new" });
} catch (e) {
  if (e.code === 11000) return { duplicate: true };  // already handled or in flight
  throw e;
}
// then apply the effect, then mark state: "applied"

Now the honest part: the insert only reserves the id. If you crash between reserving and applying, a redelivery hits the duplicate path and the effect never happens. So the row needs a state, and redelivery of a "new" row must attempt the effect rather than return success — the transition new → applied must itself be a conditional update so only one worker performs it.

For multi-collection effects, put the inbox insert and the effect in one transaction. Then duplicate detection and application commit together.

Moving money: Decimal128, transactions, and what the transaction does not protect you from.

Store amounts as Decimal128, not double — binary floating point cannot represent 0.10. Integers in minor units are also fine; pick one and enforce it with schema validation, because mixed representations are worse than either.

await session.withTransaction(async () => {
  await accounts.updateOne({ _id: from, balance: { $gte: amt } },
    { $inc: { balance: NumberDecimal(amt).negate() } }, { session });
  await accounts.updateOne({ _id: to },
    { $inc: { balance: NumberDecimal(amt) } }, { session });
  await ledger.insertOne({ from, to, amt: NumberDecimal(amt), at: new Date() }, { session });
}, { writeConcern: { w: "majority" } });

The transaction gives you all-or-nothing across the two accounts and the ledger. It does not give you idempotency: a retried transfer that bypasses the driver's dedup moves the money twice. Add a unique transferId written inside the same transaction. And it does not give you overdraft protection unless the $gte guard is inside the transaction — a check done before the transaction is a check against stale data.

Order plus order lines in separate collections: how do you keep them consistent without paying for a transaction on every read?

Write path: one transaction, so the header and its lines commit together. Read path: never require a transaction. That asymmetry is the whole design.

You can go further and make the invariant structural. If lines always sum to a total stored on the header, the transaction can assert it, and any reader that trusts the header is consistent by construction. Writes that append a line must then update the header in the same transaction — which is fine, because they are rare compared to reads.

Where people hurt themselves: putting the lines in an unbounded array so the header document grows toward 16 MB and every line write rewrites a large document, converting a cheap append into a contended write. Keep lines as their own collection with orderId indexed, and accept that a reader needing both sides does two queries with a bounded window of inconsistency — or one $lookup if the access pattern demands it, never one transaction per page view.

Soft delete inside a transaction: what has to be atomic, and what does it not solve?

Atomic: the tombstone on the document and every side effect that must agree with it — revoking a shared grant, removing the item from a saved list, releasing a reserved SKU. If any of those can happen without the others, you get an object that is deleted for its owner and live for everyone else.

await session.withTransaction(async () => {
  await docs.updateOne({ _id, deletedAt: null },
    { $set: { deletedAt: new Date(), deletedBy: actor } }, { session });
  await shares.deleteMany({ docId: _id }, { session });
  await reservations.updateMany({ docId: _id, state: "held" },
    { $set: { state: "released" } }, { session });
});

Two things it does not solve. Queries: every read path must filter deletedAt: null, and a transaction cannot enforce that — use a partial index and a validator or a repository layer that refuses unfiltered access. Growth: soft-deleted documents still occupy indexes and the working set, so a tombstone without an archival job is a slow-motion capacity problem, not a delete.

Explain precisely how "read, modify, write" in application code loses writes even on a healthy cluster.

Because atomicity in MongoDB is per document per operation. The unit of isolation is one update statement, and your business logic spans three statements separated by network time.

const d = await c.findOne({ _id });          // t0
const next = compute(d);                      // t1  -- CPU, GC, HTTP call
await c.updateOne({ _id }, { $set: { v: next } }); // t2  -- overwrites t0..t2

Anything committed between t0 and t2 is erased by the $set, and no error is raised, because at t2 there was no concurrent writer holding the document — the conflict window closed long before. Replica sets do not help; there is nothing to detect.

The three cures, in order of preference: express the change as a delta the server can apply ($inc, $push, $addToSet, $max); express the precondition in the filter ($expr, version field) and treat zero matches as a conflict; or, when the logic genuinely needs a read, wrap it in a transaction so the snapshot aborts you on conflict.

bulkWrite is not a transaction. How do you order it, and what do you do with a partial failure?

A bulk write is a batching convenience, not an atomic unit: each operation applies independently, and a failure leaves everything before it applied.

ordered: true stops at the first error; ordered: false continues and reports every failure in writeErrors. Choose by what the batch means. Independent upserts from a sync job: unordered maximises throughput, reconcile errors afterwards. A sequence where later operations depend on earlier ones — parent then children — needs ordered, and even then you own the cleanup.

Ordering rules that keep failures recoverable: put the operations that establish identity first, destructive deletes last, and never mix a delete of a document with an insert that reuses its unique key in the same batch, because order then decides whether you get a duplicate key error.

Always inspect result.writeErrors and the difference between insertedCount and what you sent. A bulk write that "succeeded" with three errors is the classic silent data gap. If the batch must be all-or-nothing, it belongs inside a transaction — and then it must be small.

When is eventual consistency the right answer, and how do you make it safe rather than merely convenient?

When the cost of strong consistency exceeds its value to the reader. Feeds, counts, dashboards, search indexes, recommendations, audit trails consumed by humans hours later — all fine. Money movement, inventory, uniqueness, and anything a user is about to act on — not fine.

Making it safe is mostly about honesty in the product and the schema, not the database. Three practices that matter:

  • Bound it. A lag figure you can state and alert on, not "eventually". maxStalenessSeconds turns an unbounded window into a contract.
  • Make the read model self-describing. Return the as-of timestamp or version so a UI can say "as of 3 minutes ago" instead of implying real time.
  • Never let a stale read feed a decision. Every write path re-reads authoritative data inside its own atomic operation; only display paths get the replica.

The failure mode to avoid is accidental eventual consistency: nobody chose it, one query just happened to hit a secondary, and the bug shows up as an intermittent "my change disappeared" report.

How do you build a resumable two-phase state machine so a crashed process can pick up where it stopped?

Persist the intent before the effect, and make every transition a conditional update on the state you expect. The document is the state machine; the process is disposable.

// 1. claim the transition atomically
const claimed = await ops.findOneAndUpdate(
  { _id: opId, state: "pending" },
  { $set: { state: "applying", worker: id }, $currentDate: { claimedAt: true } },
  { returnDocument: "after" }
);
if (!claimed) return;               // taken, or already done

// 2. do the external effect with an idempotency key = opId
await gateway.charge(opId, claimed.amount);

// 3. record completion
await ops.updateOne({ _id: opId, state: "applying" }, { $set: { state: "applied" } });

The invariant is that the external call is idempotent under opId, so a crash between 2 and 3 is recoverable: a recovery sweep finds applying rows with a stale claimedAt, re-issues the call, and the gateway deduplicates. Without that key, step 2 becomes the money-losing step.

Note what is absent: no long transaction held across the network call. That is the point of the pattern.

Which currentOp fields tell you a transaction is stuck rather than just long-running?

Do not read secs_running alone; a healthy batch transaction can legitimately be 20 seconds old. Read the shape:

  • transaction.parameters.txnNumber and lsid — the identity you will need to kill it.
  • transaction.timeOpenMicros — age of the transaction, distinct from the age of the current statement.
  • transaction.timeInactiveMicros — the discriminator. High and growing means the session is idle with an open transaction: nobody is doing work, the locks and snapshot are just held.
  • locks and waitingForLock — whether it is a victim or a blocker.
  • numYields, planSummary — whether the current statement is scanning.

A transaction with timeInactiveMicros climbing past tens of seconds is almost always an application bug: a session leaked, or an exception path with no abortTransaction. Correlate with clientMetadata and appName to find the offender, and check prepareReadConflicts before concluding it is harmless.

Write the aggregation that finds every open transaction, including idle ones, and explain the flags.

db.getSiblingDB("admin").aggregate([
  { $currentOp: { allUsers: true, idleSessions: true } },
  { $match: { transaction: { $exists: true } } },
  { $project: {
      opid: 1, appName: 1, client: 1, lsid: 1,
      secs: { $divide: ["$transaction.timeOpenMicros", 1000000] },
      idle: { $divide: ["$transaction.timeInactiveMicros", 1000000] },
      state: "$transaction.parameters.state", txnNumber: "$transaction.parameters.txnNumber"
  } },
  { $match: { secs: { $gt: 30 } } },
  { $sort: { secs: -1 } }
])

idleSessions: true is the essential flag — without it, sessions that are idle but holding an open transaction are omitted, which is exactly the population you are hunting. allUsers: true is required to see other users' operations, which means the admin privilege to run it.

transaction.parameters.state distinguishes inactive from prepared; a lingering prepared state usually points at a coordinator that died between phases. Sort by age, then look at appName — the same offender repeating is a code defect, not a one-off.

How do you kill a stuck transaction, and what will the client see when you do?

Two levers, and they are not interchangeable. db.killOp(opid) kills the current operation; for a transaction you also want the session gone, so prefer killing the session:

db.adminCommand({ killSessions: [ { id: UUID("..."), txnNumber: NumberLong(7) } ] })
db.adminCommand({ killAllSessionsByPattern: [ { "lsid.id": UUID("...") } ] })

Killing the session aborts any open transaction and releases its locks and snapshot — which is what you actually needed. Killing just the opid can leave the transaction open, and the next statement re-establishes it.

Client-side: the in-flight statement fails, and subsequent work on that session gets NoSuchTransaction with TransientTransactionError, so a well-behaved driver retries from the top. That is fine. What is not fine is killing sessions as routine operations — you have just converted your problem into the client's retry storm. Kill, then fix the leak. Log the lsid before killing so you can prove which code path it was.

Which serverStatus counters do you watch for conflict pressure, and how do you read them together?

Three families, and they only mean something in combination.

  • serverStatus().transactions — totalStarted, totalCommitted, totalAborted, plus the gauges currentOpen, currentActive, currentInactive, currentPrepared.
  • WiredTiger transaction statistics, including the write-conflict counter, which is the direct measure of two writers colliding on the same document.
  • Lock and queueing signals — globalLock.currentQueue, and the ticket gauges from wiredTiger.concurrentTransactions.

Read them as a ratio, not absolutes. totalAborted / totalStarted climbing is the number that predicts an outage: it means work is being done and thrown away. Rising currentInactive alongside a flat commit rate points at leaked sessions rather than contention. And a high conflict counter with low abort count usually means lock waits are being absorbed by the server's internal retry — latency is rising before errors appear. Use a derivative over a window; a single sample tells you nothing.

How do you detect transactions that are growing, before they hit the cache ceiling?

You cannot see the byte size of an individual in-flight transaction as a first-class metric, so you infer it. The leading indicators are the per-transaction gauges plus cache behaviour: currentOpen and currentActive rising while totalCommitted stays flat means transactions are accumulating, not flowing. On the WiredTiger side, watch cache fill and the bytes-dirty track — a growing transaction pins versions and dirties pages, so the store climbs without a matching increase in application write volume.

The hard ceiling is transactionSizeLimitBytes, derived from the cache size, and the error when you exceed it is TransactionTooLargeForCache. Two readings of that error matter. If it fires on a transaction whose size is intrinsic — a bulk migration — it is a design signal: chunk the work. If it fires only under load, contention has inflated the working set and the fix is retry with backoff plus a smaller write set.

The cheap preventative: log the document count and payload size each transaction touches, and alert when p99 crosses your own budget.

Read serverStatus().transactions for me like an operator. Which number would worry you first?

The gauges describe a population of live transactions; the counters describe throughput. currentInactive is the one I look at first, because it is the pathological state: a session that opened a transaction and walked away. It holds locks and a snapshot while doing nothing, so it costs you cache and blocks writers without contributing throughput.

Then the ratio: totalAborted against totalStarted. Some aborts are normal — optimistic patterns abort and retry by design. A ratio that climbs from 2% to 30% over an hour is contention that your retry loop is hiding from the error rate but not from the latency graph.

Finally currentPrepared sitting above zero for more than a moment. Prepared transactions are a transient state between the two phases; a stable non-zero value means coordinators died mid-flight or a shard is unreachable, and those transactions are holding locks indefinitely. That is a page-someone condition, not a dashboard curiosity.

What does the slow-query log show for a transactional operation that a normal slow query does not?

The log line for a transaction carries the session identity and the transaction context: lsid, txnNumber, and statement-level fields, plus the usual planSummary, keysExamined, docsExamined, numYields and durationMillis. That identity is the difference between guessing and knowing, because you can join the log line to the application log line that emitted the same request id.

slowms still governs what gets written, so the trap is thresholding by statement duration: each statement in the transaction can be 5 ms while the transaction takes 400 ms, and nothing is logged. For transactions, log by transaction duration in the application, not by statement duration in the server.

Also watch slowms being lowered during an incident: on a busy primary it is self-defeating, because the log volume itself becomes the bottleneck. Sample instead — log a fraction of the slow path, or use the profiler at level 2 into a dedicated collection for a bounded window.

What do transaction entries look like in system.profile, and what can the profiler not tell you?

Each profiled entry has the usual op, ns, command, planSummary, keysExamined, docsExamined, nreturned, millis — plus lsid and txnNumber for anything inside a transaction, which is how you filter:

db.system.profile.find({ lsid: { $exists: true }, millis: { $gt: 50 } })
  .sort({ ts: -1 }).limit(20)

You can then group by lsid and sum millis to reconstruct a transaction's real cost, which is the analysis the per-statement view hides.

What it cannot tell you: whether the transaction committed or aborted. There is no single entry representing the transaction as a unit, and aborted work is profiled like any other. That has two consequences — wasted work looks identical to useful work, so you cannot measure your conflict rate from the profiler, and the audit trail cannot prove an outcome. For those, use serverStatus().transactions and application-side instrumentation. Also remember the profiler writes into a capped collection, so a hot window evicts its own evidence.

Can you run explain inside a transaction? If not, how do you get a trustworthy plan for it?

Not in the general case. explain() is not part of the command set you can interleave into an open multi-document transaction; the driver will run it as its own operation, so what you get is a plan for the query shape, not for the transaction.

So you get the plan three ways and cross-check. Run explain("executionStats") outside the transaction with the identical filter, projection and sort, and read totalKeysExamined against nReturned. Reproduce the transaction on a staging copy with the same documents and the same readConcern, where you can also inspect the plan cache entry that will be selected. Then confirm on the real system from the profiler: planSummary on the actual transactional entries is the ground truth for what the server really ran.

The senior habit is the second step, because a plan that is fine on an empty collection is often a COLLSCAN ten million documents later, and the staging reproduction is the only place you will see that before production does.

Why can the plan chosen for the same query differ between a normal execution and one inside a transaction?

Four reasons, and only the first is obvious.

  1. Different cache state. The plan cache is keyed on query shape, and shapes are shared across sessions. A plan cached by a non-transactional read can be selected for the transactional one, or rejected because a competing plan won more trials.
  2. Different read concern. A snapshot read executes against a fixed point in time; the planner's selectivity estimate comes from a snapshot that may not match the current distribution, and a plan that was optimal five minutes ago is not necessarily optimal now.
  3. Different data volume. Inside a transaction you usually touch fewer documents with more selective filters, so plan choice rarely matters — but when it does, one bad COLLSCAN holds locks for the whole transaction.
  4. Sharding. Each shard plans independently, and the mongos-level plan is a merge of those, so a sharded transactional query can degrade on one shard while the other three are fine.

Practical rule: pin the access path with a supporting index, not with a hint, and verify with $indexStats.

Rapid fire: which documented limits actually break transactions in production, and which are folklore?

Real. One minute default lifetime (transactionLifetimeLimitSeconds), enforced by a cleanup process, with NoSuchTransaction as the client-visible symptom. Five milliseconds default lock-request wait (maxTransactionLockRequestTimeoutMillis). 16 MB per document and per oplog entry — not per transaction; the server splits a transaction across as many entries as needed. The WiredTiger cache ceiling behind TransactionTooLargeForCache. No cross-shard DDL. No capped collections. A shard with an arbiter cannot take part in multi-shard transactions.

Folklore. "16 MB total per transaction" — obsolete since 4.2. "1000 documents per statement" — that number circulates from a 4.0-era guidance note about keeping transactions small; it is a design heuristic, not an enforced limit, and conflating the two leads people to build batching logic for a constraint that does not exist while ignoring the cache ceiling that does. Verify against the production-considerations page for your exact version before you quote any number in a design review.

Three error codes keep appearing in your transaction telemetry. Diagnose each.

NoSuchTransaction (251). The transaction is gone: aborted by the lifetime cleanup, killed, aborted on a previous statement, or a shard stepped down. Carries TransientTransactionError, so the standard loop restarts from the beginning — which is only correct if your body is idempotent and cheap. Recurring 251s mean either a too-long transaction or an exception path that aborts and then keeps issuing statements.

TransactionTooLargeForCache. The write set cannot fit the storage cache budget, or contention inflated it. Chunk the work; retrying the same transaction unchanged is a loop with a 100% failure rate.

LockTimeout (24) / lock request timeout. The transaction waited longer than maxTransactionLockRequestTimeoutMillis for a lock — usually DDL pending behind another transaction, or a hot document. Raising the parameter is legitimate only when the blocker is transient metadata; if the blocker is an application write, raising it converts an error into latency and then into a queue.

In all three, the useful telemetry is the retry count per logical request, not the error count.

Reproduce a write conflict on your laptop in under two minutes. Then explain what the reproduction proves.

Two sessions, interleaved by hand:

// session A
const sA = db.getMongo().startSession();
sA.startTransaction();
sA.getDatabase("t").c.updateOne({ _id: 1 }, { $set: { x: 1 } });

// session B -- outside a transaction
db.c.updateOne({ _id: 1 }, { $set: { y: 2 } });   // waits for A's lock

// back in A
sA.getDatabase("t").c.updateOne({ _id: 1 }, { $set: { x: 2 } });  // WriteConflict
sA.abortTransaction();

What it proves, and why it is worth doing once by hand: the conflict is not about timing but about snapshot versus write. B's write committed after A's snapshot, so A can no longer modify that document. It also shows the asymmetry in the docs — B, outside a transaction, blocks waiting for the lock, while A, inside one, fails fast rather than waiting.

Run it with retryWrites off and a transaction, then again as two plain updates, and you will see why the same contended workload behaves completely differently depending on whether you wrapped it in a transaction.

You are about to put transactions on a hot endpoint. Give me the checklist you would not skip.

Necessity. Can the invariant live in one document instead? A transaction is the expensive answer; a conditional single-document update is usually the correct one.

Footprint. How many documents, how many shards, how many bytes at p99? Budget it explicitly, because the cache ceiling and the 60-second lifetime are the two things that will bite.

Duration. Any network call inside the body is a defect. So is any unbounded query. Measure the p99 body time under load, not in staging.

Contention. Do all requests touch the same few documents? If yes, the design converts throughput into aborts. Shard the hot document or change the model before shipping.

Failure semantics. Idempotency key written inside the transaction, retry loop with jitter and a bounded budget, UnknownTransactionCommitResult handled, abortTransaction in finally, w: "majority".

Observability. Retry counts, abort ratio, timeInactiveMicros alert, and a load test that pushes past the conflict knee. Then re-check whether the endpoint needed a transaction at all.

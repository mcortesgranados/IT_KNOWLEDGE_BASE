How does WiredTiger lay out a collection in B-tree pages, and what distinguishes an internal page from a leaf page?

A collection is not a heap of documents; it is a B-tree whose pages are the unit of I/O, caching, and compression. Internal pages hold only keys plus child page addresses — they are the routing layer, never user data. Leaf pages hold the encoded records (for MongoDB, the BSON payload keyed by record id) and are where all reads land.

In practice the tree is shallow: leaf pages are sized in the tens of kilobytes (roughly 32 KB uncompressed by default) and internal pages are only a few kilobytes, with a 4 KB allocation unit underneath. That means a collection with hundreds of millions of documents still has a root-to-leaf depth of about three, so a point lookup costs three page accesses at most, and the top one or two levels are almost always resident in cache.

The consequence for interviews is this: the cost of a query is not "documents scanned" at the storage layer, it is pages touched. When you explain a plan, every FETCH is potentially a leaf-page read.

What is an update chain in WiredTiger, and how do tombstones and record ids affect what you see in the cache?

WiredTiger is MVCC in memory. A leaf page in cache holds a set of keys (record ids) each pointing to an update chain: a list of versions, newest first, with the transactions that created them. A read walks that chain and returns the first version visible to its snapshot.

This has three practical consequences. First, an updateOne does not rewrite the page; it prepends a version, so a document updated thousands of times in a tight loop accumulates a long chain and slows every reader of that document. Second, a delete is not a page edit but a tombstone appended to the chain, which is why deleteMany burns CPU and journal rather than freeing anything. Third, cache accounting reflects this: serverStatus().wiredTiger.cache["bytes currently in the cache"] grows with versions and tombstones, not just with live documents.

Long chains are reclaimed only when no snapshot needs them, so a stuck open transaction or a lagging cursor can pin history and inflate cache pressure.

What exactly does per-collection block compression change, and how do snappy, zstd, and prefix compression differ?

WiredTiger compresses whole pages, not documents, so compression is a property you set per collection at creation time:

db.createCollection("events", {
  storageEngine: { wiredTiger: { configString: "block_compressor=zstd" } }
})

snappy is the default: fast, symmetric, moderate ratio — it mainly removes BSON key repetition and padding. zstd trades CPU for a much better ratio and, usefully, supports a dictionary so small documents compress well. zlib exists but is rarely the right answer.

Prefix compression is a separate mechanism that applies to index keys, not collection data, and it is on by default. Because index keys in a B-tree are sorted, consecutive keys share long prefixes (a tenant id, a status, a date); prefix compression strips the shared part, which is why an index on a long string field is smaller than you would estimate from the key length alone.

Compression changes disk footprint and I/O, not the size of the working set in cache: pages are decompressed before use.

When is zstd actually worth the CPU instead of snappy?

Choose zstd when the read path is dominated by I/O rather than CPU, and when the data compresses well but is read rarely relative to its size — archives, log-like documents, wide documents with repeated field names and enum values, historical partitions. The win is fewer bytes per page fault and a smaller working set on disk, which matters when your IOPS budget is the binding constraint.

Stay with snappy when the collection is hot, when writes dominate (every page write pays compression), or when the primary is already CPU-saturated by application query work. zstd also raises checkpoint cost, since checkpoints write compressed pages, so a write-heavy collection can see eviction and checkpoint latency increase.

Measure rather than guess: compare db.collection.stats().size and storageSize per compressor on a representative sample, then watch wiredTiger.cache["pages read into cache"] and CPU after the switch. A 2:1 ratio on cold data is worth it; a 1.3:1 ratio on a hot collection usually is not.

How is the WiredTiger cache sized by default, and what percentage of RAM does mongod really give it?

The default is 50% of (total RAM minus 1 GB), with a 256 MB floor. On a 64 GB host that is roughly 31.5 GB of cache; the subtracted gigabyte is reserved for the rest of the process — connections, sorting buffers, aggregation, the TTL monitor, and the OS page cache that still serves the journal and the compressed files.

Override it explicitly with storage.wiredTiger.engineConfig.cacheSizeGB when mongod shares a host (containers, co-located monitoring, Atlas-side overhead) or when you run several instances per machine. Do not raise it toward 90% and expect a proportional gain: beyond the working set, cache is idle, and a larger cache means longer eviction and checkpoint work per cycle.

Two caveats worth stating in an interview. The cache is not the only memory consumer, so RSS exceeding cacheSizeGB is normal. And on Linux the filesystem cache still holds compressed pages, which is why db.serverStatus().mem.resident can be well above the configured cache.

What is the real working set, and why does giving mongod a huge cache not guarantee a small one?

The working set is the set of pages — collection leaves, index leaves, and internal pages — that must be resident for the latency target to hold. It is not the dataset size, and it is not the cache size either. Cache is capacity; the working set is demand.

A generous cache only helps if the demand actually fits and stays stable. Three things break that assumption. Skewed access patterns make a small hot subset but a long cold tail, so every scan of the tail evicts hot pages. Index-heavy schemas inflate the resident footprint, since each index has its own B-tree and its own internal pages. And unbounded queries read cold pages faster than eviction can cope, producing the classic signature: high cache fill, dirty percentage climbing, and read latency rising even though RAM is "plenty".

So the sizing question is not "how much data do I have" but "how many distinct pages do my top query shapes touch per hour". That number, plus index footprint, is what you compare against cache.

What do WiredTiger's eviction threads actually do, and why does the dirty percentage climb?

Writes land in memory first. Eviction is the background machinery that reconciles dirty pages to disk and then frees them, and it runs at two levels of urgency: a target (pages are evicted opportunistically to keep the cache below ~80% full) and a trigger (~95%, where application threads are forced to do eviction work themselves).

Dirty bytes have their own thresholds: roughly 5% as a target and 20% as a trigger. When wiredTiger.cache["tracked dirty bytes in the cache"] stays above 20%, you have a reconciliation backlog — the writers are producing dirty pages faster than the eviction workers can flush them. The usual causes are a write burst, slow fsync on the storage, a checkpoint in progress, or too few eviction threads for the core count.

The symptom users report is not "eviction is slow", it is a latency spike: once application threads join eviction, a simple insert starts waiting on I/O. Watch pages evicted by application threads — if it is non-zero and growing, the cache is the bottleneck, not the query.

How does a checkpoint relate to the journal, and what is the "last checkpoint" record?

A checkpoint is a consistent snapshot of the data files. WiredTiger performs one roughly every 60 seconds, or earlier if the journal has grown to about 2 GB, and at the end of it writes a checkpoint record into the journal naming the point in the journal up to which the data files are consistent.

That record is the hinge between the two durability mechanisms. Recovery reads the data files as of the last checkpoint, then replays journal records from that checkpoint forward — not from the beginning of the journal. Without a valid checkpoint record the journal cannot be applied, which is why a corrupted checkpoint is a much worse incident than a corrupted tail of the journal.

Operationally: checkpoints are what make the data files eventually correct, the journal is what covers the gap since the last one. Both matter — a long checkpoint due to large dirty pages widens the window of work that a restart must replay, which is why crash recovery time tracks journal size and checkpoint frequency, not total data size.

Journal versus oplog: why are they not the same thing, and what does each one replay?

They solve different problems and live in different places.

  • The journal is a per-node, per-storage-engine write-ahead log in journal/. It records page-level physical changes and exists so that a single mongod can recover its own data files after a crash. It is internal, idempotent, and never replicated.
  • The oplog is a capped collection in the local database. It records logical, idempotent operations (applyOps-style) and exists so that other members can replay them. Change streams read it; replica set consistency depends on it.

Practical consequences follow directly. Losing the journal loses local durability; losing the oplog tail forces a resync. You size the journal by write volume and checkpoint frequency, and the oplog by write volume and the recovery window you promise. And j:true says nothing about replication — it only guarantees the local journal entry is on disk, not that any secondary has seen it. Confusing the two is one of the most common senior-level mistakes.

With j:false, what exactly can be lost and what can never be lost?

The journal is flushed to disk on an interval — on the order of 100 ms — rather than synchronously per write. With j:false, the write is acknowledged once it is in the WiredTiger cache and the in-memory journal buffer, so a crash can lose the last window of writes: everything after the last flush, up to roughly that interval's worth of operations.

What can never be lost: anything already checkpointed, and anything acknowledged with j:true. What j:false does not mean is corruption — recovery is still consistent, you just roll back to a slightly older point, and the data files remain structurally valid.

Note the interaction with replication: w:"majority", j:false still guarantees the write is on a majority of nodes' memory, so a single-node crash survives it; a full-cluster power loss does not. That is why j:false is defensible for high-volume, re-derivable telemetry and indefensible for money. Also remember that on a replica set the rollback after such a crash is applied by the replication protocol, so application-visible effects can be subtler than "one document vanished".

How do you size the oplog using GB/hour and a recovery window instead of the default percentage?

The default (about 5% of free disk, with a floor around 1 GB) is a guess about your workload and is almost never the right number for a real one. Size it from measured write volume and a stated window:

// current oplog window, in hours
db.getSiblingDB("local").oplog.rs.stats().maxSize
// and the actual time span it covers
db.getSiblingDB("local").oplog.rs.find().sort({$natural:-1}).limit(1)
// compare first.ts and last.ts

Then: required size = peak GB/hour × target hours × safety factor. Target hours must cover the worst realistic outage of a secondary — a maintenance window, a node rebuild, a cross-region link failure — so 24 to 72 hours is typical, more if you promise change-stream resume across a weekend.

Two refinements: size for the primary's peak, because every secondary must absorb that stream; and remember that bulk operations, index builds, and large backfills generate oplog entries at rates far above steady state, so measure during those events, not on a quiet Tuesday.

What happens when the oplog wraps before a secondary has read it, and how do you recover?

The oplog is capped and circular: when it fills, the oldest entries are overwritten regardless of whether every member has consumed them. A secondary that falls behind the oldest remaining entry gets OplogTruncatedException and can no longer apply changes incrementally — its position simply no longer exists.

Recovery is a full resync: the member discards its data files and re-copies the dataset, which means hours of network transfer plus index rebuilds, and sustained read load on the sync source. If the whole cluster's oplog is too small, the primary itself eventually cannot satisfy w:"majority" waits for a lagging member — the write concern blocks, latency climbs, and the incident looks like "writes hang" rather than "oplog too small".

Detection: monitor rs.printReplicationInfo() for the configured window and the actual first-to-last span, and alert when the window shrinks below your defined recovery budget. The fix is replSetResizeOplog, applied to every member, not just the primary.

What are read and write tickets, and how does ticket exhaustion manifest in metrics?

WiredTiger limits how many operations may be inside the engine at once: by default 128 read tickets and 128 write tickets, adjustable via wiredTigerConcurrentReadTransactions and wiredTigerConcurrentWriteTransactions. A ticket is taken on entry to the storage engine and returned on exit, so the limit caps concurrency inside WiredTiger — not connections, not application threads.

Exhaustion does not produce an error; it produces queueing. Operations wait in the storage layer for a ticket, so latency rises on operations that look cheap in explain, while CPU may be moderate. The tell is here:

db.serverStatus().wiredTiger.concurrentTransactions
// { write: { out: 128, available: 0, totalTickets: 128 },
//   read:  { out: 128, available: 0, totalTickets: 128 } }

available: 0 held for seconds is the signature. Usual cause is not too few tickets but slow ticket holders: fsync-bound writes, eviction stalls, or a long-running operation pinning a read ticket. Raising the limit is legitimate once the storage is healthy, but it hides the real problem if it is not.

Which disk-level bottlenecks actually limit MongoDB, and how do IOPS and fsync latency show up in diagnostics?

Three distinct constraints get conflated: throughput (MB/s), IOPS, and fsync latency. MongoDB is usually hurt by the last two. Each committed write waits for the journal flush; each checkpoint writes dirty pages; each eviction writes a page before it can be reused. If a single fsync takes 10 ms, then a serialized journal flush caps your write rate no matter how many IOPS the device advertises.

Symptoms move in a fixed order when the disk is the constraint: dirty bytes in cache climb past the 20% trigger, eviction starts running on application threads, tickets stay at available: 0, and then latency rises across unrelated query shapes. Query tuning at that point is wasted effort.

Evidence to collect: the storage latency histogram in FTDC, db.serverStatus().wiredTiger.cache["pages evicted by application threads"], and OS-level await/queue depth. On cloud volumes the classic trap is burst credits: throughput looks fine in testing and collapses under sustained checkpoint load, so test with throttled baseline performance, not burst.

Why is dropping a collection cheap while deleteMany({}) on the same data is expensive?

drop() is a metadata operation. WiredTiger unlinks the collection's files and its index files, and the space returns to the filesystem immediately. There is no per-document work, no journal entries per document, and no oplog storm. Cost is proportional to the number of files, not the number of documents, which is why dropping a 500 GB collection takes about a second.

deleteMany({}) is the opposite: every document becomes a tombstone in its update chain, gets journaled, is replicated through the oplog, invalidates index entries one by one, and must be reconciled and evicted before the space can be reused. On a large collection this means hours of write amplification, a pinned dirty cache, replica lag, and the risk of the oplog wrapping before secondaries catch up.

So the correct pattern for "clear this data" is almost always drop() or a time-partitioned collection swap — not a mass delete. If you must delete a majority of documents, deleting in bounded batches reduces the blast radius but never makes it cheap.

Why does free disk space not come back after deleting documents, and how does WiredTiger reuse the space?

Deleted space becomes reusable inside the data file, not outside it. WiredTiger keeps the freed extents on a free list; new inserts and updates of similar size will reuse them before the file grows again. That is why dbStats().dataSize falls while storageSize and the file on disk stay flat — the gap is the free list.

Reuse is not perfect, because pages are fragmented and reused only when the size fits. A collection that shrinks to 10% of its peak may still hold a mostly-empty file, and a capped or heavily fragmented collection degrades further.

This is expected behavior, not a leak, and it is the argument for partition-by-time designs: rotate to a new collection instead of deleting from an old one, then drop the old one and get the bytes back instantly. If you genuinely need the file to shrink in place, compact is the only lever, and it is expensive — which is exactly the trade-off the next question covers.

What does compact actually rewrite, and when is running it justified?

compact rewrites the collection's data files and index files, keeping only live records and discarding free space and fragmentation. It is a full physical copy: it reads every live document, writes it into new extents, and rebuilds the files. It requires a primary, it can be interrupted and restarted, and it is I/O heavy enough to look like a backup job from the storage's point of view.

Blocking behavior matters: modern versions block operations on that collection for the duration rather than the whole database, but the collection is still effectively offline for writes from the application's perspective — plan it as a maintenance action with a window, not an ad-hoc fix.

Justify it when a collection shrank dramatically and you need bytes back, when a large delete left the file badly fragmented, or when an internal check finds excessive free space. Do not justify it as routine hygiene: for time-series or append-heavy data, partitioning and dropping is cheaper, faster, and has none of the availability cost.

How are columnstore indexes built and maintained, and where does the memory go during the build?

A columnstore index stores values column-by-column rather than document-by-document. That layout is useless for point lookups — you cannot seek to one document — but it is excellent for scanning a few fields across many documents, which is precisely the aggregation shape that normally forces a COLLSCAN.

Build behavior: the index is created by scanning the collection and accumulating per-field value runs, which needs working memory proportional to the number of distinct values and the batch being sorted, and spills beyond the index-build memory budget (maxIndexBuildMemoryUsageMegabytes, 500 MB by default). Builds are therefore heavier than a normal B-tree build and should be scheduled like one.

Maintenance: unlike a B-tree, a columnstore is not updated in place per write. There is no cheap way to insert a single value into a compressed column, so it is designed around batched/segment maintenance, and it remains a specialized tool: use it when the dominant workload is a small number of analytical aggregations, not as a general replacement for compound indexes.

How is an index stored as a separate B-tree, and what exactly is inside one index entry?

Each index is its own WiredTiger B-tree in its own file (or its own set of extents inside the collection's file group). It is not a structure embedded in the collection's tree, and it is not derived at read time. The collection B-tree maps record id → BSON; the index B-tree maps key → record id.

An entry contains the indexed values in the index's sort order, the record id as the payload, and, for multikey indexes, a per-key discriminator so that the same record can appear multiple times. Because the record id is the payload, an index lookup returns a pointer and nothing else — the document still has to be fetched from the collection tree, unless the query is covered and the projection can be satisfied from the index alone.

Two consequences worth stating: index entries are subject to the same page/compression machinery as data, including prefix compression on sorted keys; and an index update is a second B-tree modification, which is why every extra index multiplies write cost rather than adding to it linearly-ish.

Why can a multikey index become enormous, and what is the "key explosion" you should watch for?

A multikey index stores one entry per array element, not one per document. A document with 50 tags produces 50 entries, each a full key plus a record id, all in the same B-tree. Multiply by array length and you get index size that has nothing to do with document count.

The pathological cases are arrays that are long and low-selectivity (thousands of strings, or an array of subdocuments where the index is on a nested field), and documents where several indexed arrays coexist — a compound multikey index on two array fields cannot be bounded efficiently, and the planner will often refuse to use it well because the bounds on the second field cannot be derived independently.

Diagnostics: db.coll.stats().indexSizes next to avgObjSize, plus $indexStats for access counts. If one index is larger than the collection, you are paying for an index that is probably being scanned rather than seeked. The fix is usually a computed summary field (a bounded set of derived keys) instead of indexing the raw array.

What are the hard limits on a compound index, and what happens at the boundary?

A compound index may contain at most 32 fields in its key pattern. There is also a limit on the total size of an index key (see the next question) and, separately, on the size of the index key pattern document itself. These are engine limits, not planner heuristics, and creation fails with an error rather than silently truncating.

In practice 32 is never the constraint you hit first; key size and write cost are. Every additional field widens every entry, multiplies the B-tree's fan-out requirement, and makes prefix compression less effective when the added fields are high-entropy. A 12-field index is a design smell: it usually means the query patterns were never consolidated.

The boundary issue to raise in an interview is the prefix rule under the limit. A 32-field index can serve queries on any prefix of its fields, so one wide index can cover several shapes — but only leading prefixes, and only if the sort directions and collation line up. Beyond that, a wide index is dead weight on every write to the collection.

What is the maximum index key size, and which error do you get when a value exceeds it?

An index entry must fit within about 1 KB of key data (1024 bytes, including the per-type overhead WiredTiger adds). Exceed it and the write fails — you get a "key too large" error from the storage engine rather than a silent truncation, and the document insert or update is rejected. That is important: the failure is on the write, so a document that is perfectly valid on its own can be rejected because you indexed a huge string or a big array.

Typical triggers: indexing a field that holds base64 blobs, a description field with unbounded length, or an array of long identifiers. Note that multikey indexes are counted per element, so a single monstrous element is enough to break inserts even though the array is short.

Mitigations: index a deterministic hash of the value (and query by the hash), index a prefix field you maintain yourself, move the payload out of the indexed document, or drop the index and accept the scan. Checking before deploy matters because the failure appears only when a specific document arrives.

How do partial indexes reduce index size, and what does the filter cost at query time?

A partial index indexes only documents matching a filter expression:

db.orders.createIndex(
  { customerId: 1, createdAt: -1 },
  { partialFilterExpression: { status: "OPEN" } }
)

Every document excluded by the filter simply has no entry, so size scales with the matching subset — often a tiny fraction of the collection. Lower size means better cache residency, faster builds, and less write amplification, since updates to excluded documents no longer touch this B-tree (though the filter field itself must still be evaluated).

The cost is a correctness constraint the planner enforces strictly: the index is usable only if the query is provably a subset of the filter. A query with no status predicate cannot use it, even though the results would be identical. That means the filter must be part of your standard query shape, and any ad-hoc query without it silently falls back to a collection scan. Design the filter around an invariant the application always enforces, not around a convenience.

What is the hide → observe → drop lifecycle for a hidden index, and why is it safer than dropping directly?

db.coll.hideIndex("idx_name") makes the planner ignore the index while the index continues to be maintained on every write. Reads behave as if it were gone; you cannot hide _id, and you cannot hide an index that is still needed to enforce a unique constraint in some setups.

The lifecycle is: hide it, then watch the workload for a full business cycle — including month-end jobs and rarely-hit admin screens — comparing latency and plan shapes on the queries that used it. If nothing degrades, dropIndex and reclaim the space. If something degrades, unhideIndex restores it instantly, with no rebuild cost.

That last point is the whole argument. Dropping and re-creating an index on a large collection means a full build: a collection scan, memory pressure, replication impact, and minutes to hours of vulnerability. Hiding gives you a reversible experiment at zero cost. The observable signal is $indexStats: a hidden index still reports accesses, but the accesses.ops counter stops incrementing in practice because the planner never selects it.

What does an index build actually do to writes while it runs?

A modern build is a hybrid: brief exclusive locks at the start and end, with a long middle phase where reads and writes are allowed. During that middle phase, writers must keep the half-built index consistent, so each write to the collection records the change in a pending side-table and the build thread later applies it.

Consequences you should be able to state. Writes pay an extra cost for the duration of the build, proportional to write rate. The build holds memory up to the budget (maxIndexBuildMemoryUsageMegabytes, 500 MB default) and spills to temp files beyond it, so watch disk. On a replica set, secondaries start their own build when they see the commit, so index builds ripple through the cluster and can widen replication lag. And the final phase briefly blocks writes to take the lock and mark the index ready, which is the small latency spike users notice.

Practical rule: build during low write volume, one index at a time, and prefer a short-lived secondary-first rollout for very large collections.

Is background: true still real, and what replaced the foreground/background distinction?

No — the flag is accepted for compatibility but no longer selects a different algorithm. The old distinction was: foreground builds took an exclusive lock for the whole build (fast, but writes blocked), background builds sampled the collection and re-scanned for changes (slow, writes allowed). Both behaviors are gone.

Since the hybrid build was introduced, all builds behave in the "background-ish" way: they yield to writes for the bulk of the work and only take an exclusive lock at the beginning and end. Removing the option removed a real footgun, because "background" used to mean a build that could take many times longer and never quite converge on a hot collection.

So the correct answer to "should I build in the foreground or background" is that the choice no longer exists; the meaningful levers are now the timing relative to write volume, the memory budget, and whether to build on secondaries before the primary with a rolling approach. Passing {background: true} is harmless but signals you learned the older documentation.

What happens when you build a unique index on a collection that already contains duplicates?

The build fails as a whole; it does not create a partially unique index. The build scans the collection in key order, and if two documents share the same key with a different record id, it aborts with a duplicate key error (code 11000) naming the offending key value. The index is not left in a usable state — on failure the partially built index is removed, so you are back to where you started, minus the time and I/O spent.

This matters operationally because the failure happens at the end of a long build on a large collection. The correct sequence is to find the duplicates first, cheaply:

db.orders.aggregate([
  { $group: { _id: "$externalId", n: { $sum: 1 } } },
  { $match: { n: { $gt: 1 } } },
  { $limit: 20 }
], { allowDiskUse: true })

Also note the interaction with multikey fields: a unique index on an array field enforces uniqueness per element across documents, so duplicate array values in different documents collide, while a repeated value inside one document's array does not create a second entry.

How does the TTL monitor thread actually delete documents, and how often does it run?

The TTL monitor is a background thread on the primary that wakes roughly every 60 seconds. Each pass, it queries each TTL index for documents whose indexed date is older than expireAfterSeconds and issues deletes in batches until the pass budget is used, with delete operations that appear in the oplog like any other write.

Consequences that follow directly from "it is a batched delete on a 60-second timer":

  • Expiry is not exact. A document can live up to roughly one monitor cycle plus however long the backlog takes, so never treat TTL as a scheduling mechanism with second-level accuracy.
  • Deletes are real deletes — journaled, replicated, and index-maintaining. A large expiry burst is a write burst, and it can show up as replication lag and dirty cache pressure.
  • The delete rate is throughput-limited, so a collection receiving 50k expiring documents a minute may never catch up.

If the exact time matters (billing cutoffs, leases), enforce it in queries and let TTL handle cleanup only.

What is the real cost of a wildcard index, and when does it earn its keep?

A wildcard index ({ "$**": 1 }) creates index entries for every field path present in each document, recursively. Entries include a $_path component identifying where the value came from, so the index is one B-tree holding every field combination in the collection. Size therefore scales with total field count across all documents, not with document count.

Costs stack up: write amplification grows with each document's field count; the same query-shape benefit can be had from one targeted compound index for a fraction of the space; and you lose the ability to reason about selectivity, because a wildcard entry for a low-cardinality field is just as large as for a unique one. Comparisons across different paths are also weaker for the planner.

It earns its keep in genuinely schemaless or polymorphic collections with unpredictable ad-hoc queries — an exploration-heavy product catalogue, tenant-defined custom fields. Constrain it: { "customFields.$**": 1 }, or add wildcardProjection, so it covers only the unbounded part of the schema.

How does a text index tokenize text, and where does its size and cost come from?

A text index is effectively a multikey index over the terms produced by the analyzer, not over the original string. For each indexed field, MongoDB applies language-specific processing: splitting into tokens on word boundaries, case-folding, removing stop words (the, and, of — which is why they never match), and stemming so that "running" and "run" collapse to a common root. The resulting terms become keys pointing at the document.

Consequences: size scales with distinct terms per document times average token length, so a text index on long prose is one of the largest indexes you can create, often exceeding the collection. Only one text index is allowed per collection, so it must cover every searchable field, with weights (1 to 99,999) biasing relevance scores rather than filtering.

The default language drives stemming and stop words, and can be set per document via a language field. Prefix and phrase semantics are limited, which is the honest reason to look at Atlas Search for anything beyond keyword matching.

How does a 2dsphere index encode geometry, and what makes a geo query use it?

2dsphere indexes GeoJSON geometry on a sphere. Internally it converts each shape into a covering of S2 cells — a hierarchical subdivision of the sphere into quadtree cells with 64-bit identifiers. The index keys are those cell ids, which makes proximity queries a matter of finding cells at the right level and then verifying exact geometry.

That two-phase design (index lookup on cells, then a precise geometry check) explains the behaviors you see in explain: the index narrows candidates via bounds, and a filter step rejects shapes whose cell covering overlaps but whose actual geometry does not. It also explains why 2dsphere supports polygons, points on a sphere, and legacy coordinate pairs, while the older 2d index treats coordinates as a flat plane with geohash cells and cannot represent real curvature.

For queries to use the index, the predicate must be a supported geo operator ($near, $geoWithin, $geoIntersects) on the indexed field, and $near additionally requires the index and sorts by distance, so it cannot be combined freely with other sorts.

What is a clustered collection internally, and what does it remove from the read path?

A clustered collection stores documents in _id order inside the collection's own B-tree, rather than in record-id order with a separate _id index pointing into it. It must be declared at creation time — you cannot convert an existing collection — and it requires a unique _id.

What disappears: the _id index itself (with its storage and its per-write maintenance), and the second B-tree traversal on every _id lookup. A range scan on _id becomes a contiguous leaf scan instead of a scatter of fetches, which is a large win for append-heavy collections and for anything using _id-based pagination.

What you give up: insert locality now depends entirely on _id monotonicity, so random _id values (hashes, UUIDs) cause page splits in the middle of the tree, exactly like a random primary key in a relational engine. Size hints and capped-style use cases must be reconsidered, and secondary indexes still exist separately.

Why does _id always have an index, and what does that cost per insert?

Every collection except a clustered one has a unique _id index, created automatically, and it cannot be dropped. It exists because _id is the document's identity: replication, retryable writes, and findOne({_id: ...}) all depend on a guaranteed unique, always-present key. If a document arrives without one, the driver or server generates an ObjectId before the write.

Cost per insert is one extra B-tree insert into a unique index — plus the uniqueness check, which is not free under concurrency. This is where the classic anti-pattern lives: a random _id (UUIDv4, random string) inserts into random positions of the _id B-tree, dirtying pages across the whole index and inflating cache pressure, whereas ObjectId is roughly monotonic and appends to the right edge.

So the practical guidance: keep _id monotonic where possible, or use a clustered collection if _id-ordered access is the dominant pattern. Do not try to drop it — you cannot, and you should not want to.

How do you detect redundant indexes by common prefix, and what tooling actually helps?

Index A is redundant if index B has A's key pattern as a leading prefix with the same collation, because B can serve every query A serves (modulo sort direction and unique/sparse semantics). {a:1} is covered by {a:1,b:1}, but not by {b:1,a:1}.

Tooling in order of usefulness: $indexStats for usage counts, db.coll.getIndexes() plus a script that groups key patterns by prefix, the Performance Advisor in Atlas, and db.coll.aggregate([{$indexStats:{}}]) to confirm the "redundant" index really has near-zero accesses. Careful with the numbers: accesses.ops resets on restart and on index rebuild, so a low count right after a deploy is meaningless.

Then be conservative. Two indexes that look like prefixes may differ in collation, in uniqueness, or in a partial filter, and a "redundant" index may be the only one that supports a covered query. Hide before dropping, and check for hint() references in code and stored aggregations — a hint on a dropped index throws.

How does multi-planning actually work, and what is the trial period?

When a query shape is new, the planner does not trust its cost estimates. It generates candidate plans (one per usable index plus a collection scan), runs them concurrently in a race against the real data, and lets them compete. During the trial period each candidate gets a number of "works" — historically on the order of a hundred evaluation cycles — and the plan that returns results fastest, weighted by work completed, wins and is cached for the shape.

Two consequences. The first execution of a shape is slower than steady state because of the race, which is why a p99 spike right after a deploy or a cache flush is often benign. And the winner is chosen on a small sample of the data, so a plan that wins on a mostly-empty collection can lose badly later — the classic reason a query degrades as data grows.

Modern versions shorten this by using statistics and heuristics to prune candidates before racing, and SBE-era planning caches both the winning plan and its trial results.

What makes a plan eligible to be cached, and what invalidates the entry?

A plan is cached only if the shape is cacheable: the query must be a simple enough find/update/delete with a stable parse tree, and the cache honors a bounded number of entries per collection. Multi-planning must have completed, so the entry stores the winning plan plus performance statistics. Aggregation pipelines and shapes the planner cannot safely reuse are simply not cached, and are re-planned each time.

Invalidation events:

  • An explicit planCacheClear or a write operation on the collection — creating or dropping an index, dropping the collection, or a change in the index catalog in some versions.
  • The collection being rebuilt or restored, and collMod-style metadata changes.
  • Cache eviction when the per-collection entry cap is reached and a new shape arrives.
  • Server restart, which empties the cache entirely.

Diagnostic note: explain reports planCacheKey and, in execution stats, the cached plan's works. If planCacheKey changes between runs of what you think is one query, the shapes differ by something subtle — usually literal types.

How is the plan cache keyed by query shape, and where does that keying go wrong?

The key is derived from the parse tree with literal values replaced by placeholders: field names, operator structure, sort, projection, collation, and the collection. Two queries with the same shape share one cached plan, which is the whole point — thousands of parameterized queries cost one planning exercise.

It goes wrong in four predictable ways. Type variance: {a: 5} and {a: "5"} are different shapes, so a collection serving both doubles entries and can cache a plan optimized for the wrong type. Value skew: {tenantId: X} with X matching 90% of documents gets the plan that was tuned for a rare X, because the shape is identical. Entry cap pressure: many shapes evict each other, so planning happens constantly. Stale statistics: nothing forces a re-plan when the data distribution changes, so a bad cached plan can persist indefinitely.

db.coll.getPlanCache().clear() forces re-planning, and .list() with planCacheKey filters shows what is cached. Clear it deliberately: after a bulk load, a major index change, or when you have evidence a specific shape is stuck.

Why does the plan the planner chose get worse as the collection grows?

Because the plan was chosen on a small sample and then frozen in the cache. A shape planned against 10k documents may reasonably prefer an index scan with a FETCH per result; the same shape at 10M documents, where the predicate now matches 40% of the collection, should switch to a collection scan — but the cached winner is never re-evaluated.

The mechanism is cost, not correctness: the planner's estimate of documents matched comes from index bounds and histograms/sampling, and when the estimate is wrong the cost comparison inverts. Growth also changes the physical picture — the index no longer fits in cache, so each FETCH becomes a random disk read, and an index scan that was cheap becomes worse than a sequential scan.

Signals to look for: totalDocsExamined far above nReturned, a rising executionTimeMillis with unchanged query text, and a plan that suddenly differs right after a restart (when the cache was empty). Remedies: drop and recreate the index to trigger re-planning, clear the plan cache, or — better — restructure the query so its shape reflects the real selectivity.

How does the planner estimate cardinality, and why are those estimates so often wrong?

Estimation runs off index bounds plus statistics. From the bounds the planner knows how many distinct key ranges the predicate touches; it then estimates how many documents each range returns using sampled statistics and heuristics about key distribution. For a collection scan it estimates total documents. Everything downstream — whether to use the index or scan — is a comparison of those estimates.

The failures are structural. Statistics are sampled, so rare values are invisible until they are not. Correlated predicates are treated as independent, so {status:"A", region:"EU"} is costed as if the two were unrelated. Skew is invisible: an index on tenantId has one key holding 80% of documents, and the estimate for that key is a uniform-distribution guess. And $or, negation, and regex predicates have bounds the planner cannot bound precisely, so it falls back to a fixed guess.

That is why the honest diagnostic is empirical: compare totalKeysExamined and nReturned against the estimate. When they diverge by orders of magnitude, the plan was built on a bad estimate.

What did the slot-based execution engine change, and what survived from the classic engine?

SBE replaced the classic tree-walking model with a virtual machine over slots: each operator produces values into numbered slots, and a compiled plan is a linear program of instructions. No per-document virtual dispatch, no heap-allocated BSON objects flowing between stages, far better cache locality and less allocation pressure.

What it changed for practitioners: throughput on scan-heavy and aggregation-heavy work improved substantially, and explain gained a second section — queryPlanner still shows the tree, while SBE plans report per-stage metrics under executionStats.executionStages with an nReturned/executionTimeMillisEstimate shape that is subtly different from the classic output.

What survived: the planner and its cost model, the index B-trees, and the plan cache. So the classic reasoning about index selection, bounds, and blocking sorts remains valid; only the execution machinery underneath is different. Many older blog posts describe operator names from the classic engine that no longer appear — that mismatch is a good sign someone is quoting pre-6.0 material.

What is the "express path" for a simple find, and when is it taken?

The express path is a fast lane that bypasses most of the normal execution machinery for very simple reads. If the query is a pure equality/range find on an indexed field, needs no sorting beyond the index order, no blocking stage, no complex projection or collation work, and no shard-side merging, the server can answer it directly from the index with a minimal execution plan.

You see it in explain as a noticeably short plan — often just EXPRESS_IXSCAN or an IXSCAN with no FETCH and no SBE wrapper stages — and in the numbers as a large drop in per-document overhead. That is why a covered equality lookup can run in microseconds while the same logical query with one extra field in the projection costs an order of magnitude more.

The lesson for design: shape point lookups to hit the express path. Keep the projection inside the index, keep the predicate a simple equality, avoid $expr, avoid mixed collations, and do not add a sort the index does not already provide.

totalKeysExamined versus totalDocsExamined: which ratio exposes a bad index?

Read them as a chain: keys examined → documents fetched → documents returned. The diagnostic ratio is totalDocsExamined / nReturned. Ideal is 1.0 for a selective query; anything above roughly 10 starts to matter, and above 100 you are paying for a full scan's worth of work through an index, which is worse than a scan because fetches are random.

The second ratio, totalKeysExamined / totalDocsExamined, tells you whether the index bounds are tight. A large value means the index scan is walking keys that the query then rejects after fetching — a low-selectivity prefix, a multikey expansion, or a range whose bounds are too wide.

"executionStats": {
  "nReturned": 5,
  "totalKeysExamined": 48000,
  "totalDocsExamined": 47000
}

This plan is a disaster on both counts: the index barely narrowed anything, and almost every examined key caused a fetch. The fix is a compound index whose prefix matches the actual predicate, not a hint.

What do seeks and nReturned tell you that the totals do not?

seeks counts how many separate positions in the B-tree the executor had to jump to. A single range predicate on a sorted key is one seek regardless of how many keys it then reads; $in with 50 values is up to 50 seeks; a multikey index or an $or across branches multiplies further.

The distinction matters because seeks are the expensive part of index access on cold pages: each seek is a new descent and likely a new page. A plan with seeks: 1 and 10,000 keys examined is a wide range, cheap per key. A plan with seeks: 5000 and 5,000 keys examined is doing random accesses, and will behave far worse than the totals suggest.

Compare against nReturned for the efficiency picture: many seeks for few results means the index is being used as a filter for sparse hits, and a different key order (or a compound index putting the selective field first) would collapse the seeks. This is the number that explains "the index exists but the query is still slow on a cold cache".

executionTimeMillisEstimate: what is it, and what traps does it hide?

It is a per-stage attribution of time in the winning plan, measured with a coarse timer, and it is an estimate by design: stages report time including the work of their children, so numbers do not sum to the total, and very fast stages often report 0 because the clock resolution is coarser than the work.

Traps worth naming: it reflects only the plan that ran, not the planning cost or the time spent in the race between candidate plans; it excludes client-side time, network, and driver deserialization; and it can be dominated by the first stage that had to touch disk, so a FETCH at 900 ms and IXSCAN at 890 ms describe the same wait, not 1.8 s of work.

Use it for relative shape, not absolutes. If SORT is the biggest slice and its spills is non-zero, that is actionable. If FETCH dominates after a huge IXSCAN, the index is wrong. But never quote it as the query's latency — measure end-to-end time for that, and read executionTimeMillis for the whole execution.

What does spill mean in a plan, and how do you confirm it happened?

A spill means a blocking stage exceeded its in-memory budget and wrote intermediate data to temporary files on disk. In aggregation the budget is 100 MB per stage and spilling requires allowDiskUse: true; without it, the operation fails instead. In a find with a blocking sort, the sort memory limit applies and no disk fallback exists — the query errors with QueryExceededMemoryLimitNoDiskUseAllowed.

In explain look for "spills": 1 (or a non-zero count) plus spilledDataStorageSize and spilledRecords on the offending stage:

"stages": [{ "stage": "$group", "spills": 1,
             "spilledRecords": 4200000 }]

A spill is a latency cliff, not a small penalty: it converts a cache-resident hash table into random I/O, and it competes with the working set for the same disk. If you see spills on a recurring pipeline, the answer is structural — reduce the rows entering the blocking stage with an earlier $match or better index, or pre-aggregate.

What are SORT_MERGE and SORT_KEY_GENERATOR doing in an explain tree?

They are the two halves of an in-memory sort in the classic operator naming, and they still appear in explain output for sorted plans.

SORT_KEY_GENERATOR extracts and materializes the sort key for each incoming document and computes the sort pattern metadata — it is the preparation step, and its cost scales with documents entering the sort. SORT_MERGE is the actual sort: it consumes those keys, orders them (with a top-k heap when a limit is present), and hands results upward.

Reading them correctly matters: a SORT_MERGE with a limit nested under it is the good case — bounded memory, top-k only. A bare SORT_MERGE with no limit and a large nReturned is the dangerous case: unbounded memory and the 100 MB-style failure mode. And if SORT_MERGE appears above an IXSCAN that already produced sorted output, the index was not usable for the sort — usually a direction or prefix problem in the compound key pattern.

Why does FETCH appear after IXSCAN, and when is it avoidable?

IXSCAN walks the index B-tree and yields record ids. Those ids are pointers, not documents, so any field the query needs that is not in the index requires a lookup in the collection B-tree — that is the FETCH stage. It is not an inefficiency by itself; it is the cost of reading the actual document.

IXSCAN { a: 1 }  →  FETCH  →  LIMIT

It is avoidable only in two situations. A covered query — every field in the filter, sort, and projection is in the index, and _id is either projected out or in the index. Or a plan that needs nothing beyond the keys themselves, such as a count-style or existence check where the server can answer from the index.

The performance argument against FETCH is cache behavior, not CPU: each fetch is a random access into the collection tree, so 10,000 fetches on a cold collection means 10,000 potential page faults. That is why "index exists but query is slow" almost always resolves to a FETCH volume problem, and why the covered-query design (trailing fields added to the key) is a real optimization.

PROJECTION_COVERED vs PROJECTION_SIMPLE: what is the difference and why does it matter?

Both are projection stages, but they describe different work. PROJECTION_SIMPLE means the document was fetched and the server is emitting a subset of its fields — an inclusion/exclusion projection applied to a full BSON object. PROJECTION_COVERED means the projection was satisfied entirely from index keys, so no FETCH occurred at all.

So the appearance of PROJECTION_COVERED (or, in SBE output, an IXSCAN with no FETCH) is the explain-level proof that a query is covered. It matters for three reasons: latency and cache (no random collection lookups), read amplification (fewer pages touched per result), and capacity (more queries per node before the working set thrashes).

Conditions to keep it: the projection must be a subset of the index fields; no field needing the full document; the filter and sort must also be index-satisfiable; _id must be excluded or present; and array fields change the semantics — projecting a multikey index field cannot be covered because the array shape is lost in the index.

Which sharding stages appear in an explain, and what do they hide from you?

On a sharded cluster the query is routed by mongos and the explain shows shard-side plans under shards[], with mongos-level stages on top: SINGLE_SHARD when routing was targeted, SHARD_MERGE when several shards returned sorted streams that had to be merged, and SHARDING_FILTER when the query was broadcast and orphaned or non-matching documents had to be filtered out after the fact.

What they hide: the per-shard numbers are separate, so a merged total of 100 ms can be 99 ms on one shard and 1 ms on the other nineteen — you must read shards[s].executionStats individually to find the straggler. And a SHARDING_FILTER in the plan is a red flag: it means the operation could not be targeted by shard key, so every shard scanned and the router discarded. That is the explain signature of a scatter-gather, and the merge stage's memory is bounded, so broadcast queries with sorts are where sharded clusters fall over.

How do you read indexBounds, and what does an unusually wide bound tell you?

indexBounds shows, per indexed field, the interval the scan will walk:

"indexBounds": {
  "tenantId": ["[\\"acme\\", \\"acme\\"]"],
  "createdAt": ["(new Date(1750000000000), new Date(1760000000000)]"]
}

Exact equality shows up as a closed interval with identical endpoints. An open interval is a range. [MinKey, MaxKey] means the field was not constrained at all — the index is scanning that field's entire key space, and any selectivity is coming from the fields before it.

Wide bounds are the single most useful explain signal for "why is this index slow": they show that the predicate did not translate into a narrow interval. Common causes are a leading field with no predicate, a range predicate on an earlier field that prevents later fields from tightening (bounds are only derived for the prefix), a multikey expansion, an $in that turned into many small intervals, or a regex that is not left-anchored and therefore becomes [MinKey, MaxKey] on that field.

How does an $or become independent plans, and how are duplicates removed?

The planner treats $or as a union of branches. Each branch that can use an index gets its own sub-plan — in explain you see an OR stage whose children are SUBPLAN nodes, each holding its own IXSCAN with its own bounds:

OR
  SUBPLAN
    IXSCAN { status: 1 }      bounds: ["open","open"]
  SUBPLAN
    IXSCAN { priority: 1 }    bounds: ["high","high"]

Branches are executed and their results are unioned, then deduplicated by record id — otherwise a document matching both predicates (a high-priority open item) would be returned twice. Deduplication costs memory proportional to the overlap, which is why an $or over low-selectivity predicates can buffer heavily.

Rules that follow: every branch should be independently indexed, or one branch becomes a COLLSCAN that drags the whole union to a scan; the sub-plans cannot share a sort, so an $or plus a sort usually means a blocking sort on top; and if the branches are on the same field, $in is strictly better than $or.

When is hint() the correct fix during an incident, and when does it become technical debt?

hint() is correct when you have evidence the planner's choice is wrong and you need a bounded, reversible mitigation now: a cached bad plan, a shape whose estimate collapses under skew, or a query where the trial-period winner is measurably worse. During an incident, pinning {tenantId: 1, createdAt: -1} on the pathological shape restores latency in seconds and buys time to fix the real problem.

It becomes debt the moment it outlives the incident, because a hint hard-codes a decision whose premise can change: data grows, the hint's index becomes non-selective, a better index is added and never used, and the query silently keeps the old plan forever. Worse, hints are fragile — dropping or renaming the hinted index turns the query into a hard error (BadValue: hint provided does not correspond to an existing index), so index cleanup becomes a code change.

The disciplined pattern: hint to stabilize, then replace it with a fixed query shape or a query setting, and record why it existed. A hint with no ticket number is a hint nobody will ever dare remove.

How do query settings let you reject or cap a query shape, and how do you use them in an incident?

Query settings attach behavior to a query shape rather than to a call site, so the server can enforce policy on queries the application cannot be redeployed to fix. Two levers matter operationally: reject, which refuses to execute matching shapes at all, and maxTimeMS, which caps their runtime.

db.adminCommand({
  setQuerySettings: {
    find: "orders",
    filter: { status: "ARCHIVED" },
    settings: { reject: true }
  }
})

In an incident caused by an unbounded report query hammering the primary, this is exactly the tool: reject the shape and the pressure stops immediately, without killing the application or dropping an index. For shapes that must remain available, a maxTimeMS cap converts an outage into a bounded failure the caller can handle.

Caveats: the shape must match precisely (field names, operators, no literal values), rejected queries surface as ordinary command errors that the application must tolerate, and the settings persist — so they must be inventoried and removed once the code path is fixed.

How does a pipeline actually execute — what distinguishes a streaming stage from a blocking one?

The pipeline is a demand-driven chain of stages: the last stage pulls, each stage produces a document and hands it upstream. A streaming stage transforms one input document into one output document and can emit immediately — $match, $project, $addFields, $limit, $unwind (per element). Such a stage never needs the whole input, so memory is O(1) per document and latency is low.

A blocking stage cannot emit until it has seen all input (or a defined subset): $group, $sort, $bucketAuto, $facet, $graphLookup, $setWindowFields. Its memory is O(distinct groups) or O(rows), which is where the 100 MB budget and spilling come from.

This is why stage order is a performance decision, not a style one. Every $match you move above a blocking stage reduces its input, and every blocking stage you can eliminate by letting an index provide the order or the grouping removes a memory ceiling entirely.

Which aggregation stages block, and why can't they be made streaming?

A stage blocks when its output depends on input it has not seen yet. That is a semantic property, not an implementation choice:

  • $group must aggregate across the entire input stream — a group's final sum is unknown until the last document.
  • $sort without an index-provided order must order everything before emitting the first result.
  • $facet runs several sub-pipelines over the same input, so the input must be buffered and replayed.
  • $graphLookup expands recursively; depth is data-dependent.
  • $setWindowFields needs the whole partition before it can compute a running or lagging value.
  • $bucketAuto needs the distribution to pick boundaries.

Two escape hatches exist: get the order from an index so $sort disappears ($sort + _id on an indexed prefix), or restructure so you never need global aggregation — filter into the blocking stage first, or pre-aggregate into a summary collection. Everything else is paying the memory cost honestly.

What exactly happens at the 100 MB limit, and what does allowDiskUse change?

Each blocking stage has an in-memory budget of 100 MB. Cross it without allowDiskUse and the operation fails with QueryExceededMemoryLimitNoDiskUseAllowed — not a partial result, a failure. With allowDiskUse: true, the stage writes its intermediate state to temporary files under the storage directory and continues.

It is a safety valve, not a fix. Spilling converts memory pressure into disk I/O on the same device serving your working set, so a spilling pipeline slows down every other query on the node. It also means the operation is now competing for the same IOPS as checkpoints and eviction.

Also note what the limit is per stage, not per pipeline: a chain of three blocking stages can hold 300 MB. And the budget applies to memory, not to output size — a pipeline returning gigabytes through a streaming tail is fine, while a modest result set behind a large $group can fail. That distinction is what most candidates miss.

How does $group hold its state, and what changes when it spills?

$group builds a hash table keyed by the group key, holding the accumulators ($sum, $push, $addToSet, $first) for each distinct key. Memory is proportional to the number of distinct keys times the size of the accumulator state — which is why grouping by a high-cardinality field (a request id, a document id) is effectively a materialization of the whole collection.

When it exceeds 100 MB and allowDiskUse is set, the hash table is partitioned and spilled: keys are written to bucket files by hash, then each partition is processed separately. The output is identical, but you have paid a full write and read of the intermediate data. Two accelerators exist and both are worth naming: a $match before the $group to shrink input, and a $sort on the group key before it so the stage can use a sorted (streaming) grouping instead of a hash table — the classic optimization when input is already index-ordered.

$push and $addToSet are the accumulator traps: they hold every value.

Why is $sort followed by $limit cheap in aggregation but a bare $sort is not?

When a $limit sits directly after a $sort, the optimizer coalesces them and the sort becomes a top-k heap of size k instead of a full ordering. Memory is bounded by k, not by input size, so $sort + $limit 10 over 50 million documents holds ten documents in memory. That is why "latest 20 events" pipelines are safe while "all events, sorted" is not.

Two ways this breaks. If anything sits between the sort and the limit — a $addFields, a $project the optimizer will not push through — the coalescing may not happen and you get a full blocking sort. And if the sort can be served by an index (an IXSCAN producing the requested order), there is no sort stage at all: the pipeline is streaming and the $limit lets the executor stop early.

db.events.aggregate([
  { $match: { tenantId: "acme" } },
  { $sort: { createdAt: -1 } },
  { $limit: 20 }
])  // index { tenantId: 1, createdAt: -1 } makes this streaming

Design for the second case; the first is only a mitigation.

How does an aggregation use indexes, and why only at the beginning of the pipeline?

Only the $match, $sort, and $geoNear stages that appear before any stage that transforms documents can be pushed down to the query planner. That leading prefix compiles into an ordinary find-style plan — visible in explain as a $cursor stage with its own IXSCAN and FETCH — and everything after it runs as an in-memory pipeline.

The reason is structural: once a stage has produced new documents ($group output, $project with computed fields, $unwind expansions), those documents have no index. An index maps stored fields to record ids; a computed document is not in any B-tree. So $match after $group filters a derived stream and cannot be indexed at all.

The practical skill is knowing which rewrites keep the pipeline indexable: put every filter that references stored fields first, put $sort before any reshaping, and avoid a $project that renames the field you later filter on — that alone can turn a covered index scan into a full collection pass.

How does $lookup execute, and what changes when the foreign field is indexed?

$lookup is a nested-loop join: for each document arriving from the left side, it runs an inner query against the foreign collection and attaches the matching documents as an array. The shape of that inner query is what determines the cost.

With an index on the foreign field (foreignField), the inner query is an index seek — one B-tree descent per left document, roughly O(1) each, so total cost is linear in the left side. Without an index, the inner query is a collection scan per left document: 10,000 left documents means 10,000 full scans of the foreign collection. That is the single most common cause of a "the aggregation was fine in staging" incident.

db.orders.aggregate([
  { $match: { status: "OPEN" } },              // shrink the left side first
  { $lookup: { from: "customers",
               localField: "customerId",
               foreignField: "_id",
               as: "customer" } }
])

Verify with explain: on the shard/collection side the $lookup stage reports its own totalDocsExamined, and a value far above the left-side count means the inner query is scanning.

Why is $lookup followed by $unwind so much more expensive than $lookup alone?

$lookup produces one output document per input, with an array of matches. $unwind then flattens that array into one document per matched element. So the cardinality changes from N to N × matches — and every downstream stage, including another $lookup, now operates on the expanded stream.

That is the quadratic trap: a chain of two $lookup + $unwind pairs multiplies fan-out at each hop. A left row with 10 matches, each of which has 10 matches, is 100 rows, and each of those rows may trigger its own inner query. Nothing in the pipeline warns you; the plan just gets slow and starts spilling.

Mitigations, in order of effectiveness: filter or project the array down (use a $lookup with a sub-pipeline and $limit: 1 when you only need the top match, or $arrayElemAt instead of $unwind when you need one element); apply $match before the join so you expand fewer left rows; and if the fan-out is inherent, denormalize the fields you actually need into the parent document.

What is $facet's memory restriction, and how do you design around it?

$facet buffers its entire input and replays it into each sub-pipeline, so its memory is proportional to the input size and it is a blocking stage. Each sub-pipeline's own stages are subject to the 100 MB per-stage budget, and — critically — allowDiskUse does not rescue a $facet whose buffered input exceeds the limit; you get a failure rather than a spill.

That makes $facet safe only if the input is already small. The standard fix is to put everything that reduces cardinality before the facet:

[ { $match: { tenantId, createdAt: { $gte: since } } },
  { $facet: {
      byStatus: [{ $group: { _id: "$status", n: { $sum: 1 } } }],
      total:    [{ $count: "n" }] } } ]

If the input cannot be reduced — a global reporting facet over millions of documents — the honest answer is to pre-aggregate nightly into a summary collection and facet over that, instead of buffering a production collection in memory on demand.

What are the real limits of $graphLookup, and why do they bite so quickly?

$graphLookup performs a recursive breadth-first expansion inside the pipeline, following connectFromField to connectToField up to maxDepth. Each level runs a query against the from collection, so the number of queries grows with the frontier size, not with depth alone: a node with 100 children generates 100 lookups at the next level.

Constraints to state: the stage is blocking and has a memory limit on the order of 100 MB for the accumulated visited set and results, spilling only if allowDiskUse is enabled; maxDepth is your only bound on runaway expansion, and unbounded is the default; and depthField adds bookkeeping per result.

The decisive limitation is that $graphLookup cannot use sharding in a targeted way — it queries from from the current context — so on a sharded collection it is closer to a broadcast per level. For deep or dense hierarchies, a materialized closure table or an array of ancestors beats recursion every time.

How does $setWindowFields partition work, and what makes it expensive?

$setWindowFields requires a partitionBy, a sortBy, and an output window. Internally it must group the stream into partitions, order each partition by the sort key, and then evaluate the window function for each document — so it is a blocking stage with a sort underneath, and memory scales with the size of the largest partition.

Cost drivers, in order:

  • Partition cardinality. Many small partitions means the engine manages many independent buffers; one giant partition means it must hold it entire.
  • Sort. If partitionBy plus sortBy can be served by an index prefix, the sort disappears; otherwise it is a blocking sort with the 100 MB budget and possible spill.
  • Window bounds. An unbounded window (range: ["unbounded", "current"]) over a large partition is the streaming-friendly case; arbitrary documents: [-1000, 1000] frames force buffering.

Practical rule: keep partitions small and index-ordered ({ tenantId: 1, ts: 1 } matching partitionBy: tenantId, sortBy: ts), and it behaves well; ignore both and it will spill.

How does $merge materialize results, and what locks does it take?

$merge writes pipeline output into an existing (or auto-created) target collection using on as the match key (default _id) and whenMatched/whenNotMatched to decide between update, replace, insert, keepExisting, or fail. It is not a bulk load: internally it is a stream of find-and-modify-style operations, applied incrementally as documents arrive.

Consequences: it takes document-level write locks and can produce write conflicts (WiredTiger write conflict errors) when the target is concurrently written by the application or by another $merge on overlapping keys. It cannot target the collection being aggregated in the same pipeline, which prevents self-merge but means you need an intermediate collection for in-place enrichment. And it is not atomic as a whole — a failure halfway leaves the target partially updated, so the pipeline must be idempotent and re-runnable.

Design implication: run $merge against a target nobody else writes to — a summary collection consumed only by readers — and prefer $merge over $out when readers must keep seeing valid data throughout.

$out vs $merge: how do they differ under concurrent readers and writers?

$out is a replace-the-whole-collection operation. It builds the result in a temporary collection, then renames it into place. That gives a strong property: readers see the old collection completely, then the new one completely — never a half-built state. The cost is that any concurrent writer to the target is in for a surprise, the rename needs an exclusive moment, and the whole result must be materialized before it becomes visible.

$merge is incremental: it upserts as documents flow, so readers can see a partially updated collection during the run, and concurrent writers contend at the document level, risking write conflicts. In exchange it can update a subset of documents (whenMatched with a $set), preserve documents it did not touch, and run against a collection that other pipelines are also feeding.

So: $out for full rebuilds of a derived collection refreshed on a schedule, where atomicity of publication matters more than availability of the target; $merge for continuous incremental maintenance, and whenever dropping untouched documents would be wrong. Neither is safe as a substitute for a transaction.

What do $densify and $fill cost, and when do they backfire?

$densify inserts documents into gaps along a numeric, date, or partitionByFields sequence at a given granularity. $fill then populates missing values using value, locf (last observation carried forward), or linear interpolation. Together they turn sparse time-series-shaped data into a dense grid suitable for charting.

The cost is that output size is chosen by the granularity, not by the data. A year of sparse events densified at one-minute granularity is 525,600 buckets per partition — the stage generates those documents whether or not any data exists. With partitionByFields, multiply by the number of partitions. Both stages require sorted input per partition, so they add a sort, and $fill is window-like and buffers.

Backfire conditions: fine granularity over a long range, many partitions, or being placed before a $match that would have filtered the range. The pattern that works is to filter the time range first, densify at the coarsest granularity the chart can use, and push the densification to the reporting layer when the consumer can tolerate gaps.

How do you read explain() output for an aggregation pipeline?

Aggregation explain is shaped differently from a find. You get two things: a $cursor stage that shows the query plan for the indexable prefix (with its own IXSCAN/FETCH, indexBounds, and examined counts), and a stages array listing every subsequent pipeline stage with per-stage metrics.

{ "stages": [
    { "$cursor": { "executionStats": { "nReturned": 1200,
                  "totalKeysExamined": 1200, "totalDocsExamined": 1200 } } },
    { "$group": { "nReturned": 12, "executionTimeMillisEstimate": 340 } },
    { "$sort":  { "nReturned": 12, "spills": 0 } } ] }

Read it top-down looking for the first stage where nReturned collapses or where time concentrates. A $cursor returning 1.2M rows into a $group that outputs 12 is a story about missing index coverage at the start, not about the group. spills, usedDisk, and executionTimeMillisEstimate per stage are the three fields that turn "the aggregation is slow" into a named stage.

What is $documents for, and how do you use it to test a pipeline?

$documents is a source stage that produces documents from a literal expression — either an array of document literals or an expression that evaluates to one. It must be the first stage, and it lets a pipeline run without touching a collection at all:

db.aggregate([
  { $documents: [ { _id: 1, amount: 10, status: "A" },
                  { _id: 2, amount: 5,  status: "B" } ] },
  { $group: { _id: "$status", total: { $sum: "$amount" } } }
])

Its value in an interview answer is as a testing discipline: you can unit-test the transformation semantics of a $group, $setWindowFields, or $densify chain in isolation, with deterministic fixtures and no seed data, and without a server-side $lookup into a real collection. It is also useful for generating parameter rows to $lookup against, and for reproducing a production bug with three documents instead of a dump.

Limits worth knowing: results flow back to the client as a normal cursor, the stage cannot appear anywhere but first, and it is a debugging/utility tool rather than a production data source.

Why can't a $match after $group use an index, and what is the fix?

Because at that point the documents do not exist in any collection. $group emits newly computed documents whose _id is the group key and whose fields are accumulator results. There is no B-tree mapping those values to anything, so the planner has nothing to seek into — the $match is a filter on a derived stream and is executed as a plain stage.

This is often a correctness-of-performance issue rather than a query error, because the query looks selective:

[ { $group: { _id: "$customerId", spend: { $sum: "$amount" } } },
  { $match: { spend: { $gt: 10000 } } } ]   // no index possible

The fix is to move selectivity to where the data is stored: filter on stored fields before the group ($match on date range, region, status), so the group sees a smaller input and produces a smaller output. Where the post-group filter is essential (a HAVING-style condition), accept it as an in-memory filter over a small result set — that is cheap. The failure mode is a large group output filtered to a handful of rows, where the work was already done.

How do you design a pre-aggregation strategy with a summary collection?

The idea is to compute expensive aggregations once, on a schedule or on change, into a small collection shaped exactly like the queries that need it — then serve dashboards from a covered index scan on a few thousand documents instead of a $group over millions.

The design decisions:

  • Grain. Pick the coarsest grain that answers the query: per tenant per hour, not per event. Anything you cannot derive from the summary must be answered elsewhere.
  • Key. Make the summary's _id the natural grain key ({tenantId, bucket}), so the refresh is an idempotent $merge on _id rather than a delete-and-insert.
  • Refresh. Either a scheduled $merge over a bounded window, or incremental maintenance via change streams updating counters.
  • Late data. Recompute the last N buckets each run, because events arrive out of order and a bucket is never final on first write.

The cost is staleness and a second source of truth. Mitigate with a documented freshness contract and a rebuild path that reconstructs the summary from raw data, so a bad refresh is recoverable rather than terminal.

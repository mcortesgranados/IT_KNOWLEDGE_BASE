How do you turn an RPO and an RTO into an actual backup schedule?

Start from the business, not from the tool. RPO is how much data you may lose; RTO is how long you may be down. An RPO of fifteen minutes rules out nightly dumps entirely — you need continuous oplog-based recovery, such as Atlas continuous cloud backups or volume snapshots plus oplog replay. An RPO of twenty-four hours tolerates one snapshot a day, but only if the business truly accepts losing a day of writes.

Then convert RTO into restore throughput. Measure a full restore of your real data size, add cluster provisioning, DNS or connection-string cutover, TLS validation and application smoke tests. If a 400 GB restore takes three hours, an RTO of one hour is fiction unless you keep a warm standby cluster.

Finally tier your datasets: a payments collection and a log archive should not share the same policy, and the tiering decision belongs in writing, signed by the data owner.

Logical dump, volume snapshot, or Atlas continuous backup: how do you choose?

Each answers a different question.

  • Logical dump (mongodump): portable, selective, survives version and platform changes, restores one collection if needed. Slow on large datasets, heavy on the source, and not point-in-time consistent without oplog capture.
  • Volume snapshot: fast and cheap at scale, taken outside the database, restored by attaching disks. It is tied to the storage provider and to the same major version, and it captures a whole deployment, not a collection.
  • Atlas continuous cloud backup: snapshots plus oplog, giving point-in-time restore to a new or existing cluster with almost no load on the source. The trade-off is that you inherit Atlas retention limits, region choices and pricing.

Mature deployments usually run snapshots as the primary recovery mechanism and periodic logical dumps as the portability and compliance layer.

Why is a filesystem snapshot taken without the journal inconsistent?

WiredTiger writes to the journal continuously but only checkpoints the data files periodically — every 60 seconds by default. Between checkpoints, committed writes live in memory and in the journal, so the data files on disk are a torn mix of old and new pages: half-written index entries, half-applied updates.

Copy those files while mongod runs and you get a database where pages disagree with each other. Include the journal in the same snapshot and recovery can replay from the last checkpoint to a consistent point, because the journal is the source of truth for everything after the checkpoint.

This is why "snapshot the volume" is only a backup when the whole data directory, journal included, is captured atomically. Splitting the journal onto a different volume that is snapshotted separately is a classic way to produce a backup that will not open.

db.fsyncLock()   // optional: freeze writes for the copy window
db.fsyncUnlock()

Which replica set member do you back up, and with what write concern?

Back up a secondary, never the primary, so the dump does not evict the working set the application depends on. Prefer a member that exists for this purpose: a hidden, priority-0 secondary in the same region, or a dedicated backup node.

Consistency comes from the read position, not the member. Use --oplog with mongodump so the dump records the oplog position when it started and captures the oplog entries written during the dump; mongorestore --oplogReplay then applies them, giving a point-in-time consistent restore across collections.

mongodump --host rs0/backup1:27017 --readPreference=secondary \
          --oplog --gzip --archive=/backup/rs0-$(date +%F).gz

The write concern that matters here is the one your application uses: if it writes with w:1, a secondary backup can legitimately miss acknowledged writes that were rolled back after a failover, so the backup can be "consistent" and still be behind what clients were told was committed.

Why does the order of operations matter when backing up a sharded cluster?

Because chunk metadata and the data it describes must come from the same instant. The config database records which ranges of the shard key live on which shard; if you dump shard A, then the balancer migrates a chunk from A to B, then you dump shard B, your backup describes a cluster that never existed. Restoring it produces missing ranges or duplicate ranges, and the cluster refuses to start cleanly.

The safe sequence is to stop the balancer, capture the config database and each shard at effectively the same point, then re-enable balancing.

sh.stopBalancer()
// dump config servers, then each shard, recording timestamps
sh.startBalancer()

For restore the order is reversed: config first, so mongos knows the topology, then the shards. This is also why a single mongodump through a mongos is not a valid sharded backup — it reads collections sequentially while the cluster keeps moving chunks underneath it.

Do you need to back up indexes and configuration data, or can you rebuild them?

Index definitions are part of the dump: mongodump writes them alongside each collection, and mongorestore recreates them unless you pass --noIndexRestore. They are also the cheapest thing to lose, because they can be rebuilt from the data — at a cost. On a multi-terabyte collection an index build can take hours and saturate I/O, so a restore that rebuilds every index is a slower restore.

Configuration data is different, and people forget it:

  • The config database in a sharded cluster — without it the dump is unrestorable.
  • admin.system.users and admin.system.roles — your users and custom roles.
  • Collection options: validators, collation, time series options, clustered index settings.

A useful trick for large restores: restore data with --noIndexRestore, then build indexes afterwards, and let secondaries build in parallel rather than serially during the load.

What does mongodump actually cost the primary, and how do you avoid paying it there?

mongodump reads every document of every collection through normal queries. On the primary that means a long stream of full collection scans, each pulling pages into the WiredTiger cache and evicting the hot working set. The visible symptoms are a latency spike, more disk reads and a cache that suddenly has to refill — during business hours, on the node serving writes.

Practical mitigations, in order of preference:

  1. Dump from a dedicated hidden or priority-0 secondary, ideally in the same region to avoid cross-region read cost.
  2. Use managed snapshots so the source sees no query load at all.
  3. Throttle: --numParallelCollections 1, a projection of only what you need, and a maintenance window.
  4. Prefer --gzip --archive to a local fast disk, not to a network share that back-pressures the read.
mongodump --host rs0/backup1:27017 --readPreference=secondary \
          --numParallelCollections=1 --gzip --archive=/backup/dump.gz

Note that a dump is not a snapshot: without --oplog different collections are read at different times, which is fine for reference data and wrong for money.

How do you compress and encrypt backup artifacts, and where does the key live?

Compression is the easy half: mongodump --gzip --archive=... produces a single compressed stream, and mongorestore --gzip --archive=... reads it back. A single archive is much easier to ship, checksum and encrypt than a directory tree.

Encryption is the half people get wrong. gzip is not encryption. Encrypt the artifact after dumping, or encrypt the destination:

mongodump --gzip --archive=/tmp/d.gz
age -r $BACKUP_PUBKEY -o /backup/d.gz.age /tmp/d.gz
sha256sum /backup/d.gz.age > /backup/d.gz.age.sha256

Keep the private key outside the backup account and outside the database account — a key stored beside the ciphertext means a single compromised credential loses both. Object storage with server-side encryption and a bucket policy that denies deletion is a good second layer, and writing the checksum next to the artifact lets you prove the file you are about to restore is the file you wrote.

How do you design a retention policy beyond "keep 30 days"?

Retention exists to satisfy two different clocks: operational recovery (hours to days, where you need dense restore points) and compliance or investigation (months to years, where you need sparse but immutable copies). A grandfather-father-son scheme serves both: keep 7 daily, 4 weekly, 12 monthly, and one or two yearly snapshots.

Three details decide whether the policy survives an audit:

  • Immutability. If a compromised administrator can delete snapshots, retention is a suggestion. Atlas backup compliance policies make retention unchangeable, block early deletion and require extra confirmation; object storage has equivalent lock modes.
  • Legal hold. A hold must override expiry, so it needs an owner, a ticket reference and a documented release process.
  • Deletion semantics. Know whether terminating a cluster deletes its backups — on some managed tiers it does.

Also align retention with your oplog window: a snapshot you cannot roll forward is worth less than it looks.

Cross-region backups: what do they cost, and what do they actually buy you?

They buy survival of a regional failure and, more importantly, isolation from your own account: a copy in a different region and a different account is the only thing that helps when the primary region is down or the credentials are compromised.

The cost is threefold: storage duplicated per region, inter-region data transfer on every copy, and slower restores because the bytes are far from the compute you will restore onto. On Atlas this is delivered by additional snapshot regions or by snapshot distribution to another region; the restore target must then be created there.

Design questions worth asking in the interview:

  • Is the backup region in the same cloud and the same legal jurisdiction? Data-residency rules may forbid the copy you just made.
  • Do you have the keys there too? An encrypted backup in a region where the KMS key is unavailable is not a backup.
  • Have you restored from the remote copy at least once?

What does a real restore test look like, and how often should you run it?

A restore test is a rehearsal with a clock and a checklist, not a mongorestore that exits zero.

  1. Pick a real snapshot or dump from production, not a synthetic dataset.
  2. Provision a disposable cluster at the same major version, with the same TLS and auth configuration as production.
  3. Restore and time it, including provisioning and index builds.
  4. Verify: document counts per collection against the source at that timestamp, validate({full: true}) on the critical collections, index count and types, users and roles present.
  5. Point a real application build at it and run smoke tests — reads, writes, an aggregation, a login.
  6. Record the measured RTO and the failures found, then destroy the cluster.

Monthly for the tier-1 dataset, quarterly for the rest, and always after a topology change, a major upgrade or a backup policy change. Automate it so it runs without a human remembering, and alert when the drill fails — a silent drill is theatre.

How do you restore a single collection, or only a range of dates?

Two different mechanics, and only one of them is native.

From a logical dump you have full control: restore one namespace into a side database and copy across, or restore directly with a namespace filter.

mongorestore --gzip --archive=/backup/dump.gz \
  --nsInclude "shop.orders" --nsFrom "shop.*" --nsTo "recovery.*"
mongorestore --gzip --archive=/backup/dump.gz --nsInclude "shop.orders" \
  --queryFile ./range.json

// range.json
{ "createdAt": { "$gte": { "$date": "2026-01-01T00:00:00Z" },
                 "$lt":  { "$date": "2026-02-01T00:00:00Z" } } }

From continuous backup point-in-time restore is cluster-wide: you cannot ask Atlas to rewind one collection. The pattern is to restore to a temporary cluster at the chosen timestamp, export the collection, and load it into production.

Watch the consequences of partial data: documents that reference the missing ones now dangle, unique indexes can collide with rows that already exist, and any derived or aggregated state is now wrong. Partial restore is a surgical tool, and surgery needs a plan for referential integrity.

Point-in-time recovery: what granularity do you actually get?

You get operation granularity, not wall-clock granularity. The restore replays oplog entries up to your target timestamp, and the last entry applied is the last one whose timestamp is less than or equal to the target. So the finest real resolution is "the state after the last write before T" — if nothing happened for ten minutes, no timestamp in that window produces a different result.

Three constraints bound what you can promise:

  • Atomic units. A transaction or an index build appears in the oplog as a single unit, so you cannot restore to a point inside it.
  • Oplog window. The rewindable range starts at the oldest oplog entry, not at the oldest snapshot.
  • Scope. It is cluster-wide. There is no per-collection PITR, which is why "just rewind the orders collection" is usually a two-step restore.

In an interview, answer with the window you can prove — "we can rewind 48 hours with per-operation precision" — rather than an unqualified "we have PITR".

What happens if the oplog is shorter than the PITR window you promised?

Your promise silently becomes a snapshot restore, and every write between the snapshot and the incident is gone. This is the most common false guarantee in MongoDB operations, because the oplog window shrinks precisely when you need it: a bulk import, a backfill, or a re-index generates far more oplog than the steady state, and the oldest entries roll off.

Detection is a metric, not a hope. Track the window as the timestamp difference between the first and last oplog entry and alert when it drops below your committed RPO horizon:

db.getReplicationInfo()
// or
db.getSiblingDB("local").oplog.rs.find().sort({$natural:1}).limit(1)

Mitigations: size the oplog for peak write volume rather than average, set a minimum retention where the platform offers one (Atlas exposes an oplog minimum retention setting), and cap bulk jobs so they cannot outrun retention. Then write the honest fallback into the runbook: if the target predates the oplog, restore the newest snapshot and reconcile from application logs.

How do you restore "hot" into another cluster and cut over without a long outage?

You keep production serving while the restore happens somewhere else, then move the pointer. The restore target is a separate cluster, built to the same major version, with the same auth, TLS and index configuration; you restore the dump or the snapshot there and validate while users keep writing to the old system.

Cutover is where the discipline is:

  1. Restore to time T, then keep replaying or dual-writing so the gap stays small.
  2. Freeze writes with a short maintenance flag, or flip the application to a write-pause mode.
  3. Apply the final delta, verify counts on the few critical collections.
  4. Switch the connection string — DNS with a low TTL, or a secrets-manager value the app re-reads.
  5. Keep the old cluster readable for a defined rollback window, then decommission.

Watch for cached connections: drivers hold sockets to the old host for minutes, so force a restart or accept a mixed-write period you must reconcile.

Your documented RTO is one hour but the real restore takes four. How do you find and close the gap?

Time a real drill end to end and break it into phases with timestamps: detection and decision, cluster provisioning, artifact transfer, data load, index builds, validation, cutover, and cache warm-up. Almost always the documented number was computed from the load only, or from a dataset a tenth of the current size.

Typical findings and their fixes:

  • Transfer dominates because the artifact is in another region → co-locate backup and restore target.
  • Index builds are serial → restore with --noIndexRestore, load, then build in parallel.
  • One monolithic mongorestore → raise parallel collections, use a bigger target host, restore independent collections concurrently.
  • Human latency → pre-authorised runbook, two named decision makers, credentials already escrowed.

Then publish the measured number and either invest to hit the target or renegotiate it with the business. An RTO nobody has tested is a rumour.

Who declares a disaster, and what belongs in the DR runbook's first page?

Declaring a disaster is a decision with a named owner, not a consensus. Typically the on-call engineer detects, the incident commander declares, and the data owner approves any restore that will discard writes — because rewinding to T-10 minutes destroys ten minutes of real customer transactions. That approval is a two-person rule, logged with a timestamp.

The first page should be readable under stress:

  • Declaration criteria, as falsifiable conditions: region unavailable, corruption on two members, confirmed data loss beyond RPO.
  • Named roles: incident commander, database lead, comms.
  • Decision tree: restore in place versus restore to a new cluster versus fail over to the DR region, with the trade-off in one line each.
  • Exact commands and identifiers: cluster names, snapshot IDs, the KMS key alias, the escalation phone numbers.

Bias to declaring early: a false alarm costs a meeting, a late declaration costs the RPO. And rehearse the runbook — a document nobody has executed is fiction with good formatting.

How do you back up users, roles, and the Atlas configuration itself?

Two separate problems that people merge and then lose half of.

Inside the database, users and roles live in the admin database — system.users and system.roles. Dumping admin captures them, including the stored SCRAM credentials, so a restore keeps existing passwords. Many teams prefer to treat users as code instead: keep role definitions in version control and recreate users from a script, so the restore is reproducible and reviewable rather than a binary blob.

mongodump --db admin --collection system.roles --out /backup/admin
db.getSiblingDB("admin").getRoles()

For Atlas, database users and most security settings are not in the cluster at all — they live in the control plane. Back them up through the Admin API or, better, Terraform: project, cluster tier, IP access list, private endpoints, custom roles, alert configuration, backup compliance policy. A cluster restored from snapshot comes back without any of that context, so an infrastructure-as-code repository is the real configuration backup.

How do you detect data corruption in MongoDB, and what can actually be salvaged?

Detection comes from three places. First, WiredTiger checksums: a bad page surfaces as a checksum mismatch in the log and often prevents startup or fails reads on the affected pages. Second, validation: db.collection.validate({full: true}) walks the collection and its indexes and reports inconsistencies — expensive, so run it on a secondary, one collection at a time. Third, symptom-level signals: documents that fail to decode, indexes whose counts drift, aggregation results that stop reconciling.

What you can salvage depends on the damage. Index corruption is cheap: drop and rebuild. Document damage on one member is fixed by resyncing it from a healthy peer. Logical corruption — bad writes, a buggy migration — is not storage damage at all, and only a point-in-time restore fixes it, because every member faithfully holds the same wrong data.

Keep the damaged files before you repair anything; forensics after an overwrite is guesswork.

How do you rebuild a single node without stopping the cluster?

You let the replica set heal itself rather than restoring a backup. The clean version is initial sync: stop mongod on the bad member, move or delete its data directory, start it again with the same configuration, and it copies the full dataset from a healthy member and then tails the oplog. The cluster keeps a primary and at least one other secondary the whole time, so availability is unaffected — provided you never take two members down at once.

systemctl stop mongod
mv /var/lib/mongo /var/lib/mongo.corrupt.$(date +%s)
systemctl start mongod
rs.status()   // watch stateStr: STARTUP2 -> SECONDARY

Practical cautions: initial sync is I/O- and network-heavy, so throttle it or do it off-peak; a member with a huge dataset can take hours; and if the member is also a backup source, pause that job. If the data directory is intact and only the process failed, restarting is enough — resync is for corruption, not for a crash.

Someone ran dropDatabase() in production. Walk me through the recovery.

First, stop the bleeding and take a snapshot of the current state. Then check how much time has passed, because that decides everything: if the drop is inside the oplog window you can restore to just before it; if it is outside, you restore the newest snapshot and lose everything since.

The practical options, in order:

  1. Restore to a side cluster at T-1 minute, verify the data looks pre-drop, then either copy the database into production or cut over to the side cluster.
  2. If a logical dump exists from before the drop, restore just that database with a namespace filter — much faster than a full cluster restore.
  3. If neither, salvage from a delayed or hidden secondary that has not yet applied the drop, if one exists and you can stop it in time.

Note that dropDatabase leaves users intact, so authentication keeps working while data is gone — a classic misdiagnosis.

A migration script deleted four million documents instead of forty. How do you restore them without undoing the last two hours of legitimate writes?

You cannot rewind production: point-in-time restore replaces the whole cluster, so a full rewind throws away two hours of good writes from every other collection. The pattern is restore to a side cluster, extract, merge back.

  1. Restore a side cluster to T-1, just before the bad script ran.
  2. Identify the affected documents with a predicate you can reproduce — usually a field the bad script wrote, a timestamp range, or an explicit _id list exported from the diff.
  3. Insert them back into production with unordered bulk writes, ignoring duplicate-key errors on documents that still exist.
  4. Reconcile counts, and re-run any downstream aggregation or index that consumed the now-corrected data.
db.orders.find({ updatedBy: "migration-2026-04" },
              { _id: 1 }).forEach(d => print(d._id))

Two things matter: the restore target was isolated, and the merge was idempotent, because you will run it twice. And if "deleted" really means soft deletes were flipped, the fix is one targeted updateMany, not a restore.

The oplog on a cluster is truncated or has a gap. What are the recovery options?

Distinguish two different problems. A member whose oplog has a gap — after a long outage, a resize, or a restore — cannot catch up, and must resync from scratch: stop it, clear the data directory, let it initial sync. There is no way to "repair" a gap in a replication stream.

A whole deployment with an unexpectedly short oplog window is a recovery-scope problem: PITR is now limited to the surviving entries, so if the target timestamp is older than the first entry you fall back to the newest snapshot. Check the actual window before promising a rewind:

db.getReplicationInfo().timeDiff   // seconds covered by the oplog
rs.printReplicationInfo()

If the truncation came from replSetResizeOplog or from restoring an old oplog alongside newer data, treat the deployment as suspect and validate the collections before returning to service. And record the incident: "our PITR window was 40 minutes, not 24 hours" is a finding that belongs in the postmortem, not in a Slack thread.

The restore is running and it will clearly exceed the RTO. What do you do?

Switch from "restore everything" to "restore the business". The RTO is a promise about service, not about bytes, so the question becomes: what is the smallest dataset that makes the product usable?

Concrete moves, roughly in order:

  • Prioritise namespaces. Restore the revenue-critical collections first and in parallel, leave analytics and archives for later; announce degraded mode.
  • Split the work. Independent collections can be restored concurrently into the same target, and index builds can be deferred until after the load.
  • Remove bottlenecks. Bigger target host, local SSD for the artifact, artifact already in the target region, no compression on read if CPU-bound.
  • Communicate with a number. "Available in 40 minutes with orders and catalog; history backfills by 18:00" beats silence.

Then escalate honestly: if the measured minimum exceeds the RTO, the target was wrong or the architecture needs a warm standby. Deciding that mid-incident is expensive; deciding it in the postmortem is free.

Can you restore a dump into a different MongoDB version?

Forward, yes; backward, no. mongorestore into the same or a newer major version is supported, and it is the normal upgrade path. Restoring a dump produced by a newer server into an older one is unsupported, because the BSON types, index options and collection metadata may not exist there — and data files themselves can never move to an older version.

Even forward restores need care:

  • Feature compatibility version. A dump can contain a clustered collection, a columnstore index or a validator the target FCV does not allow.
  • Collection options such as time series granularity or collation are replayed as-is; a mismatch fails the collection.
  • Index builds are slower on the newer version's defaults, and some options are silently normalised.

The reliable drill: restore into a scratch cluster of the exact target version, run validate and smoke tests, then touch production. Going backwards means export and reload, never a data-file downgrade.

How do you prove a restore is actually complete and correct?

With evidence captured before the incident, compared afterwards. A restore that returns success has only proved that the tool did not crash.

A defensible checklist:

  • Counts per collection against the source at the same timestamp — countDocuments({}) on the important ones, not estimatedDocumentCount, which reads metadata and can be stale.
  • Structural validation: db.coll.validate({full: true}) on the tier-1 collections, on a secondary where possible.
  • Index inventory: compare getIndexes() names, keys and options with the source; a missing unique index is a silent data-quality bug.
  • Sampled content: hash a few hundred documents by _id on both sides and compare, since counts hide truncation.
  • Configuration: validators, users and roles, FCV, sharding metadata.
  • Behaviour: application smoke tests, including one write.

The legacy dbHash command still exists in some deployments but is deprecated; do not build a verification story on it. Store the baseline numbers with the backup so future-you has something to compare against.

How do restores interact with the feature compatibility version?

FCV gates which features the server will accept, so it decides whether restored metadata is legal. Two scenarios matter.

Restoring into a cluster with a lower FCV can fail or silently lose capability: an index type or collection option introduced in the newer release is rejected, and the collection restores without it. That is worse than a hard failure, because you learn about it weeks later.

Restoring the admin database can carry system.version, the document that holds the FCV itself. Dropping an old FCV document onto a cluster running newer binaries can leave the deployment in a state it will not start from. Restore user and role collections selectively, and set FCV explicitly afterwards with setFeatureCompatibilityVersion rather than inheriting it from a dump.

Practical rule: after any cross-version restore, confirm db.adminCommand({ getParameter: 1, featureCompatibilityVersion: 1 }) matches the intended value, and only then let applications connect.

Walk me through restoring in Atlas from continuous cloud backup.

In the project, open the cluster's Backup tab. You get two modes: pick a snapshot, or pick a point in time inside the oplog-backed window. Then choose the target — the same cluster, which overwrites its data, or a new cluster, which is the safe default — and confirm.

What interviewers want you to know beyond the clicks:

  • Restoring in place is destructive and causes downtime; connections drop and the data is replaced. Always restore to a new cluster first, validate, then cut over.
  • Atlas database users are not part of the restore. They live in the control plane, so the new cluster needs them recreated.
  • The rewind window depends on oplog retention, not on how many snapshots exist.
  • Restores are cluster-scoped; no single-collection rewind.
  • Restore into an equal or larger tier, in a region reachable from your application.

After the restore, run your validation checklist and record how long it took — that number, not the vendor's, is your RTO.

How do you migrate from on-premises MongoDB to Atlas with near-zero downtime?

With a continuous sync tool rather than a dump: mongosync (Atlas's live migration service) copies the initial dataset and then tails changes, so the destination stays current while the source keeps serving.

The sequence that keeps the outage to minutes:

  1. Prepare the destination: cluster size, indexes, users, network path (peering or private endpoint), IP access list.
  2. Start the sync; let the initial copy finish and watch lag fall to near zero.
  3. Rehearse the cutover in staging, including the application's connection-string change.
  4. Freeze writes briefly, wait for lag to reach zero, commit the cutover.
  5. Point applications at the new cluster, validate, and keep the source intact for a rollback window — the tool supports reversing direction, which is the reason to prefer it over a dump.

Things that bite: heavy index builds during sync, large transactions, and users or roles that live outside the data. Also plan the reverse: a documented way back for 24 hours beats optimism.

A major version upgrade failed halfway. What is your rollback plan, and what makes it impossible?

The critical fact: once FCV has been raised, downgrading the binaries is not supported, because the data files may already use newer on-disk formats. So rollback is only cheap during the bake period, while FCV is still on the old value.

A workable plan:

  • Before: verified snapshot or dump, old binaries or machine image still available, rollback triggers written down.
  • During: upgrade secondaries first, keep FCV low, run the workload, then step up and raise FCV last.
  • If it fails: stop, step the primary back to an unupgraded member if one exists, restore the pre-upgrade snapshot if not, and accept losing writes made after the snapshot — which is why the decision window should be short.

The uncomfortable part: writes accepted after the upgrade must be harvested or discarded. Say that out loud. Best practice is a staged deployment rehearsed under real load, so rollback is a restore you have timed.

The backup is encrypted and the key is gone. What now?

Honestly: the data is gone. Encryption is not a lock you can pick — without the key-encryption key the data-encryption keys cannot be unwrapped, and no amount of mongorestore changes that. This is the one failure mode where a backup can exist, be intact, and still be worthless.

Before declaring loss, exhaust the boring possibilities:

  • Pending deletion. Cloud KMS keys usually sit in a waiting period before destruction and can be cancelled; check that first, it is the most common rescue.
  • Old key versions. Rotation keeps previous versions; a backup from before the rotation needs the version that was current then.
  • Escrow copies. HSM backup, offline key ceremony material, a replica of the KMS in another region.
  • Key identifier drift: the key exists and only the alias or credential was lost.

Prevention is the real answer: documented escrow, deletion blocked by policy, a drill that restores using the escrow copy, and keys in an account DBAs cannot delete.

What goes into the postmortem of a data-loss incident, and what do you automate afterwards?

The postmortem is about the system, not the person. Content that matters:

  • Timeline in one-minute resolution: first bad write, detection, declaration, restore start, service restored.
  • Impact quantified: documents lost, customers affected, the actual RPO and RTO achieved versus promised.
  • Detection gap: why nobody noticed for forty minutes — usually no alert on the thing that broke.
  • Contributing factors, plural, because single-cause stories are usually wrong.
  • Actions with owners and dates, and the ones you deliberately declined.

Then automate the mechanical parts, because humans repeat mistakes: backup success and freshness alerts, an oplog-window alert tied to the RPO, a scheduled restore drill that fails loudly, checksum verification of artifacts, and the destructive commands behind a two-person approval. The best signal of a mature team is that the runbook shrank after the incident, not that the document grew.

SCRAM-SHA-256 versus SCRAM-SHA-1: what actually differs, and why does SHA-1 still exist?

Both are challenge-response mechanisms: the client never sends the password, and the server stores a salted, iterated derivative rather than the password itself. SCRAM-SHA-256 uses SHA-256 with a higher default iteration count, so an offline attack against a stolen system.users collection is far more expensive. It also gives the client proof that the server knows the verifier, so the server is authenticated too.

SHA-1 survives for compatibility, not for merit:

  • Credentials created before SCRAM-SHA-256 existed are stored in SHA-1 form and keep working after an upgrade.
  • Old drivers and embedded clients may only offer SHA-1.
  • Mechanisms are per-user, so a deployment can run both during migration.

The migration is explicit: update the user to allow only SHA-256, reset the password so the verifier is regenerated, then restrict the server to SHA-256 once every client is verified. Leaving both enabled forever means the weakest accepted mechanism defines your security posture.

x.509 authentication: what is it for, and where does it fit in a cluster?

It replaces a shared secret with a certificate signed by a CA you control. The client presents a certificate, MongoDB maps the subject to a user in the $external database, and no password is ever transmitted or stored. That makes it a natural fit for machine-to-machine authentication: application pods, migration agents, and the members of a replica set or sharded cluster authenticating to each other.

net:
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/ssl/mongod.pem
    CAFile: /etc/ssl/ca.pem
security:
  clusterAuthMode: x509

Why teams choose it: no static password to leak, short-lived certificates are possible, and revocation is a CA-level operation. The costs are real too — a PKI to run, per-node certificates with correct subject names, and an expiry date that will one day take down the cluster at 3 a.m. unless you alert on it. Rotate by putting both CAs in the trust bundle before switching issuers, never after.

LDAP, Kerberos, or OIDC: how do you decide?

Pick by where the identity already lives and what the client can do.

  • Kerberos: an existing Active Directory or MIT realm, Windows-centric estates, and services that should never hold a password. Clients obtain a ticket from the KDC; MongoDB validates the service ticket for its own principal. Strong SSO story, but every host needs a service principal and clock skew becomes an outage.
  • LDAP: a directory that is the source of truth for people, with simple bind against the directory and group membership driving authorization. Straightforward to operate; the directory becomes a hard dependency for every login, so cache or plan for its outage.
  • OIDC: cloud-native identity, short-lived tokens, workload identity federation for CI and services, no long-lived database password at all. The right default for new Atlas-centric platforms.

In practice: humans through SSO, workloads through x.509 or OIDC workload identity, LDAP only where the directory is already the contract. Document which governs which principal.

How do authenticationRestrictions work, and what do they not protect you from?

They are per-user restrictions evaluated at authentication time: an array of source CIDR ranges and, optionally, expected server addresses. A login attempt from outside the allowed ranges is rejected even with correct credentials.

db.getSiblingDB("admin").createUser({
  user: "opsAdmin", pwd: passwordPrompt(),
  roles: [{ role: "clusterMonitor", db: "admin" }],
  authenticationRestrictions: [
    { clientSource: ["10.20.0.0/16", "203.0.113.7/32"] }
  ]
})

What they buy: a stolen admin password is useless from an attacker's network, which is a meaningful second factor for privileged human accounts.

What they do not do: they are not a firewall, they do not encrypt anything, and they only see the address the server observes — behind a proxy, NAT or a connection pooler that is the proxy's address. On sharded clusters the restriction must be configured consistently on every mongos, or behaviour depends on which router you hit. And they are useless against an attacker already inside your network range, so pair them with real network segmentation.

Which built-in roles do you reach for first, and what does each actually allow?

Four that cover most operational needs, with sharp edges worth knowing:

  • readWriteAnyDatabase: read and write on every database except admin, local and config. Convenient, and far too broad for an application: one compromised service can modify every tenant's data.
  • clusterMonitor: read-only visibility into the deployment — server status, current operations, replication status, collection and database statistics, index statistics. Note what it does not grant: it cannot read documents. A monitoring user with clusterMonitor is safe to hand out; one with readAnyDatabase is a data breach waiting for a stolen key.
  • backup: what mongodump needs, including bypassing document validation so partial or invalid documents can be read out. Read-mostly.
  • restore: the write side — inserting data and creating collections and indexes.

Use backup for the backup agent instead of giving it a read role: it is the difference between "can copy the database" and "can exfiltrate and query it".

Write a custom role for a specific application. What do you include, and what do you refuse?

Scope the resource as narrowly as the schema allows, and grant only the actions the code path performs.

db.getSiblingDB("shop").createRole({
  role: "ordersService",
  privileges: [
    { resource: { db: "shop", collection: "orders" },
      actions: ["find", "insert", "update"] },
    { resource: { db: "shop", collection: "outbox" },
      actions: ["find", "insert", "update", "remove"] },
    { resource: { db: "shop", collection: "catalog" },
      actions: ["find"] }
  ],
  roles: []
})
db.getSiblingDB("shop").createUser({
  user: "orders-svc", pwd: passwordPrompt(),
  roles: [{ role: "ordersService", db: "shop" }]
})

What I refuse: remove on orders (the service soft-deletes, so it never needs hard deletes), dbAdmin (index changes belong to a migration job), and any cluster-wide role. No createIndex, because schema changes should be a reviewed, separate principal.

Then verify the role by attempting a forbidden operation in a test — a role nobody has tried to break is a role with unknown edges.

Why is root not an operational role?

Because it is the union of everything: read and write on all databases, user and role administration, cluster administration, backup and restore. Granting it is not a permission decision, it is the absence of one.

Concretely, root breaks four things you need in production:

  • Attribution. If three people share a root-capable account, the audit log names the account, not the actor.
  • Blast radius. A stolen root credential can drop every database, rewrite users, and disable the controls you would use to detect it.
  • Separation of duties. The person who can delete data should not be the person who can erase the evidence, and with root they are the same person.
  • Safe automation. Scripts that run as root hide the moment when someone writes dropDatabase() into a maintenance job.

The replacement is a small set of named, purpose-built accounts: clusterMonitor for observability, backup/restore for the backup agent, per-database readWrite for applications, and a tightly held admin role used interactively with MFA.

How do you separate the duty to delete from the duty to audit?

By making them different principals with different credentials, different approval paths, and — ideally — different identity providers.

A workable split:

  • Application role: can insert and update, only soft-deletes. It cannot call dropDatabase or dropCollection at all, so an application bug cannot destroy a collection.
  • Destructive operations role: a named human role able to drop collections, used only through a two-person approval (change ticket, or a break-glass account whose use pages the security team).
  • Audit owner: can read and export the audit log and cannot modify data or the audit configuration. Crucially, the DBA team must not be able to turn auditing off.

The test of the design is a simple question: can the person who ran the bad command delete the record of having run it? If yes, the split is decorative. On Atlas, keep the audit log destination in an account the database administrators do not control, and export continuously rather than on demand.

dbAdmin versus userAdmin: what is the practical difference?

dbAdmin is about structure: create and drop collections and indexes, run collMod, validate, compact, read collection and index statistics, manage the plan cache. It deliberately does not grant find: a DBA can drop a collection without being able to read it, which is exactly what many compliance regimes want.

userAdmin is about identity: create, update and drop users and roles on that database, and grant or revoke roles. Here is the trap that separates a senior answer from a memorised one:

userAdmin on admin is effectively superuser. Whoever can create a user can create one with the root role, then log in as it. So userAdminAnyDatabase is not a "user management" privilege, it is a privilege-escalation path, and it must be treated with the same care as root — with MFA, review, and a very short list of holders.

Assign dbAdmin per database to the owning team; keep user administration centralised and monitored.

Internal cluster authentication: keyfile or x.509?

Both authenticate members to each other; they differ in what you are trusting.

Keyfile is a shared secret copied to every node. It is trivial to set up and it does the job, but it is a single secret with no identity: any host holding the file can join the set, every host's copy is equally powerful, and rotating it means a coordinated restart of the whole deployment.

x.509 gives each node its own certificate and key, signed by your CA. Membership is a property of the certificate identity, revocation is a CA operation, certificates can be short-lived, and rotation can be done member by member with an overlap window because the trust bundle holds both CAs. It costs you a PKI and an expiry-monitoring alert.

security:
  clusterAuthMode: x509

Use x.509 on anything with more than a handful of nodes; keep keyfiles for labs.

How do you rotate database credentials with no downtime?

Overlap, never swap. The pattern is: create the new credential while the old one still works, roll it out, verify traffic, then retire the old one after a defined window.

  1. Create a second user with the same roles (or a new password on a second principal).
  2. Publish it in the secrets manager as a new version; applications pick it up on restart or on a watcher event.
  3. Watch authentication failures during the rollout — a spike means some instance still uses the old value.
  4. After the window, delete the old user and revoke its sessions.

The subtlety: changing a password does not disconnect existing sessions. A client that authenticated an hour ago keeps working, so "we rotated it" can be false. Revoke explicitly when the credential is suspected compromised:

db.getSiblingDB("admin").runCommand({
  killAllSessionsByPattern: [{ users: [{ user: "app", db: "shop" }] }]
})

For x.509, add the new CA to the trust bundle first, then roll certificates, then remove the old CA — in that order, or you lock yourself out.

How do you manage database passwords in Atlas without it becoming a spreadsheet?

Treat Atlas database users as infrastructure, not as a UI activity. The pattern that survives audits:

  • One user per application and per environment, named after the service (orders-svc-prod), so the audit log tells you who did what.
  • Passwords generated, never chosen, stored in a secrets manager and injected at runtime — never in a connection string committed to a repository or baked into an image.
  • Defined as code through the Atlas Admin API or Terraform, so review and drift detection work the same way.
  • Admin API keys scoped by role — a read-only key for dashboards, a project owner key for the pipeline — and rotated on a schedule, with an IP access list on the key itself.

Better still, remove the static password: Atlas supports workload identity federation and IAM-based authentication, which issues short-lived credentials and makes rotation a non-event. If you can rotate a credential without a change ticket, that is the sign the design is right.

How do you audit failed authentication attempts, and what do you look for?

You have to have enabled auditing before the incident — that is the whole answer, and it is why the control is a design decision rather than a query.

With auditing on, filter for authentication events and their results. A practical filter targets the authentication action type and the failure codes, so the volume stays affordable:

{
  atype: "authenticate",
  result: { $in: [18, 13] }
}

What to look for: a burst of failures against one user followed by a success (credential stuffing that worked), failures from a new geography or ASN, failures spread across many usernames from one source (spraying), and service accounts failing — which usually means a rotation broke something rather than an attack.

Two operational notes. First, failed logins are cheap for an attacker and expensive for your pipeline, so route them to a SIEM with retention, not a local file that rotates in a day. Second, watch for the opposite signal: privileged accounts with zero logins for months, which should be disabled.

What does least privilege look like across a fleet of microservices?

Each service gets its own principal, scoped to the collections it owns, with only the operations its code performs — and no service can administer the database it depends on.

In practice:

  • Ownership boundaries. The orders service reads catalog but never writes it; if it needs catalog data changed, that is the catalog service's API, not a direct write. Otherwise every service becomes a coupling point.
  • Roles as code. Custom roles live beside the service, reviewed like code, applied by the pipeline.
  • No shared "app" user. Distinct users are what make the audit log readable and revocation surgical.
  • A separate migration principal. Index and validator changes need more privilege than runtime traffic; make a job hold it for the minutes it runs, not the service for its lifetime.
  • Dev and prod separated at user, project and network level.

The failure mode: least privilege nobody can operate. If adding a field needs a ticket, teams share one user within a quarter.

Why is one shared credential across services such a serious problem?

Because it destroys every property you rely on during an incident.

  • Attribution disappears. The audit log says appUser dropped the collection, and now five teams are suspects. You cannot answer "who" or "which deployment".
  • Revocation is an outage. The credential is compromised, but rotating it means coordinating every consumer at once, so in practice nobody rotates it.
  • Blast radius is total. The union of every service's needs becomes the permission set of each service.
  • Least privilege becomes impossible, since the shared role must satisfy the most demanding consumer.
  • Detection fails. Anomalous access is normal access: the credential legitimately touches every collection at every hour.

The migration is unglamorous but cheap: enumerate consumers from the audit log, create a user per consumer with the observed access pattern, deploy them one at a time, then disable the shared account and watch what breaks. Doing that once is far cheaper than doing it during a breach.

It is Monday and a collection is gone. How do you determine who dropped it?

It depends entirely on what was enabled before the event. Say that first, because it is the honest answer.

  • Audit log: the authoritative source. With auditing configured to capture authorization checks, you get the principal, the source address, the command and the timestamp for dropDatabase or dropCollection. On Atlas, database auditing exports to your own storage, which is your protection against log tampering.
  • In-flight only: $currentOp exposes effectiveUsers, but only while an operation runs — useless after the fact.
  • Profiler: system.profile entries carry the authenticated user, but the collection is capped and filtered by slowms, so it is diagnostic, not evidentiary.
  • Change streams and the oplog: they record what happened, not who — the drop appears as an event with no principal.

Conclusion to state plainly: if auditing was off, you can reconstruct the sequence but not the actor, and the fix is a configuration change plus retention in a system the DBAs cannot edit.

How does encryption at rest get its keys, and what changes when you bring your own?

WiredTiger's native encryption uses a two-level scheme: a master key held outside the database, and data keys that encrypt the actual files. The master key never touches the data directory; it lives in a keyfile, in a KMIP server, or — on Atlas — in your cloud KMS.

With a KMIP deployment, mongod authenticates to the key server with a client certificate, fetches and unwraps the data keys at startup, and keeps them in memory. That means the KMS is on the critical path for every restart: if the nodes cannot reach it, they do not start.

Bring-your-own-key on Atlas means the project's data keys are wrapped by a key in your KMS account, with Atlas granted access through an IAM role. It buys revocation and a key-usage audit trail, and it costs a new dependency: KMS downtime becomes database downtime, and revoking the key breaks restores too.

What happens when you rotate the master key, and how is that different from rekeying the data?

Two operations that get conflated constantly.

Rotating the master key only re-wraps the existing data keys: the ciphertext of your collections is untouched, so it is fast, online and low-risk. In a KMS you create a new key version, point the deployment at it, and the nodes re-wrap. The old version must stay enabled until everything has been re-wrapped, otherwise you cannot start a node that still holds an old-wrapped key. On Atlas the equivalent is rotating the customer-managed key and updating the cluster's key configuration.

Rekeying means generating new data keys and re-encrypting the data itself. That rewrites the dataset — I/O heavy, and it must keep reading old keys throughout. Plan it as a project with a verified backup, never as a 2 a.m. runbook step.

Interview point: rotation frequency is policy; the ability to rotate is design. Test it before you need it.

Volume-level encryption or MongoDB's native encryption — which do you deploy?

Both, and for different reasons.

Volume encryption (LUKS, cloud provider disk encryption, SAN-level) protects the physical medium: a decommissioned disk, a stolen drive, an abandoned snapshot. It is transparent to MongoDB, costs almost nothing in performance, and covers everything on the host — logs, temporary files, other software. Its limit: it stops protecting anything once the OS runs — anyone with a shell on that host, or the cloud role that can attach the disk, reads plaintext.

Native encryption encrypts the data files and journal inside the storage engine, with keys that are not on the disk. It gives you per-deployment keys, independent rotation, and a real barrier against "I mounted the volume" and "I restored the snapshot into my own account".

Neither protects against a valid database user running a query. Choose native where the threat model includes insiders or shared storage; keep volume encryption because it is cheap and covers the files MongoDB does not manage.

CSFLE explicit versus automatic: when do you choose each?

Same cryptography, different control surface.

Explicit encryption means the application calls the client-side encryption library itself to encrypt a value and store the binary; decryption is also explicit. Nothing is transparent, and you get full control: encrypt on one code path only, use a different data key per tenant, handle values arriving from a queue, encrypt something you will never query. The cost is that every read path must remember to decrypt and every write path to encrypt.

Automatic encryption declares the rules in a JSON schema attached to the collection, and the driver encrypts on write and decrypts on read without application changes. Much harder to get wrong, but the schema is stored server-side (field names and algorithms visible), must be known to every client, and unsupported operations fail at runtime rather than design time.

Default to automatic; use explicit when a single field needs different handling in different services, or when the encrypted value never leaves one component.

Queryable Encryption: what can you query on an encrypted field, and what is still off limits?

You declare, per field, which query types the server should support, and you pay in index size and write cost for each one you enable.

  • Equality: $eq, $in and the equivalent find filters, for strings and most BSON types.
  • Range: $gt, $gte, $lt, $lte on numeric and date fields, with bounds and precision you choose — a direct trade-off between index size and accuracy.
  • Prefix, suffix and substring matching on strings (9.0): "starts with" and "contains" searches that previously required client-side decryption.

Still off limits: sorting on the field, regular expressions beyond the supported substring types, $expr and computed predicates, joins and $lookup matching on encrypted values, and unique constraints on a randomly encrypted field. Aggregation stages that need plaintext arithmetic or ordering do not work either.

The design rule: encrypted fields are for lookup, not analysis. If a field must be sorted and grouped freely, it should not be the encrypted one.

Why can't you sort by a Queryable Encryption field?

Because sorting is an ordering operation, and ordering is exactly the information the encryption is designed to hide.

Range queries work through an encoded structure that lets the server test membership in the client's predicate without learning the value. That supports matching, not a total order: the server cannot compare two encrypted values, and its index is not ordered by plaintext. If it could sort, an attacker could read the approximate distribution of salaries or ages straight off index order — the leakage deterministic encryption already suffers, with better manners.

The practical workarounds:

  • Sort client-side after decryption, so pagination and limits move to the application.
  • Sort by an unencrypted field — createdAt truncated to the day, a sequence number, or the _id.
  • Model it: keep the sensitive value encrypted and a coarse, deliberately lossy sort key in plaintext, and be explicit about what that leaks.

Never "fix" this by storing a second plaintext copy; that removes the control entirely.

What do encrypted indexes cost you?

More than a normal index, in three currencies.

Space. Queryable Encryption maintains metadata structures alongside your collection plus internal collections holding the index state. Add per-field metadata padding and the result is commonly two to three times the storage of the equivalent plaintext index, replicated like any other data.

Write amplification. Each insert or update that touches an encrypted field updates the encrypted index structures too, so a single logical write becomes several internal writes. On a write-heavy collection this shows up as higher latency and more oplog volume, which in turn shortens your oplog window — a security feature that quietly reduces your recovery capability.

Operational complexity. These internal collections are real data: they must be included in backups, they inflate restore times, and dropping or filtering them out of a dump leaves the collection queryable in theory and broken in practice. Enabling a query type on a large existing collection is a backfill, not a toggle.

Encrypted fields inside aggregation pipelines: what actually works?

Pipelines work as long as the server never needs to understand the plaintext.

What works: a $match using a supported query type on the encrypted field, because the driver rewrites the predicate into the encrypted form and the server evaluates it against the encrypted index. Everything around it — filtering on unencrypted fields, projecting, counting, unwinding arrays of unencrypted subdocuments — is unaffected.

What breaks: $group keyed on an encrypted field, $sort on it, $bucket, range-based $facet bucketing, arithmetic such as $sum or $avg over it, and $lookup joins that match encrypted to encrypted. The server either rejects the stage or returns ciphertext that cannot be compared.

The pattern that works is to aggregate on unencrypted dimensions and decrypt only the small result set client-side — for example group by region and month, return the encrypted salary values, and compute averages in the application after explicit decryption. That keeps the sensitive values protected and moves the analytics to a place you control.

For each encryption layer, what does it protect and what does it not?

Layer by layer:

  • Volume encryption: protects stolen disks, abandoned cloud snapshots and physical media. Does not protect against a running host, a mounted volume, or any user with credentials.
  • Native encryption at rest: protects data files and journal against filesystem access and snapshot restore into another account. Does not protect against a compromised mongod or an authorised query.
  • TLS in transit: protects against interception on the wire. Does not protect the endpoints, and is worthless if the client skips verification.
  • CSFLE / Queryable Encryption: protects field values from administrators, a compromised server, and backups. Does not protect against a compromised application holding the keys, and does not hide metadata: field names, counts, sizes, timing and access patterns remain visible.

What no layer protects: an authorised user reading data they are entitled to see, or a service that holds the keys and is itself the breach. Encryption changes who must be compromised; it never makes the system safe.

TLS in transit: which settings actually matter, and where do teams get it wrong?

Three things matter: the protocol floor, the certificate chain, and whether the client verifies it.

net:
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/ssl/mongod.pem
    CAFile: /etc/ssl/ca.pem
    disabledProtocols: TLS1_0,TLS1_1

Set requireTLS, not "prefer" — opportunistic TLS means a misconfigured client silently downgrades. Disable TLS 1.0 and 1.1 so the floor is 1.2 or 1.3. Atlas enforces modern TLS for you, which is a reason to prefer private endpoints over hand-rolled tunnels.

Where teams get it wrong is the client: tlsAllowInvalidCertificates and tlsInsecure turn off hostname and chain validation, which converts TLS into obfuscation and makes man-in-the-middle trivial. The second mistake is OCSP: revocation checking is good, but if the responder is unreachable and the client is strict, connections fail — decide deliberately whether to soft-fail. The third is certificate expiry: monitor it, because an expired node certificate takes down a replica set as effectively as a disk failure.

What is wrong with storing the encryption key next to the data?

It reduces encryption to an encoding step: whoever obtains the ciphertext almost always obtains the key in the same movement.

The familiar versions of this mistake: the keyfile in the same backup bucket as the dump; the KMS key in the same account, administered by the same role as the database; the data key in an environment variable on the database host; the passphrase in the deployment repository "so the runbook works".

Each one collapses the threat model. Ransomware that reads the backup reaches the key. An administrator who can read files can also read the key.

The separation you want is organisational as much as technical: key material in an HSM or a KMS account that database administrators cannot read, an IAM policy denying decryption to the database role, key usage alerted on, and an escrow copy held by another team. Then a stolen backup is genuinely useless — which is the entire point of encrypting it.

How does encryption interact with backups and restores?

Four separate concerns that people treat as one.

  • The artifact. A backup is a copy of your data with different access controls, so it needs its own encryption: encrypt dumps before they leave the host, and storage-side encryption with a separate key for the bucket. Database-level encryption does not secure an exported logical dump: mongodump writes plaintext BSON unless you encrypt the stream.
  • The key at restore time. A restored volume or Atlas cluster needs the same key available. If the key is region-bound and your DR region is elsewhere, the backup you shipped there cannot be opened.
  • Privilege. Restoring encrypted data does not require decrypting it at the storage level, but application-level encryption does: the clients need key access to read the restored fields, so key access is part of the DR runbook.
  • Internal metadata. For Queryable Encryption, the internal index collections must be in the backup. A restore that includes only the user collection produces data nobody can query.

Why is bindIp: 0.0.0.0 so often the first line of an incident report?

Because it is the shortest path from "the container cannot connect" to "the database is on the internet". Binding the wildcard makes mongod listen on every interface, including the public one; it is usually done to fix a test-environment connection and then copied into a template.

net:
  bindIp: 127.0.0.1,10.20.4.11   # never 0.0.0.0 in production

What follows is predictable: scanners sweep for open database ports within hours, and if authentication is missing, the collection is dropped and replaced with a ransom note. Even with authentication it absorbs credential stuffing and becomes a denial-of-service target, since mongod spends CPU on unauthenticated handshakes.

The correct pattern: bind the private interface explicitly, keep the cluster behind a security group that only application subnets can reach, and expose it externally only through a private endpoint or a bastion with MFA. A container's 127.0.0.1 is not the host's, which is why people reach for the wildcard; fix it with container networking, not by opening the port.

Private endpoints versus VPC peering in Atlas: how do you choose?

Both remove the public internet from the path; they differ in who owns the plumbing.

Private endpoints (AWS PrivateLink, Azure Private Link, GCP Private Service Connect) create a one-directional connection to a specific service. You get an endpoint in your own VPC, traffic stays on the provider backbone, the cluster has no public address, and CIDR overlap is not your problem. The cost is per-endpoint, per-region, plus DNS: resolution must return the private addresses, or the driver resolves the public ones.

Peering connects whole networks, so anything routable can talk to anything routable — convenient when many services need many clusters, dangerous for the same reason: the blast radius of a compromised host is the entire peered range. It also needs non-overlapping CIDRs and route maintenance.

Default to private endpoints for application traffic; use peering when you need many-to-many connectivity and have the discipline to segment it. Either way keep the IP access list: a second, independent gate.

IP access list or VPC peering — isn't one of them enough?

No, because they answer different questions. The access list answers "which source addresses may attempt a connection"; peering answers "is there a network path at all".

Their weaknesses are complementary. An access list is satisfied by any host inside an allowed range, and it breaks constantly for teams with dynamic egress addresses, which is how 0.0.0.0/0 ends up in production. Peering gives you privacy but not authorization: every host in the peered VPC can reach the cluster and must still authenticate, so a single leaked credential is still enough.

The layered answer for a production cluster: private endpoint or peering so the cluster has no public route, an access list restricted to the specific application subnets, authentication with per-service users, and authorisation scoped per database. Disable public access entirely if your tier allows it, then test from outside to prove it is closed — a control nobody verified is a control you do not have.

TLS is mandatory. Why do you still have to verify the certificate?

Because encryption without identity verification protects you from eavesdropping and not from impersonation. A client that skips validation will happily establish an encrypted session with whoever answers on that address — which is exactly what a man-in-the-middle wants: the attacker terminates TLS, reads plaintext, and re-encrypts to the real server.

The specific failures to name:

  • tlsAllowInvalidCertificates and tlsAllowInvalidHostnames disable chain and name checks. They exist for labs; in production they are a finding.
  • Trusting a CA bundle that includes a widely used public CA instead of your own, so any certificate from that CA is accepted.
  • Connecting by IP when the certificate has a DNS name, then "fixing" it by disabling hostname checks.
  • Terminating TLS at a proxy and speaking plaintext to mongod on the internal network, which moves the trust boundary without documenting it.

Mandatory TLS means every hop, including mongos to shards and member-to-member replication, uses requireTLS — and every client validates against the CA you control.

Is moving off port 27017 a security measure?

No. It is noise reduction at best, and usually self-deception.

Port scanning is cheap and exhaustive: an attacker who reaches your network scans all ports, not a list of well-known ones, and a MongoDB handshake on port 4711 is recognised in one packet. Changing the port removes you from the least sophisticated mass scanners, which feels like progress and changes nothing about the actual exposure.

Worse, it has real costs. mongodb+srv discovery, Atlas, most drivers' defaults, monitoring agents, backup tools and runbooks all assume the standard port; a non-standard port becomes a configuration detail that gets missed during an incident, and the first symptom is a driver timeout that looks like a network failure.

If somebody proposes it as a hardening measure, redirect the conversation to what actually reduces risk: authentication enabled, network path closed, least-privilege users, TLS with verification, audit logging. Security by obscurity can be a thin extra layer; it must never be the layer you are counting on.

In a sharded cluster, why should clients never reach the shards directly?

Because mongos is not just a proxy — it owns the routing logic and the chunk metadata contract. A client that connects straight to a shard bypasses both.

The consequences:

  • Orphaned documents. Writes that skip the router do not update chunk bookkeeping, so after a migration a shard holds documents it no longer owns and mongos will not see them consistently.
  • DDL inconsistency. Creating an index or a collection on one shard directly leaves the others different, and sharded collection creation is cluster-wide.
  • Broken invariants. Unique constraints and transactions rely on the router coordinating participants; direct access violates them.
  • Wider attack surface. Every shard becomes a reachable database.

The design rule: only mongos endpoints are reachable from application subnets; shards and config servers live in a private tier whose security groups accept traffic only from routers and each other. In Atlas that is the cluster endpoint and nothing else.

How do you design firewall rules and egress policy for a database tier?

Ingress is the part everyone does; egress is where mature designs differ.

Ingress: default deny, then explicit allows from named application security groups to the database port, referenced by group so instances can scale. No allow from 0.0.0.0/0, none from the office range "temporarily", none between database nodes and the general application subnet.

Egress: default deny with an allow-list for what the database genuinely needs — key management, the backup target, the monitoring collector, and the directory or KDC if you use one. This is the control that limits exfiltration: a compromised mongod that cannot open outbound connections cannot ship your data anywhere or be commanded remotely.

The trap: overly tight egress breaks a control you forgot about — the KMIP server, the NTP source, the package mirror — and the outage lands at the worst time. Document every exception with an owner, and use flow logs to prove the rules do what you think.

What does network least privilege look like for BI and analytics teams?

Analytics is the classic path for an analyst to export the whole customer table. The controls are layered:

  • Separate path. BI tools connect from a dedicated analytics subnet through its own private endpoint or peering, not through the application's network segment.
  • Separate principal. A read-only user scoped to specific databases or, better, to a set of views that expose aggregated or masked data instead of raw PII. Not readAnyDatabase.
  • Separate capacity. Analytics reads go to a dedicated secondary or a separate cluster fed by change streams, so a runaway aggregation cannot starve production.
  • Guardrails on the query. Enforce maxTimeMS at the client, forbid unbounded scans on tier-1 data through views and projections, and give analysts a cluster they can restart themselves.

The design principle: an analyst should answer the question without holding a credential that reads raw customer records. If the only path to a report is a production connection string, the network was never the control.

security.javascriptEnabled and $where: what is the actual risk?

Server-side JavaScript runs arbitrary code inside the database process, per document, on data the client chose. Three distinct problems:

  • Injection. If a $where string is assembled from user input, an attacker is no longer injecting a query operator — they are injecting code that the server executes. String concatenation into $where is as bad as SQL string concatenation.
  • Cost. A JavaScript predicate cannot use an index, so it is evaluated against every candidate document, and a pathological expression can pin a CPU core for the duration.
  • Attack surface. The interpreter is a large piece of native code reachable from an authenticated session.

The default posture for a production deployment is to turn it off unless a workload genuinely needs it:

security:
  javascriptEnabled: false

That disables $where, $function, $accumulator and mapReduce, pushing those computations into the application where they belong. If you must keep it enabled for one legacy pipeline, that is a documented exception with a migration date.

Which endpoints may face the internet, and which must never?

In a well-built deployment, the answer is "the application's HTTPS load balancer, and nothing else".

May be exposed, with care: a public API gateway in front of the application; a public web endpoint that never speaks the database protocol; a managed private endpoint that only looks public to your own VPC.

Must never be exposed: any mongod or mongos port to 0.0.0.0/0; shard and config server ports even to the application tier; the backup bucket; the key management endpoint from the database subnet beyond the specific API; monitoring agents' admin interfaces; and any tool that grants shell or query access, including "just for the analyst" direct connections.

For human access: a bastion or session-manager tunnel behind SSO with MFA, plus per-person accounts so the audit log has names in it. If you open a cluster temporarily for a demo, put an expiry on the rule — the incidents that matter start with a rule someone forgot to remove.

Give me your security checklist before a cluster is declared production-ready.

I would sign off in five groups.

Identity: authorisation enabled; SCRAM-SHA-256 only, no SHA-1 fallback; one user per service with a custom least-privilege role; no shared or root-equivalent application account; administrative access named, MFA-protected, and separate from data access.

Network: private endpoint or peering; cluster has no public route; access list restricted to application subnets; TLS required with verified certificates; egress allow-listed.

Data: encryption at rest with keys outside the database account; field-level encryption for the regulated fields; backups encrypted, cross-region, retention defined and immutable where required.

Detection: audit log enabled and exported where DBAs cannot edit it; alerts on failed authentications, backup failures, oplog window, and unusual privilege changes.

Recovery: PITR window at least equal to the RPO, a restore drill completed and timed, the DR runbook with named decision makers, and one documented answer to "who approves destroying writes to recover".

Anything you cannot demonstrate with evidence is not a control yet — it is an intention.

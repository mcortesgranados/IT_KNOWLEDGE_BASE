How do I ship a $jsonSchema validator to a live collection with no downtime?

Keep the schema in a $jsonSchema validator on the collection, not only in application code. Build the rule set, attach it with collMod using validationLevel: "moderate" and validationAction: "warn", watch the log for a day, then flip only validationAction to "error" with a second collMod. Warn mode lets every write through and logs a validation warning, so you learn which writers break the schema before you enforce it. moderate still validates inserts and valid documents on update, but tolerates already-invalid documents.

// mongosh
const validator = {
  $jsonSchema: {
    bsonType: "object",
    required: ["sku", "price", "status"],
    additionalProperties: false,
    properties: {
      _id:     { bsonType: "objectId" },
      sku:     { bsonType: "string", minLength: 3 },
      price:   { bsonType: "decimal", minimum: 0 },
      status:  { bsonType: "string", enum: ["draft", "active", "retired"] },
      tags:    { bsonType: "array", items: { bsonType: "string" } }
    }
  }
};

// 1) deploy in warn mode - writes still succeed, violations are logged
db.runCommand({
  collMod: "products",
  validator: validator,
  validationLevel: "moderate",
  validationAction: "warn"
});

// 2) after the log is clean, enforce without rewriting anything
db.runCommand({ collMod: "products", validationAction: "error" });

// rollback is one command away
db.runCommand({ collMod: "products", validator: {}, validationLevel: "off" });

Trap: collMod never re-validates existing documents, so old garbage survives until it is touched; and additionalProperties: false instantly rejects any writer that adds a field, which is the single most common cause of a "validator broke production" incident.

How do I build an ESR index for an equality + sort + range query, and prove it with explain?

Order the keys by Equality, then Sort, then Range. Given a filter on status, a range on total and a sort on createdAt descending, the index is { status: 1, createdAt: -1, total: 1 }. Equality first pins the scan to one prefix, the sort key next lets the index deliver rows already ordered (no blocking SORT stage, so limit can stop early), and the range field last filters inside that prefix. Run explain("executionStats") before and after and compare the same three numbers instead of eyeballing the plan.

// mongosh
const q = { status: "shipped", total: { $gte: 100 } };
const s = { createdAt: -1 };

// BEFORE: no index - every document is read, then sorted in memory
db.orders.find(q).sort(s).limit(20).explain("executionStats");
// winningPlan: COLLSCAN + SORT | totalDocsExamined: 1240881 | nReturned: 20

db.orders.createIndex({ status: 1, createdAt: -1, total: 1 }, { name: "esr_status_created_total" });

// AFTER: IXSCAN - bounded keys, no SORT, early exit at 20
const e = db.orders.find(q).sort(s).limit(20).explain("executionStats");
printjson({
  keys: e.executionStats.totalKeysExamined,   // ~20
  docs: e.executionStats.totalDocsExamined,   // ~20
  returned: e.executionStats.nReturned,       // 20
  ms: e.executionStats.executionTimeMillis,
  plan: e.queryPlanner.winningPlan.stage
});

Trap: swapping sort and range ({ status: 1, total: 1, createdAt: -1 }) forces an in-memory sort of every matching document, so limit: 20 no longer bounds the work - totalKeysExamined explodes while nReturned stays at 20.

How do I use $lookup with pipeline and let to join only matching foreign documents?

The short localField/foreignField form always returns every match and then you filter. The pipeline form gives you a sub-query per outer document: pass outer values in through let, read them inside as $$ variables, and filter before anything is attached. Put the join equality alone in an $expr $eq so the planner can use the foreign index, then apply constant predicates in a normal $match, and finish with $project and $limit. That makes it a conditional join plus a top-N, at the cost of one indexed lookup per input document.

// mongosh - customers join on a business key, not _id
db.customers.createIndex({ externalId: 1, tier: 1 }, { name: "lk_external_tier" });

db.orders.aggregate([
  { $match: { status: "paid" } },
  { $lookup: {
      from: "customers",
      let: { cid: "$customerRef", wantedTier: "gold" },
      pipeline: [
        { $match: { $expr: { $eq: ["$externalId", "$$cid"] } } },  // indexable
        { $match: { tier: "$$wantedTier" } },                      // literal is fine
        { $project: { _id: 0, name: 1, tier: 1 } },
        { $limit: 1 }
      ],
      as: "customer"
  } },
  { $match: { "customer.0": { $exists: true } } }   // INNER JOIN semantics
]);

Trap: a $$ variable inside a plain $match is illegal unless wrapped in $expr, and any extra $expr predicate on a computed expression kills the index pushdown - the sub-pipeline then degrades to a collection scan repeated once per order.

How do I paginate by _id cursor and return a nextCursor from an API?

Never use skip for deep pages: it walks and discards every preceding document, and it drifts when rows are inserted. A keyset cursor asks for "everything after the last key I saw", which is an index seek of exactly limit documents. Request one extra row to know whether a next page exists, then hand back the cursor of the last row you actually return. Encode the cursor opaquely so clients cannot forge or reorder it, and validate its shape before casting, otherwise a malformed value becomes a server error.

// Node driver 6.x
async function page(cursorStr, limit = 20) {
  const filter = {};
  if (cursorStr) {
    const raw = Buffer.from(cursorStr, "base64url").toString("utf8");
    if (!/^[0-9a-f]{24}$/.test(raw)) throw new Error("bad cursor");
    filter._id = { $gt: new ObjectId(raw) };
  }
  const rows = await coll.find(filter).sort({ _id: 1 }).limit(limit + 1).toArray();
  const hasMore = rows.length > limit;
  const items = hasMore ? rows.slice(0, limit) : rows;
  const last = items[items.length - 1];
  return {
    items,
    nextCursor: hasMore ? Buffer.from(last._id.toHexString()).toString("base64url") : null
  };
}

Trap: this cursor is bound to the sort key - if you sort by { createdAt: -1 } you must paginate on the compound tuple { createdAt, _id } with a matching compound index, or documents that share a timestamp get silently skipped or repeated at page boundaries.

How do I run a multi-document transaction with retries on TransientTransactionError?

Take a session, wrap the unit of work in session.withTransaction() and set readConcern: snapshot plus writeConcern: w: "majority". MongoDB generates the transaction number for you and the driver already wraps the callback in the two retry loops that matter: the whole callback is re-run when the error carries the TransientTransactionError label (a write conflict, a primary stepdown), and commitTransaction alone is retried when the error carries UnknownTransactionCommitResult - because a commit that timed out may still have succeeded. Every operation inside the callback must receive the session, and the callback must be safe to run twice.

// Node driver 6.x
const session = client.startSession();
try {
  await session.withTransaction(async function () {
    await accounts.updateOne(
      { _id: "acct-1", balance: { $gte: 100 } },
      { $inc: { balance: -100 } },
      { session }
    );
    await accounts.updateOne(
      { _id: "acct-2" },
      { $inc: { balance: 100 } },
      { session }
    );
    await ledger.insertOne(
      { from: "acct-1", to: "acct-2", amount: 100, at: new Date() },
      { session }
    );   // aborts the txn when the debit matched 0 documents
  }, {
    readConcern: { level: "snapshot" },
    writeConcern: { w: "majority" },
    maxCommitTimeMS: 5000
  });
} finally {
  await session.endSession();
}

// if you drive the session by hand, keep this commit loop
async function commitWithRetry(session) {
  for (;;) {
    try { await session.commitTransaction(); return; }
    catch (e) {
      if (e.hasErrorLabel("UnknownTransactionCommitResult")) continue;
      if (e.hasErrorLabel("TransientTransactionError")) throw e; // re-run callback
      throw e;
    }
  }
}

Trap: transactions need a replica set or sharded cluster, die at 60 seconds by default, and cannot contain $out or $merge; side effects such as sending mail must happen after the commit, never inside the retried callback.

How do I resume a change stream from the last persisted token after a restart?

Each change event carries a resume token in _id. Persist that token after you process the event, then open the stream with resumeAfter on the stored token: MongoDB replays from the next event. Persisting after processing gives at-least-once delivery, so make the handler idempotent with an upsert keyed by the event's document key plus the token. Use startAfter instead when the previous stream ended with an invalidate event, since resumeAfter refuses a token from a stream that was invalidated. Keep the token write in the same transaction or the same idempotent step as the effect whenever the action is not naturally repeatable.

// Node driver 6.x
const ops = client.db("ops").collection("streamState");
const saved = await ops.findOne({ _id: "orders-watch" });

const stream = orders.watch(
  [{ $match: { operationType: { $in: ["insert", "update", "replace", "delete"] } } }],
  saved
    ? { resumeAfter: saved.token, fullDocument: "updateLookup" }
    : { fullDocument: "updateLookup" }
);

for await (const change of stream) {
  await applyIdempotently(change);                    // effect first
  await ops.updateOne(
    { _id: "orders-watch" },
    { $set: { token: change._id, seenAt: new Date() } },
    { upsert: true }
  );                                                  // then the checkpoint
}

// on startup again: the stream opens one event after the stored token

Trap: the token is only valid inside the oplog window of the same deployment - after a long outage the resume fails with ChangeStreamHistoryLost and you must fall back to a snapshot plus a timestamp, so monitor the oplog window against your maximum downtime.

How do I expire documents after N days and change the TTL later without rebuilding the index?

A TTL index on a date field makes mongod's background TTL monitor delete documents once expireAfterSeconds has elapsed since that date. Use a fixed window (604800 for seven days) on a createdAt field, or expireAfterSeconds: 0 on a per-document expiresAt field, which lets each document carry its own deadline. Since MongoDB 7.0 you can change the window in place with collMod and index.keyPattern - the index keeps its name and build, no drop and recreate, no downtime - and you can park the index entirely by setting expireAfterSeconds: "off".

// mongosh
// fixed 7-day window
db.sessions.createIndex(
  { createdAt: 1 },
  { name: "ttl_createdAt", expireAfterSeconds: 604800 }
);

// per-document deadline, set by the writer
db.tokens.createIndex(
  { expiresAt: 1 },
  { name: "ttl_expiresAt", expireAfterSeconds: 0 }
);

// change the window in place - no rebuild, no downtime
db.runCommand({
  collMod: "sessions",
  index: { keyPattern: { createdAt: 1 }, expireAfterSeconds: 2592000 }
});

// pause / resume deletion without touching data
db.runCommand({
  collMod: "sessions",
  index: { keyPattern: { createdAt: 1 }, expireAfterSeconds: "off" }
});

db.sessions.getIndexes().find(function (i) { return i.name === "ttl_createdAt"; });

Trap: the monitor wakes about every 60 seconds and deletes in the background, so expiry is eventual and never a scheduler; a TTL index must be single-field on a date (or an array of dates) and cannot be compound or on _id, so a compound "expire by tenant" index silently does nothing.

How do I run a mixed bulkWrite and read the per-operation errors?

bulkWrite sends many operations in one round trip and accepts insertOne, updateOne, updateMany, replaceOne and deleteOne/deleteMany in the same array. With ordered: false the server executes all operations and reports failures per index instead of aborting at the first one. The driver still throws MongoBulkWriteError, and the useful data lives in err.writeErrors (each with index, code, errmsg) alongside the partial result counts, so a duplicate key on operation 2 does not hide the successful upserts on operations 1 and 3.

// Node driver 6.x
try {
  const res = await items.bulkWrite([
    { insertOne:  { document: { _id: 1, sku: "A-1", qty: 5 } } },
    { updateOne:  { filter: { _id: 2 }, update: { $set: { qty: 7 } } } },
    { updateOne:  { filter: { sku: "A-3" },
                    update: { $set: { qty: 0 }, $setOnInsert: { createdAt: new Date() } },
                    upsert: true } },
    { replaceOne: { filter: { _id: 4 }, replacement: { sku: "A-4", qty: 1 } } },
    { deleteOne:  { filter: { _id: 5 } } }
  ], { ordered: false });

  console.log(res.insertedCount, res.matchedCount, res.modifiedCount,
              res.upsertedCount, res.upsertedIds);
} catch (e) {
  if (!e.writeErrors) throw e;              // real connection / auth failure
  for (const we of e.writeErrors) {
    console.error(we.index, we.code, we.errmsg);   // index = position in the array
  }
  console.log("applied before failure:", e.result);
}

Trap: writeErrors[].index is the position in your operation array, not a document identifier, so keep an id array alongside the ops to map failures back; and ordered: false means a retried batch can re-apply operations that already succeeded, so the ops themselves must be idempotent.

How do I turn explain("executionStats") into a repeatable diagnosis routine?

Read four numbers, not the pretty tree: totalKeysExamined, totalDocsExamined, nReturned and executionTimeMillis, plus whether the winning plan contains a COLLSCAN or a blocking SORT stage. For a selective query all three counts should be close to each other. Alert when docsExamined / nReturned is above roughly 1.2 (the index is not filtering), when keysExamined / nReturned is above 10 (poor prefix or a range that scans), when a SORT stage appears with a small limit, or when latency crosses the endpoint's p95 budget. Wrap it in one function so every slow endpoint is measured the same way.

// mongosh
function diagnose(coll, filter, sort, limit) {
  const e = coll.find(filter).sort(sort).limit(limit).explain("executionStats");
  const st = e.executionStats;
  const plan = JSON.stringify(e.queryPlanner.winningPlan);
  const r = function (a, b) { return b === 0 ? null : Number((a / b).toFixed(2)); };
  const out = {
    plan: plan.includes("COLLSCAN") ? "COLLSCAN"
        : plan.includes("IXSCAN")   ? "IXSCAN" : "OTHER",
    blockingSort: plan.includes('"SORT"'),
    nReturned: st.nReturned,
    keysExamined: st.totalKeysExamined,
    docsExamined: st.totalDocsExamined,
    docsPerRow: r(st.totalDocsExamined, st.nReturned),   // alert if > 1.2
    keysPerRow: r(st.totalKeysExamined, st.nReturned),   // alert if > 10
    ms: st.executionTimeMillis,
    rejected: e.queryPlanner.rejectedPlans.length
  };
  out.verdict = out.plan === "COLLSCAN" ? "missing index"
              : out.blockingSort && limit < 1000 ? "sort not covered by index"
              : out.docsPerRow > 1.2 ? "index not selective enough"
              : "ok";
  return out;
}
diagnose(db.orders, { status: "shipped", total: { $gte: 100 } }, { createdAt: -1 }, 20);

Trap: explain is a plan inspection, not a benchmark - it runs on the current plan cache, excludes network and cursor batching, and truncates stats at limit, so a "20 keys examined" plan can still be a bad plan for a 20k-row scan.

How do I write an idempotent upsert that cannot duplicate under concurrency?

An upsert is read-then-write, so two concurrent callers can both miss and both insert. The only real guarantee is a unique index on the natural key: then the loser of the race gets a duplicate-key error E11000 instead of a second document, and you retry as a plain update. Keep the filter as an equality on that unique key, put mutable fields in $set and creation-only fields in $setOnInsert, and treat code 11000 on an upsert as "someone else won, apply the update". This makes the operation idempotent: running it once or five times leaves the same single document.

// Node driver 6.x
await users.createIndex({ externalId: 1 }, { unique: true, name: "uniq_externalId" });

async function upsertUser(doc) {
  const key = { externalId: doc.externalId };
  const patch = { $set: { email: doc.email, name: doc.name },
                  $setOnInsert: { createdAt: new Date(), logins: 0 } };
  try {
    await users.updateOne(key, patch, { upsert: true });
  } catch (e) {
    if (e.code !== 11000) throw e;             // lost the insert race
    await users.updateOne(key, { $set: { email: doc.email, name: doc.name } });
  }
}

Trap: the filter must be equality-only and must cover the unique key - an upsert whose filter uses $gt or a missing key builds a document from the query and can insert a row that violates the index; and a field in both $set and $setOnInsert is a hard error, not a merge.

How do I return page, total and filter facets in a single $facet aggregation?

$facet takes one input stream and runs several sub-pipelines over it, returning one document with a field per sub-pipeline. That collapses four round trips (rows, count, brand facets, price buckets) into one request, and every facet sees exactly the same snapshot. Put the shared filters in a single $match before $facet, then add the sort, skip and limit only inside the items branch: the total and the facets must count the whole filtered set, not the returned page.

// mongosh
db.products.aggregate([
  { $match: { status: "active", category: { $in: ["shoes", "bags"] } } },
  { $facet: {
      items: [
        { $sort: { createdAt: -1, _id: -1 } },
        { $skip: 40 },
        { $limit: 20 },
        { $project: { name: 1, price: 1, brand: 1 } }
      ],
      total: [ { $count: "value" } ],
      byBrand: [
        { $group: { _id: "$brand", n: { $sum: 1 } } },
        { $sort: { n: -1 } },
        { $limit: 10 }
      ],
      priceBuckets: [
        { $bucket: { groupBy: "$price", boundaries: [0, 50, 100, 500],
                     default: "500+", output: { n: { $sum: 1 } } } }
      ]
  } }
]);
// total[0].value is the filtered count; 0 when the branch returns nothing

Trap: all facet output is assembled into a single BSON document, so the combined result must stay under 16 MB and a facet returning thousands of buckets fails the whole query; $out, $merge and $geoNear are not allowed inside a facet, and each branch re-reads the input, so cost is the sum of the branches.

How do I create a weighted text index and sort by $meta textScore?

A text index tokenizes the listed string fields, applies stemming and stop words, and lets $text match whole terms with phrase, negation and OR syntax. Weights bias the score per field, so a hit in title outranks the same hit in body. Project the score with { $meta: "textScore" } and sort by that same expression - MongoDB can sort on the computed score without a blocking stage. Use it for relevance ranking on modest corpora; reach for Atlas Search when you need fuzzy matching, autocomplete or per-field analyzers.

// mongosh
db.articles.createIndex(
  { title: "text", tags: "text", body: "text" },
  { name: "article_text",
    weights: { title: 10, tags: 5, body: 1 },
    default_language: "english" }
);

db.articles.find(
  { $text: { $search: "\"connection pool\" -timeout" } },
  { title: 1, score: { $meta: "textScore" } }
).sort({ score: { $meta: "textScore" } }).limit(10);

// relevance inside an aggregation
db.articles.aggregate([
  { $match: { $text: { $search: "replica set election" } } },
  { $addFields: { score: { $meta: "textScore" } } },
  { $sort: { score: -1 } },
  { $limit: 5 }
]);

Trap: a collection allows exactly one text index, and the field list and weights are fixed at creation, so adding a searchable field means dropping and rebuilding the index - plan the field set up front, and remember $text does no prefix or fuzzy matching ("pool" does not match "pooling" unless stemming aligns).

How do I run a resumable batch backfill of a new field?

Walk the collection in _id order with a range cursor, write each batch with bulkWrite, and checkpoint the last _id to a small state collection after the batch is acknowledged. Restarting reads the checkpoint and continues, so a crash costs one batch, never the whole migration. Make the operation itself idempotent - filter on "field still missing" - because a batch that was applied but not checkpointed will run again. Keep batches in the low thousands, throttle between them, and never run this as one unbounded updateMany that holds a lock storm and floods the oplog.

// mongosh
const mig = db.getSiblingDB("ops").migrations;
const key = "backfill-currency-2026-10";
const BATCH = 1000;
const saved = mig.findOne({ _id: key }) || { lastId: null };
let lastId = saved.lastId;

for (;;) {
  const filter = lastId ? { _id: { $gt: lastId } } : {};
  const docs = db.orders.find(filter, { _id: 1 }).sort({ _id: 1 }).limit(BATCH).toArray();
  if (docs.length === 0) {
    mig.updateOne({ _id: key }, { $set: { done: true, finishedAt: new Date() } }, { upsert: true });
    break;
  }
  const ops = docs.map(function (d) {
    return { updateOne: {
      filter: { _id: d._id, currency: { $exists: false } },   // idempotent
      update: { $set: { currency: "USD", currencySource: "backfill" } }
    } };
  });
  const r = db.orders.bulkWrite(ops, { ordered: false });
  lastId = docs[docs.length - 1]._id;
  mig.updateOne({ _id: key },
    { $set: { lastId: lastId, at: new Date() }, $inc: { batches: 1 } },
    { upsert: true });                                        // checkpoint last
  printjson({ batch: r.modifiedCount, lastId: lastId });
}

Trap: an _id cursor misses documents inserted behind the cursor during the run and documents whose _id is not monotonic, so finish with one verification pass that counts remaining matches, and inspect writeErrors - a validator rejection shows up there, not as an exception.

How do I run a mongodump/mongorestore with --oplog and verify the restore?

mongodump alone is not a consistent snapshot: it reads collection by collection while writes continue. Adding --oplog records every write that happened during the dump into oplog.bson, and mongorestore --oplogReplay re-applies them, giving a point-in-time consistent copy. Then verify four things before you call it done: per-collection counts against the source, the index definitions, the collection options (validator, collation, time-series), and a data checksum plus a known document. Finally confirm the last replayed oplog entry.

# 1) consistent dump - full instance, --oplog forbids --db / --collection
mongodump --uri="mongodb://backup@h1:27017,h2:27017/?replicaSet=rs0&authSource=admin" \
  --gzip --archive=/backup/shop-2026-10-23.archive --oplog

# 2) restore + replay writes that landed during the dump
mongorestore --uri="mongodb://restore@h3:27017/?replicaSet=rs1" \
  --gzip --archive=/backup/shop-2026-10-23.archive \
  --oplogReplay --drop --numInsertionWorkersPerCollection=4

# 3) the four checks (mongosh, against the restored deployment)
["orders", "customers", "ledger"].forEach(function (c) {
  print(c, db.getCollection(c).countDocuments({}));      // 1. counts vs source
});
printjson(db.orders.getIndexes());                        // 2. keys, unique, TTL
printjson(db.getCollectionInfos({ name: "orders" })[0].options);  // 3. validator, collation
printjson(db.orders.aggregate([                           // 4. checksum + spot check
  { $group: { _id: null, n: { $sum: 1 }, amount: { $sum: "$total" } } }
]).toArray());
printjson(db.getSiblingDB("local").oplog.rs.find().sort({ $natural: -1 }).limit(1).toArray());

Trap: --oplogReplay re-applies entries under their original namespaces, so it cannot be combined with --nsFrom/--nsTo remapping; and it only covers writes during the dump - anything after the dump still needs the oplog or a change stream, so record the dump's end timestamp.

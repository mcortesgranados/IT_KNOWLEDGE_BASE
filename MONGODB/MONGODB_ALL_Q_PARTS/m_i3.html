How does a $lookup with a pipeline and let differ from the localField/foreignField form?

The short form is a correlated equality join: localField is matched against foreignField and MongoDB can always use an index on the foreign field. The pipeline form is a full sub-query per input document. You pass outer values through let and read them inside the sub-pipeline as $$ variables, so you can filter, project, sort and limit the foreign side before it is attached.

db.orders.aggregate([
  { $lookup: {
      from: "customers",
      let: { cid: "$customerId" },
      pipeline: [
        { $match: { $expr: { $eq: ["$_id", "$$cid"] } } },
        { $project: { name: 1, tier: 1, _id: 0 } }
      ],
      as: "customer"
  } }
])

The catch: an $expr comparison is not automatically indexable. Put an equality $match on an indexed field first, or the sub-pipeline becomes a collection scan per document. The pipeline form is the right tool when you need a top-N join, not a full array of matches.

When would you use $unionWith, and what does it not do for you?

$unionWith appends the output of another collection or pipeline to the current stream. It is the clean way to query a live collection and an archive collection as one logical set, or to combine pre-aggregated rollups with raw data.

db.events.aggregate([
  { $match: { type: "click" } },
  { $unionWith: {
      coll: "events_archive",
      pipeline: [ { $match: { type: "click" } } ]
  } }
])

What it does not do: no deduplication, no schema reconciliation, no ordering guarantee, and both branches must live in the same database. Duplicate _id values from both sides are returned twice. Each branch is read in full, so an unindexed $match in either branch costs a collection scan. Treat it as a UNION ALL, and add a $group or $sort afterwards only when you actually need it.

How does $graphLookup traverse a hierarchy, and which options control its cost?

$graphLookup performs a breadth-first search inside one collection. startWith seeds the search, connectFromField and connectToField define the edge, and as names the resulting array. Documents are de-duplicated by _id, so cycles terminate.

db.employees.aggregate([
  { $graphLookup: {
      from: "employees",
      startWith: "$reportsTo",
      connectFromField: "reportsTo",
      connectToField: "_id",
      as: "chain",
      maxDepth: 5,
      depthField: "level",
      restrictSearchWithMatch: { active: true }
  } }
])

Cost control: maxDepth caps recursion, depthField lets you stop or filter later, and restrictSearchWithMatch prunes branches early. Crucially, an index on connectToField turns each hop into an index lookup instead of a scan. Without maxDepth on a deep or cyclic graph, the working set grows quickly per input document.

How does $facet run several sub-pipelines, and what are its limits?

$facet receives the documents produced so far and feeds the same input to every sub-pipeline in one pass. It is the standard way to return a page of results, a total count and per-facet counts in a single round trip.

db.products.aggregate([
  { $match: { status: "active" } },
  { $facet: {
      items: [ { $sort: { price: 1 } }, { $skip: 20 }, { $limit: 20 } ],
      total: [ { $count: "n" } ],
      byBrand: [ { $group: { _id: "$brand", n: { $sum: 1 } } } ]
  } }
])

Limits worth knowing: the input is materialised before the facets run, so put $match and $project before it; sub-pipelines cannot contain $out, $merge or a nested $facet; and each facet's output document is capped at 100 MB, which allowDiskUse does not relieve. Indexes only help the stages before $facet.

How do $bucket and $bucketAuto differ, and when is each appropriate?

$bucket takes explicit, sorted boundaries that must all share one BSON type. Every document whose group-by value falls in [lower, upper) lands in that bucket, and you control the labels and the accumulators.

{ $bucket: {
    groupBy: "$price",
    boundaries: [0, 50, 100, 500],
    default: "other",
    output: { n: { $sum: 1 }, avgPrice: { $avg: "$price" } }
} }

$bucketAuto computes the boundaries itself from a requested bucket count, trying to distribute documents evenly; granularity (R5, R10, 1-2-5, POWERSOF2) snaps the edges to human-friendly numbers. Use $bucket for fixed business bands such as price tiers or SLA ranges, where the boundaries must stay stable across runs. Use $bucketAuto for exploratory histograms, accepting that boundaries shift as data changes and that documents outside the computed range can land in an overflow bucket.

What can $setWindowFields compute that $group cannot?

$setWindowFields keeps every document and adds computed fields over a window, instead of collapsing rows into groups. That gives you running totals, moving averages, ranks and period-over-period comparisons in one stage.

db.orders.aggregate([
  { $setWindowFields: {
      partitionBy: "$customerId",
      sortBy: { createdAt: 1 },
      output: {
        runningTotal: { $sum: "$amount",
                        window: { documents: ["unbounded", "current"] } },
        last30d: { $sum: "$amount",
                   window: { range: [-30, "current"], unit: "day" } }
      }
  } }
])

Key mechanics: documents windows count positions, range windows work on the sort key's values (so unit applies to dates), and the default window is ["unbounded", "unbounded"]. Because it needs ordered input, it sorts and can spill; it is the natural replacement for self-joins and correlated sub-queries used to compute deltas.

How do $densify and $fill work together, and when do you need them?

$densify creates the documents that are missing from a sequence, and $fill assigns values to them. Together they turn sparse series into a continuous timeline, which matters when a chart or a downstream calculation must show zero-value periods rather than skip them.

db.metrics.aggregate([
  { $densify: { field: "ts", range: { step: 1, unit: "hour",
                 bounds: "full" }, partitionByFields: ["host"] } },
  { $fill: { sortBy: { ts: 1 }, partitionBy: "host",
             output: { value: { method: "linear" } } } }
])

$densify either extends the observed range or you supply explicit bounds. $fill supports a constant value, locf (last observation carried forward), or linear interpolation across the sort key. Both are partition-aware, so run them per tenant or per device. They generate rows, so the cost grows with the gap size: densifying years of minute data explodes the pipeline.

What is the practical difference between $merge and $out for materialised results?

$out writes the whole pipeline result into a collection, atomically replacing whatever was there. It is simple and readers never see a half-written collection, but it rewrites everything on each run, so the cost is proportional to total output size.

$merge is incremental: it matches on an on field (default _id, which needs a unique index), then applies whenMatched (merge, replace, keepExisting, fail, or a pipeline) and whenNotMatched (insert, discard, fail). That makes on-demand materialised views practical: recompute only a recent slice, merge it into the summary collection, and keep history.

{ $merge: {
    into: "daily_sales",
    on: "_id",
    whenMatched: [ { $set: { total: "$$new.total", refreshedAt: "$$NOW" } } ],
    whenNotMatched: "insert"
} }

Both are write stages, so they cannot appear in a view definition or inside $lookup/$facet.

What are $$ROOT, $$NOW and $$REMOVE used for in pipelines?

They are system variables, not fields. $$ROOT references the whole input document, which is handy for keeping a snapshot while reshaping: { $push: "$$ROOT" } inside a $group collects full documents, and { $sortArray: { input: "$items", sortBy: { price: 1 } } } style reshaping often starts from $$ROOT.

$$NOW returns the same date value for the entire pipeline, evaluated once at start, so every document sees an identical timestamp. That makes age calculations safe: { $dateDiff: { startDate: "$createdAt", endDate: "$$NOW", unit: "day" } }.

$$REMOVE removes a field conditionally inside $project or $addFields: { secret: { $cond: [ "$isPublic", "$secret", "$$REMOVE" ] } }. It is far cleaner than computing a value and then unsetting it in a later stage.

What are the edge cases of $unwind that break pipelines?

By default $unwind drops the document entirely when the field is an empty array, missing, or null, which silently loses rows in reports.

{ $unwind: {
    path: "$items",
    includeArrayIndex: "idx",
    preserveNullAndEmptyArrays: true
} }

preserveNullAndEmptyArrays keeps those documents with the array field absent, and includeArrayIndex gives the array position (null for preserved documents), which is useful for "position in cart" logic. Also note that a non-array value is treated as a one-element array, so string fields pass through unchanged. And unwinding multiplies document count, so a later $group or $sort processes far more rows than you might expect. Often $filter plus $map avoids the explosion.

What are the risks of using $function in an aggregation pipeline?

$function runs JavaScript on the server for every document. It is expressive, but it is the wrong default for three reasons.

  • Cost: the JS engine is invoked per document, so it is far slower than native operators and cannot use indexes at all.
  • Opacity: the optimiser cannot reason about the expression, so stages around it cannot be pushed down or reordered.
  • Portability: server-side JavaScript can be disabled at deployment level, so an expression that works in staging may fail in a hardened production tier.

Most requests that reach for $function are satisfied by $switch, $cond, $getField, $regexMatch, or $dateTrunc. If the logic truly belongs in code, compute it in the application on write and store the result, so reads stay indexable and cheap.

What is the 100 MB per-stage limit, and how does allowDiskUse change behaviour?

Memory-hungry blocking stages such as $sort, $group, $bucketAuto and $setWindowFields are limited to 100 MB of RAM per stage. Exceeding it raises an error unless the operation may spill to disk.

db.events.aggregate(pipeline, { allowDiskUse: true })

Since MongoDB 6.0 the server parameter allowDiskUseByDefault is true, so pipelines spill instead of failing unless a deployment turns it off. Spilling prevents the error but does not make the query fast: disk-backed sorts are an order of magnitude slower, and the real fix is a supporting index, a preceding $match, or a $project that shrinks documents. The 100 MB bound is per stage; a $facet result is still capped at 100 MB per facet regardless of allowDiskUse.

Does sorting before $group make $group use less memory?

Not in general, and this is a common misconception carried over from SQL engines. $group is a blocking hash aggregation: it keeps one entry per distinct group key in memory, so its footprint scales with the number of distinct groups, not with input order. Pre-sorting by the group key does not remove that hash table, and it adds a full blocking sort of its own.

What actually helps:

  • Filter first with $match so fewer documents reach the stage.
  • Reduce cardinality: grouping by userId over millions of users costs far more than grouping by country.
  • $project only the fields the accumulators need.
  • Bound the work with $limit or a time window where the business question allows it.

Check explain for spill indicators; a $group that writes to disk is a signal to redesign the pipeline, not to add a sort.

How expensive is $sample, and when does it not behave like a random sample?

$sample with a size below roughly 5% of the collection uses a pseudo-random cursor, which jumps to randomly chosen positions in the storage engine rather than reading every document. That is cheap on a large collection but it is not a strict uniform sample, and on small collections the server switches strategy.

For larger sample sizes it performs a top-k random sort, which scans the collection and keeps the best candidates in memory, so cost grows with collection size and the 100 MB stage limit applies.

db.users.aggregate([ { $sample: { size: 100 } } ])

Consequences: never put $sample after an expensive $group and expect it to save work, and do not use it for statistical guarantees. For "N random documents matching a filter", apply $match first; the sample is then drawn from the filtered stream, not the whole collection.

$redact versus $project for hiding sensitive fields: which one do you choose?

$redact walks the document recursively and evaluates an expression per level, returning $$DESCEND, $$PRUNE or $$KEEP. It is the right tool when the decision depends on a field's own value at any depth, for example hiding every sub-document whose classification is internal.

{ $redact: { $cond: [
    { $eq: [ "$classification", "internal" ] }, "$$PRUNE", "$$DESCEND" ] } }

$project with an inclusion list is explicit, predictable, and cheap: you state exactly which fields leave the database. It is the safer default for API responses, because a new sensitive field added later is excluded unless someone opts it in.

Note that $redact cannot use an index for the fields it inspects and it runs after other stages, so it does not reduce the data read from disk. For a hard guarantee, restrict with a $project and enforce field-level access with views or roles.

How do you read explain output for an aggregation pipeline?

Pass explain: true to aggregate(), or call .explain("executionStats") on the cursor. The output nests stages rather than showing one flat plan, so you read it inside-out: the innermost $cursor shows the collection access, and each stage reports its own timing and document counts.

db.orders.explain("executionStats").aggregate([
  { $match: { status: "open" } },
  { $group: { _id: "$customerId", n: { $sum: 1 } } }
])

Look for totalKeysExamined versus totalDocsExamined at the cursor, nReturned per stage to spot where rows explode, usedDisk to catch spilling, and whether the $match was pushed into the $cursor or sits above it. A $match that appears after $cursor instead of inside it means the filter was applied in memory, not by the index.

Why does $sort followed by $limit behave differently from $limit followed by $sort?

Because order of stages defines meaning, not just performance. $sort then $limit gives the top N by that key; $limit then $sort sorts an arbitrary subset, which is almost never what a report wants.

Performance-wise, the pair $sort + $limit is optimised into a top-k sort: the server keeps only N candidates in memory instead of materialising the full sorted set, so a $limit of 10 over millions of documents is far cheaper than sorting them all. The optimiser can also coalesce a $sort immediately followed by $limit when the source is a single collection.

{ $sort: { score: -1 } }, { $limit: 10 }   // top 10, bounded memory

If the sort is placed after a $group or $unwind, no index can help and the top-k optimisation still applies, but the input has already been materialised.

How do you test an aggregation pipeline without production collections?

The $documents stage lets you define the input inline, which turns a pipeline into a self-contained, runnable test fixture.

db.aggregate([
  { $documents: [
      { sku: "A", qty: 2, price: 10 },
      { sku: "A", qty: 1, price: 10 },
      { sku: "B", qty: 5, price: 2 }
  ] },
  { $group: { _id: "$sku", revenue: { $sum: { $multiply: ["$qty", "$price"] } } } }
])

This keeps the logic under test identical to what runs in production, with no fixture collection to create or clean up. Two caveats: $documents must be the first stage, and it accepts only constant expressions, so you cannot reference collection data. For deeper coverage, keep pipelines in one place in code and run them against a seeded test database in CI, asserting on exact output rather than on document counts.

How do arrayFilters with several identifiers work in a nested array update?

arrayFilters lets you update specific elements of an array without knowing their positions. Each filter gets an identifier, and the update path references that identifier with $[id].

db.orders.updateOne(
  { _id: 42 },
  { $set: {
      "items.$[i].status": "backordered",
      "items.$[i].notes.$[n].flagged": true
  } },
  { arrayFilters: [
      { "i.sku": { $in: ["A-1", "B-2"] } },
      { "n.visibility": "public" }
  ] }
)

Each identifier is an independent predicate on its own array level, so the two filters do not interfere. An element matches only if it satisfies the filter at that level. Rules that trip people up: you must declare an identifier for every $[...] placeholder, identifiers cannot be reused across levels, and the filter field paths are relative to the array element, not to the document root.

How does the positional $ operator differ from $[] and $[identifier]?

The positional $ updates the first array element matched by the query filter. Its big limitation is that it is ambiguous with multiple array conditions, which is why pairing it with $elemMatch is the safe pattern.

db.orders.updateOne(
  { _id: 42, items: { $elemMatch: { sku: "A-1", qty: { $lt: 2 } } } },
  { $inc: { "items.$.qty": 1 } }
)

Without $elemMatch, the two predicates could match different elements and the position is undefined. The alternatives are $[] (all elements) and $[id] (elements matching an arrayFilters entry). Prefer the identifier form in new code: it is explicit, handles multiple conditions cleanly, and does not depend on the query filter's shape, so refactoring the filter cannot silently change which element is updated.

What does $push with $each, $position, $sort and $slice let you do in one write?

It turns a read-modify-write into a single atomic update, which is exactly what a bounded leaderboard or recent-activity list needs.

db.boards.updateOne(
  { _id: "weekly" },
  { $push: {
      top: {
        $each: [ { player: "ana", score: 91 } ],
        $position: 0,
        $sort: { score: -1 },
        $slice: 10
      }
  } }
)

Order of application inside the modifier is fixed: $each inserts, $position places them, $sort orders the whole array, then $slice trims to the first or last N (negative keeps the tail). Because $slice runs last, the array never grows past the cap, so the document stays far below the 16 MB limit and the write stays cheap.

Note that $sort on the array elements requires the field to exist; missing sort keys are ordered by BSON type rules, so normalise the documents before relying on the ordering.

How does $addToSet deduplicate, and where does it surprise people?

$addToSet adds a value only if an equal value is not already present, using BSON equality rather than a field-level key.

db.users.updateOne(
  { _id: 7 },
  { $addToSet: { tags: { $each: ["beta", "beta", "gamma"] } } }
)

Surprises: the comparison is order-sensitive for embedded documents, so {a:1, b:2} and {b:2, a:1} are different values and both get added. Numeric types compare by value, so 1 and 1.0 do not duplicate, but NumberInt(1) and NumberLong(1) are distinct types. And each element is checked against the array, so a large $each on a huge array is O(n·m) and can be slow on hot documents.

If order and uniqueness matter more than array semantics, model membership as an object keyed by the value, or keep a separate collection with a unique index, which also removes the document-growth problem.

How does $setOnInsert behave, and why can it not be used in an update pipeline?

$setOnInsert applies only when the upsert inserts a new document; on a match it is ignored. It is the standard way to stamp creation metadata without a second round trip.

db.users.updateOne(
  { email: "ana@example.com" },
  { $set: { lastSeen: new Date() },
    $setOnInsert: { createdAt: new Date(), role: "member" } },
  { upsert: true }
)

Update pipelines (an array of stages such as $set and $replaceWith) are a different execution mode: the stage list is applied to the matched document and there is no notion of "insert only", so $setOnInsert, $push, $inc and friends are rejected there.

If you need computed creation values in a pipeline upsert, branch inside the pipeline on a field that only exists on insert, or simply use the classic modifier form for upserts and reserve pipelines for recomputation.

How do aggregation-pipeline updates work, and when are they worth it?

Instead of modifier operators you pass an array of stages, which lets the new value depend on other fields of the same document, computed on the server.

db.products.updateMany(
  { category: "sale" },
  [ { $set: { finalPrice: { $round: [
        { $multiply: ["$price", { $subtract: [1, "$discount"] }] }, 2 ] },
      updatedAt: "$$NOW" } } ]
)

Allowed stages are the ones that reshape a single document: $set/$addFields, $project/$unset, and $replaceWith/$replaceRoot. The write is still atomic per document, so readers never observe the intermediate state.

The trade-off is that each document runs the pipeline, so a large updateMany with heavy expressions costs more CPU than a constant $set, and the expressions cannot use indexes. Use it for deterministic recomputation during backfills and schema migrations, not as a general substitute for computing values in the application.

Why is $inc atomic, and what does it not protect you from?

$inc is applied by the storage engine while the document is locked for that write, so concurrent increments serialise and no update is lost. There is no read-then-write window for two clients to interleave, which is why counters should never be implemented as find then save.

db.stats.updateOne({ _id: "page:home" }, { $inc: { views: 1 } })

What it does not protect: numeric type overflow. A 32-bit integer at 2147483647 will not silently become a long; the update fails with an error, so initialise counters with NumberLong when they can exceed that. Nor does it help when the same document is the target of thousands of increments per second: the document becomes a hotspot and writes queue behind each other, so shard or bucket the counter instead.

Why use findOneAndUpdate with returnDocument: "before" for a work queue?

Because you need to know what you claimed, and the claim must happen in the same atomic step as the state change. With returnDocument: "before" you get the document as it was prior to the update, which is the only way to prove you are the client that moved it from queued to processing.

const job = await jobs.findOneAndUpdate(
  { status: "queued", runAt: { $lte: new Date() } },
  { $set: { status: "processing", lockedBy: workerId,
            lockedUntil: new Date(Date.now() + 60000) } },
  { sort: { priority: -1, runAt: 1 }, returnDocument: "before",
    projection: { payload: 1 } }
);

If the result is null, someone else won the race: no exception, no duplicate processing. With the default "after" you cannot tell whether you performed the transition or merely re-read a job another worker had already taken, which is the classic double-processing bug.

An updateMany touches 50,000 documents. What atomicity guarantees do you actually have?

Only per document. Each document's modification is atomic, but the set of documents as a whole is not: concurrent readers can observe some documents updated and others not, and if the operation fails partway, the earlier writes remain applied.

Two practical consequences:

  • The update must be idempotent, because a retry after a partial failure will re-apply it to documents that already succeeded. Prefer absolute assignments or guards such as { migrated: { $ne: true } } over relative operators like $inc.
  • A long updateMany yields to other operations between documents, so it does not block the collection, but it also gives you no isolation boundary.

If the whole set must land together, wrap it in a transaction — subject to the 16 MB oplog entry size and the 60-second default lifetime, which means batching anyway. Otherwise accept eventual consistency and make progress resumable.

What is $bit good for, and what are its constraints?

$bit performs bitwise and, or and xor on an integer field in place, atomically. Classic uses are permission masks, feature flags packed into one integer, and compact presence bitsets.

db.users.updateOne(
  { _id: 7 },
  { $bit: { perms: { or: NumberInt(4) } } }
);
db.users.updateOne(
  { _id: 7 },
  { $bit: { perms: { and: NumberInt(~4) } } }
);

Constraints: the field must be an int or long. A missing field is treated as zero, but a field holding a double, string or decimal raises an error, so the schema must be consistent. Because the operation is read-modify-write inside the storage engine, concurrent flag flips do not clobber each other — unlike fetching the value and writing it back. For bitsets spanning more than 64 flags you need multiple fields or an array of longs.

What exactly does { field: null } match, and how does an index treat it?

It matches three cases: the field is explicitly null, the field is absent, and the field is an array that contains null. That last case is the one people forget, because equality against an array matches if any element equals the value.

db.users.find({ nickname: null })
// matches: {nickname: null}, {}, {nickname: [null, "ace"]}

A normal index stores a null entry both for explicit nulls and for missing fields, so the query can be answered with an index scan on the null key rather than a collection scan. That is why { field: null } is indexable while { field: { $exists: false } } historically was not. If you want strictly null and not missing, query { field: { $type: "null" } }, and if you want "present", use { field: { $ne: null } } knowing it excludes nulls but includes arrays.

How does $type work, and what does the "number" alias cover?

$type matches by BSON type, either by string alias or numeric code. The alias "number" is a shorthand that expands to double, int, long and decimal, which is why it is the right choice when a field's numeric type drifted over the years.

db.orders.find({ total: { $type: "number" } })
db.orders.find({ total: { $type: ["int", "long"] } })
db.orders.find({ total: { $type: "string" } })   // data-quality check

Two behaviours to remember: for an array field, $type matches if any element has that type, and the aggregation expression $type returns an array of the distinct types present, which is useful for finding mixed-type fields before a migration. $type on an indexed field can use the index, unlike a $where-style check.

In what order does MongoDB compare values of different BSON types?

Cross-type comparison follows a fixed order, roughly: MinKey, Null, Numbers, String/Symbol, Object, Array, BinData, ObjectId, Boolean, Date, Timestamp, Regular Expression, MaxKey.

The important consequence is type bracketing: a range predicate only compares against values of the same type bracket. { price: { $lt: 100 } } will never return a document where price is the string "50", even though "50" sorts after numbers overall. That is deliberate — it stops queries from returning nonsense — but it also means a single stray string breaks range reports silently instead of loudly.

db.items.find({ price: { $lt: 100 } })   // numbers only
db.items.find({ price: { $type: "string" } })  // find the strays

Note that numbers compare by numeric value across int, long, double and decimal, so 1 equals 1.0.

What are the risks of passing user input straight into $regex?

Three distinct problems, and only one of them is about indexes.

  • Injection: characters like ., *, ( change the meaning of the pattern, so a search for "a+b" quietly matches "aab". Escape the input before building the pattern.
  • ReDoS: a nested quantifier such as (a+)+$ can make the matcher backtrack exponentially. A short malicious string can pin a CPU core on the server, so cap input length and reject patterns with nested quantifiers, or avoid user-supplied patterns entirely.
  • Cost: an unanchored pattern scans every candidate document; only ^prefix patterns get index bounds.
const safe = input.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
db.docs.find({ title: { $regex: "^" + safe } })

For real search requirements, use a text index or Atlas Search rather than regex.

How does one unindexed branch affect an $or query?

It usually collapses the whole query into a collection scan. To answer $or with indexes, the planner needs a usable index for every branch, then it runs them as sub-plans and deduplicates the results by record id. If any branch has no index, the planner compares costs and normally concludes that scanning once is cheaper than scanning once anyway plus doing index lookups for the other branches.

db.orders.find({ $or: [
  { customerId: 42 },        // indexed
  { legacyRef: "X-9" }       // no index -> whole query scans
] })

Read explain for SUBPLAN/OR stages; seeing COLLSCAN at the top confirms it. Fixes: index every branch, split into two queries and merge in the application, or restructure the data so one indexed field covers both cases. Also watch duplication — the same document can match several branches, which the OR stage removes.

Why does $elemMatch matter with arrays of objects, and when is dot notation equivalent?

Dot notation with several predicates can be satisfied by different array elements; $elemMatch requires one element to satisfy all of them.

// different elements can match each predicate
db.orders.find({ "items.sku": "A-1", "items.qty": 5 })

// the same element must match both
db.orders.find({ items: { $elemMatch: { sku: "A-1", qty: 5 } } })

For a single predicate the two are equivalent, and dot notation is preferable because it produces tighter index bounds and lets the planner use separate index entries per condition. Reach for $elemMatch whenever two or more conditions must describe the same element, and remember that $elemMatch on a single condition disables the usual multikey bounds optimisation, so it can be slower for simple equality.

Why can't $size use an index, and what do you do instead?

Because an index stores one entry per array element, not the array length. { tags: { $size: 3 } } is a predicate on the array as a whole, so the server must examine every candidate document and count elements.

db.posts.find({ tags: { $size: 3 } })   // COLLSCAN

Workarounds:

  • Maintain a tagCount field with $inc on push/pull and index it — the standard approach for "exactly N" queries.
  • For "at least N", an index on the array field with a range predicate can bound the candidates, then filter with $expr: { $gte: [ { $size: "$tags" }, 3 ] }.
  • For "has exactly one element", an index on tags.1 plus { "tags.1": { $exists: false } } is narrow and cheap.

Any denormalised count must be kept consistent by every write path, or it silently drifts.

How do $expr and $cond behave inside a filter, and what does it cost?

$expr lets a query use aggregation expressions, so you can compare two fields of the same document or branch on a condition with $cond.

db.orders.find({ $expr: {
  $gt: [ "$shippedAt", { $cond: [ { $eq: ["$express", true] },
                                   "$promisedAt", "$createdAt" ] } ]
} })

The expression is evaluated per candidate document, so the planner cannot derive index bounds from it and you get a collection scan (or an index scan on whatever separate predicates exist). $cond additionally makes the predicate non-sargable: even a supporting index on the compared fields cannot be ranged, because the comparison target varies per document.

If this shape is hot, compute the threshold on write into a field and index it, or restructure to a plain range predicate. Reserve $expr for ad-hoc analysis and admin queries.

What is the 32 MB sort limit, and how does an index avoid it?

A blocking in-memory sort is capped at 32 MB of data. Beyond that the operation fails with QueryExhausted-style sort errors unless it can spill or use an index.

An index avoids the sort entirely when the requested order matches the index order for the scanned bounds: the plan shows no SORT stage, just IXSCAN followed by FETCH. The equality prefix can be in any order, but the sort fields must appear in index order with matching direction (or the exact reverse).

db.orders.createIndex({ customerId: 1, createdAt: -1 });
db.orders.find({ customerId: 42 }).sort({ createdAt: -1 }).limit(20);
// IXSCAN supplies the order: no SORT, no 32 MB ceiling

Since 4.4 find accepts allowDiskUse, which lets an oversized sort spill instead of failing — a safety valve, not a design. If explain shows SORT with usedDisk: true, the index is missing or the direction is wrong.

How do maxTimeMS and $comment help you diagnose a slow endpoint?

maxTimeMS puts an upper bound on server-side execution and aborts the operation with error 50 (MaxTimeMSExpired) when exceeded, which stops one bad query from occupying a connection indefinitely. $comment attaches an arbitrary string that the server records in the profiler, in currentOp and in the slow-query log, which is how you connect a database operation back to the code path that issued it.

db.orders.find({ status: "open" })
  .comment("OrdersApi.listOpen v3 requestId=8f2c")
  .maxTimeMS(800)

Then db.system.profile.find({ "command.comment": /OrdersApi/ }) gives you the exact plans and timings for that endpoint. Treat the timeout as a contract: the application must catch error 50 and return a controlled response rather than a 500, and the budget should be lower than the client's own timeout so the server gives up first.

How do missing fields, nulls and arrays behave when you sort?

Sorting uses the same cross-type order as comparison: missing fields sort as null, and null sorts before numbers and strings. So a document without a score field appears before every document that has one when sorting ascending, which usually surprises people building leaderboards.

db.players.find().sort({ score: -1 })   // nulls land last here
db.players.find({ score: { $ne: null } }).sort({ score: -1 })

For arrays, ascending sort uses the smallest element of the array as the key and descending sort uses the largest, so an array-valued field can appear in an unexpected position. Sorting on an array field also prevents the plan from being a pure index-order scan when the index is multikey in ways that break the order guarantee, so verify with explain that no SORT stage appears. If ordering must be deterministic, add a tiebreaker such as _id.

Is sorting by { $natural: -1 } a reliable way to fetch the latest documents?

It works on small, append-only collections and it is a trap at scale. $natural bypasses indexes and returns documents in storage order; -1 walks that order backwards, so on a fresh collection the newest inserts come first.

It stops being true once documents are updated or deleted. Updates can relocate a document inside the storage engine, and deleted space is reused by later inserts, so reverse natural order is no longer insertion order. A capped collection or a clustered collection keyed by a monotonic value does preserve insertion order, but a normal collection does not.

db.events.find().sort({ $natural: -1 }).limit(20)   // works, but not "latest"

The reliable version is an index on a monotonic field: find().sort({ createdAt: -1 }).limit(20), ideally with _id as a tiebreaker. The index scan returns exactly the newest documents without touching the rest of the collection.

What happens when a field mixes Double and Decimal128 values?

Comparisons work numerically across numeric types, so a Decimal128 10.00 and a double 10 compare equal and sort together. Arithmetic is where the trouble starts: the result takes the wider type, so mixing decimal and double promotes to decimal, but the double has already lost precision before the conversion happens.

db.invoices.aggregate([
  { $group: { _id: null, total: { $sum: "$amount" } } }
])
// mixed types -> decimal result, but double inputs carried their rounding error in

Ordering also has a subtlety: 0.1 as a double is not exactly 0.1, so it can compare unequal to NumberDecimal("0.1") in edge cases, which breaks equality lookups and unique indexes over the field.

Practical rule: pick one type per field and enforce it with $jsonSchema bsonType: "decimal". Never convert currency with $toDouble in the middle of a pipeline.

What precision and timezone information does a BSON Date carry?

A BSON Date is a signed 64-bit integer of milliseconds since the Unix epoch, always UTC. There is no timezone stored with the value — the offset only exists when you format it for display or parse it from a string.

new Date("2026-03-01T00:00:00-05:00")   // stored as 05:00Z
ISODate("2026-03-01T00:00:00Z")

Consequences: millisecond resolution only, so sub-millisecond ordering needs a separate sequence field; two events in the same millisecond are indistinguishable by date alone. Local midnight is not a fixed instant, so "today" must be computed with a timezone-aware library or an explicit offset, never by string concatenation on the client.

Do not confuse Date with Timestamp, which is an internal BSON type used by the oplog with second and increment components, and is not meant for application timestamps. Store UTC, convert at the edge, and keep a separate field for the user's declared timezone when it matters.

What is inside an ObjectId, and does it guarantee creation order?

Twelve bytes: a 4-byte Unix timestamp in seconds, a 5-byte random value generated once per process, and a 3-byte incrementing counter.

ObjectId("65f1c2a4b7e3f10a9c8d4e21").getTimestamp()
// ISODate("2024-03-13T09:12:04Z")

Approximate order, yes: sorting by _id generally groups documents by insertion time, which is why it works as a cursor for pagination. Strict order, no — two processes can produce ids whose timestamps differ from the actual write order, the counter is per-process, and clock skew breaks the assumption entirely. Within a single process the counter makes ids monotonically increasing, which is why _id is usually a good tiebreaker.

Also note that ids are not secrets: the embedded timestamp leaks creation time. If that is sensitive, use a random UUID or a custom string key instead.

What are the driver traps when storing UUIDs as subtype 4 binary?

A UUID is 16 bytes stored as BinData, and the subtype determines byte order. Subtype 4 is the standard, but drivers historically wrote subtype 3 with a different byte order, so the same logical UUID can end up as two distinct BSON values that never compare equal.

db.users.insertOne({ _id: UUID("3b241101-e2bb-4255-8caf-4136c566a962") })
// BinData(4, "OyQRAdK7QlWMr0E2xWapYg==")

Traps to watch: configure the driver's UUID representation explicitly (in the Node.js driver, uuidRepresentation: "standard"); a legacy subtype 3 value inserted by an old service will not match a new subtype 4 query; and a unique index on the field will happily accept both representations as different keys. Migration requires rewriting values, not just changing the driver setting.

Also consider index locality: random UUIDs scatter inserts across the whole index, unlike monotonic ids.

How do you find documents approaching 16 MB before writes start failing?

The hard limit is 16 MB per BSON document, and the failure mode is ugly: a $push or $set throws once the new version would exceed it, which typically happens in production on a document that has been growing quietly for months.

db.articles.aggregate([
  { $project: { size: { $bsonSize: "$$ROOT" } } },
  { $match: { size: { $gt: 8000000 } } },
  { $sort: { size: -1 } }
])

Remediation depends on the shape: for unbounded arrays, apply the subset or bucket pattern and keep a bounded recent slice in the parent; for large embedded blobs, move them to GridFS or object storage and keep a URL; for wide, uneven documents, split rarely-read fields into a companion collection keyed by the same _id. Note the limit also applies to aggregation output documents, so a $group that builds a huge array fails the same way.

Is there a nesting depth limit, and why does it matter in practice?

Yes: BSON documents support a maximum nesting depth of 100 levels. Beyond that, writes are rejected. In practice you hit design problems long before the number.

Deeply nested paths are painful because every query, index and update has to spell out the full path, and a single mistyped segment silently matches nothing. Indexes on deep paths also grow, because the whole path is part of the index key metadata. Updates to a field at depth 8 are hard to express with positional operators, and $lookup or $unwind over such structures gets unreadable.

{ a: { b: { c: { d: { e: 1 } } } } }   // "a.b.c.d.e" everywhere

If a document needs more than three or four levels, that is usually a signal to flatten it, extract a sub-document into its own collection, or use an array of objects with a type discriminator instead of nested type-specific containers.

Why do Long and Int32 cause bugs in JavaScript applications?

Because JavaScript has no 64-bit integer. A BSON long arrives as a driver Long object, and treating it as a plain number silently truncates anything above 2^53.

const doc = await coll.findOne({ _id: 1 });
doc.seq.toNumber();                  // may lose precision
Long.fromString(doc.seq.toString()); // safe round trip

Typical failures: JSON serialisation turns a Long into { low, high, unsigned }; == comparisons against numbers fail; arithmetic on the Long object yields nonsense. Numeric fields also drift in type — an int that exceeds 2,147,483,647 stops accepting $inc with an overflow error, and a value written as a double when it should be a long breaks equality with existing documents.

Decide the type per field, set bsonType validation, and configure the driver to promote longs consistently rather than relying on defaults.

Why is document field order preserved, and when does it break equality?

BSON stores fields in the order they were written and MongoDB does not reorder them, so { a: 1, b: 2 } and { b: 2, a: 1 } are different byte sequences. That matters because equality on an embedded document is order-sensitive: the query below matches the first document and not the second, even though the values are the same.

db.docs.find({ sub: { x: 1, y: 2 } })   // does NOT match { sub: { y: 2, x: 1 } }

Two practical consequences. Any hash or checksum computed over serialized BSON changes when a field is renamed, because $rename moves it to the end of the document. And an import that rebuilds documents in a different order silently breaks keys built from those hashes. When identity should ignore order, compare field by field with $expr instead of relying on document equality.

How do you validate nested objects and arrays with $jsonSchema?

Each level needs its own properties block, and array elements are validated with items. A common mistake is declaring required at the top level and assuming it applies inside the array.

{ $jsonSchema: {
    bsonType: "object",
    required: ["orderId", "items"],
    properties: {
      orderId: { bsonType: "string" },
      items: {
        bsonType: "array", minItems: 1,
        items: {
          bsonType: "object",
          required: ["sku", "qty"],
          additionalProperties: false,
          properties: {
            sku: { bsonType: "string" },
            qty: { bsonType: "int", minimum: 1 }
          }
        }
      }
    }
} }

additionalProperties: false makes the schema strict, which is powerful but painful when a new field is rolled out — plan it deliberately. Validation applies to inserts and updates on the collection, including updates through aggregation pipelines.

How do you roll out a new validator without breaking writes?

Deploy it in warn mode first. validationAction: "warn" lets every write through but logs violations, so you can measure how much existing or in-flight code would fail before you enforce anything. "error" is the default and rejects the write with DocumentValidationFailure.

db.runCommand({ collMod: "orders",
  validator: { $jsonSchema: { bsonType: "object",
                              required: ["status"] } },
  validationLevel: "moderate",
  validationAction: "warn" });

Sequence: warn with validationLevel: "moderate" so already-invalid documents can still be updated if the update does not touch the missing field; watch the logs until violations stop; backfill the bad documents; then flip validationAction to "error". The "strict" level applies the rules to all documents, including previously invalid ones, which reverts an unrelated field update — useful only once the data is clean.

What can you change at runtime with collMod?

collMod modifies collection metadata without recreating the collection, which makes it the safe way to change rules on a live collection.

  • Validation: validator, validationLevel, validationAction.
  • TTL: change expireAfterSeconds on an existing TTL index by referring to its key pattern, including setting it to a much shorter value to purge old data quickly.
  • Views: replace the pipeline of a view in place.
  • Storage and indexing options: such as changeStreamPreAndPostImages and index hints.
db.runCommand({ collMod: "sessions",
  index: { keyPattern: { lastSeen: 1 }, expireAfterSeconds: 3600 } })

Changing expireAfterSeconds does not trigger an immediate mass delete: the TTL monitor runs about once a minute and removes in batches, so a large purge still takes time and produces oplog traffic.

What are the limits of a view that uses $lookup?

A view is a stored pipeline evaluated at read time, so a $lookup inside it re-runs for every query — the join is never precomputed and no index can span the joined collections.

db.createView("order_summary", "orders", [
  { $lookup: { from: "customers", localField: "customerId",
               foreignField: "_id", as: "customer" } },
  { $unwind: "$customer" },
  { $project: { customerName: "$customer.name", total: 1 } }
]);

Limits worth stating: the pipeline cannot contain $out or $merge, including inside an embedded $lookup sub-pipeline; a view must live in the same database as its source; it is read-only; and the definition is public — getCollectionInfos and explain expose the pipeline, so never embed literal secrets or references to sensitive fields. Also, the view has its own collation, which must match if it reads another view.

What does a capped collection actually guarantee?

It pre-allocates a fixed byte size and keeps documents in insertion order. When the space is full, the oldest documents are overwritten automatically, so the collection acts as a ring buffer with no cleanup job.

db.createCollection("recent_logs",
  { capped: true, size: 10485760, max: 100000 })

Guarantees and restrictions: reads in natural order return insertion order, deletes are not allowed, updates that would grow a document beyond its allocated space fail, and the collection cannot be sharded. Because writes are append-only, they are fast and predictable, and a tailable cursor can follow new inserts.

Where it does not fit: anything needing deletion, resizing documents, secondary indexes with heavy query patterns, or TTL-based retention. For log retention with flexible queries, a normal collection with a TTL index is usually the better choice; capped collections are for fixed-size, in-order streams.

How do you enforce a rule that compares two fields, given that $jsonSchema cannot?

$jsonSchema validates structure and per-field types, but it has no expression language, so it cannot say "endDate must be after startDate" or "total must equal sum of line items".

The trick is that a validator is a query filter, not just a schema: you can combine $jsonSchema with query operators, including $expr.

db.runCommand({ collMod: "bookings", validator: { $and: [
  { $jsonSchema: { bsonType: "object", required: ["start", "end"],
                   properties: { start: { bsonType: "date" },
                                 end: { bsonType: "date" } } } },
  { $expr: { $gte: ["$end", "$start"] } }
] } })

This runs per write on the server and rejects violations with DocumentValidationFailure. It costs a small amount of CPU and cannot reference other documents, so cross-document invariants still belong to unique indexes or transactions.

What makes a GeoJSON document valid for a 2dsphere index?

The field must hold a GeoJSON object with a type and coordinates: Point, LineString, Polygon, MultiPoint, MultiLineString, MultiPolygon or GeometryCollection.

db.places.createIndex({ location: "2dsphere" });
db.places.insertOne({ name: "Cafe",
  location: { type: "Point", coordinates: [-74.0721, 4.7110] } });

Rules that cause silent failures: coordinates are [longitude, latitude], in that order, not lat/lng; longitude must be within -180 to 180 and latitude within -90 to 90; a polygon's linear ring must be closed, with the first and last positions identical; and coordinates must be numbers, not strings, so a value imported as "4.7110" makes the document unindexable.

An insert with invalid geometry is rejected when the index exists, which is good — but a 2d index without GeoJSON validation accepts far looser input and behaves differently.

When do you use $near and when $geoWithin?

$near answers "nearest to this point": results come back sorted by distance, and it supports $minDistance and $maxDistance. That ordering is exactly what you want for "closest stores", but it also means the server must compute and sort distances.

db.stores.find({ location: { $near: {
  $geometry: { type: "Point", coordinates: [-74.07, 4.71] },
  $maxDistance: 2000
} } }).limit(10);

$geoWithin answers "inside this shape": a polygon, a circle via $centerSphere, or a multi-polygon. The result is unordered, which makes it cheaper and composable — it can appear inside an aggregation $match, be combined with other predicates, and be used when order is not part of the question.

Rule of thumb: distance-ranked search uses $near (or $geoNear in aggregation); containment or region filtering uses $geoWithin.

Why must $geoNear be the first stage of an aggregation?

Because it relies on the geo index to produce documents in distance order, and once other stages have transformed or filtered the stream the index can no longer be used. The server therefore rejects the pipeline if $geoNear is not first.

db.stores.aggregate([
  { $geoNear: {
      near: { type: "Point", coordinates: [-74.07, 4.71] },
      distanceField: "dist.meters",
      maxDistance: 3000,
      query: { open: true },
      key: "location",
      spherical: true
  } },
  { $limit: 10 }
])

Notes: distanceField is required and receives the computed distance; query adds non-geo predicates that are applied alongside the index scan; key disambiguates when several geo indexes exist; spherical: true is required for 2dsphere semantics. It cannot be used inside $lookup or $facet, and unlike $near it works in aggregation at all.

What units does a 2dsphere distance use, and how do you convert them?

Meters. With a 2dsphere index, $maxDistance, $minDistance and the value in distanceField are all in meters on the WGS84 sphere, so a 5 km radius is 5000.

{ $geoNear: { near: point, distanceField: "d",
              maxDistance: 5000, spherical: true } }
// d ~ 5000 means 5 km

Conversions are on you: divide by 1000 for kilometres, by 1609.34 for miles. $geoNear also offers distanceMultiplier, which scales the value written to distanceField — handy for returning kilometres directly, but be aware it does not change the unit of maxDistance, which stays in meters.

With a legacy 2d index the unit is not meters at all: it is the coordinate system's own unit, and distances come back in radians for spherical queries. Mixing a 2d index with GeoJSON input is the classic source of "my radius is 100x too small" bugs.

Which geo queries quietly bypass the geo index?

Several shapes look reasonable but cannot be answered by the index:

  • Negations: $not, $nin or $nor around a geo predicate, since the index finds what is inside, not what is outside.
  • Computed distance: an $expr or $function that calculates a haversine distance per document instead of using $near/$geoNear.
  • Index type mismatch: a 2d index queried with GeoJSON geometry, or a 2dsphere index queried with legacy coordinate pairs and $box-style operators.
  • Wrong field or representation: coordinates stored as strings, or as {lat, lng} objects instead of a GeoJSON array, which the index simply does not contain.

Confirm with explain: a geo query should show IXSCAN with 2dsphere in the index name, not COLLSCAN. If it scans, the predicate is not index-eligible regardless of how it reads.

How do you use collStats indexSizes to decide which index to drop?

indexSizes gives the on-disk bytes per index, which is the only honest measure of what an index costs you in cache and storage.

const s = db.orders.stats();
Object.entries(s.indexSizes).forEach(([k, v]) =>
  print(k.padEnd(40), (v / 1048576).toFixed(1) + " MB"));

Interpretation: an index larger than the data it serves is usually a candidate for removal, especially if it is a prefix of another compound index. Compare with $indexStats access counts and with the working set — a rarely used index that fits in RAM is still cheap, one that pushes the working set out of cache is expensive.

Before dropping: check for hints referencing it, unique or TTL semantics it enforces, and whether a query relies on its sort order. Hide the index first (db.collection.hideIndex()) so you can restore it instantly if a rarely-hit path degrades.

What is the difference between profiler level 1 and level 2?

Level 1 records only operations slower than slowms, which is the right setting for production triage. Level 2 records every operation, including sub-millisecond ones, so it captures the full workload but adds real overhead to every read and write and fills system.profile quickly.

db.setProfilingLevel(1, { slowms: 100 });
db.system.profile.find(
  { ns: "app.orders", "command.comment": /OrdersApi/ },
  { op: 1, millis: 1, planSummary: 1, keysExamined: 1, docsExamined: 1 }
).sort({ ts: -1 }).limit(10)

Read the entries for planSummary (was it COLLSCAN or IXSCAN?), the ratio of keysExamined/docsExamined to nreturned, hasSortStage, and appName when appName is set in the connection string. Level 2 is for short, targeted windows on staging or a single replica, never a permanent production setting.

How do you inspect and change server parameters without restarting mongod?

Use getParameter and setParameter admin commands. Only parameters marked as runtime-settable can be changed this way, and the change does not survive a restart, so it must also be written into the configuration file for permanence.

db.adminCommand({ getParameter: 1, slowms: 1 });
db.adminCommand({ setParameter: 1, logLevel: 1 });
db.adminCommand({ setParameter: 1, slowms: 200 });

Typical uses during an incident: raise logLevel briefly to capture verbose logs, adjust slowms without touching the profiler, or check limits such as maxTransactionLockRequestTimeoutMillis. Both commands require elevated privileges (clusterMonitor to read, clusterManager/hostManager to write).

Because settings are per node, in a replica set you must apply them to every member; a change on the primary alone makes behaviour inconsistent after failover.

What does $collStats with latencyStats tell you that a profiler cannot?

The profiler shows individual slow operations; $collStats aggregations show the distribution of all of them. latencyStats returns read and write latency histograms in microseconds, so you can see whether the 95th percentile degraded even when no single query crossed slowms.

db.orders.aggregate([
  { $collStats: { latencyStats: { histograms: true } } },
  { $project: { reads: "$latencyStats.reads.latency",
                writes: "$latencyStats.writes.latency" } }
]);

This is how you answer "is the collection slower than last week?" with per-collection evidence rather than a server-wide average. Combined with storageStats in the same stage you get document counts, average object size and free space in one call. It is a cheap, read-only command, safe to run on production, and the histograms reset on restart — so capture them periodically if you need a trend.

Why does system.profile need managing, and how do you rotate it?

Because it is a capped collection. Once it fills, new profile entries overwrite the oldest, so a long-running level-2 session can erase the very evidence you were collecting, and on a busy node the default size covers only seconds of activity.

db.setProfilingLevel(0);
db.system.profile.drop();
db.createCollection("system.profile",
  { capped: true, size: 50 * 1024 * 1024 });
db.setProfilingLevel(1, { slowms: 100 });

Profiling must be off while the collection is dropped, and it is recreated implicitly if you skip the explicit step. Practical routine: capture a bounded window, export the entries you need, then reset. Keep level 1 permanently with a sensible slowms, and reserve level 2 for minutes-long investigations on one node. Also remember that profiling writes are themselves writes, adding load to the same instance you are diagnosing.

When should an operational task be a mongosh script rather than driver code?

mongosh is for humans running a bounded administrative action: creating an index, adjusting a validator, sampling documents, checking a plan. It connects, does the work, and exits; there is no pool to size, no retry policy, and no deployment pipeline around it.

// idempotent by construction
const name = "orders_status_createdAt";
if (!db.orders.getIndexes().some(i => i.name === name)) {
  db.orders.createIndex({ status: 1, createdAt: -1 }, { name });
}

Driver code is for anything that must run repeatedly, be tested, retry on transient errors, or participate in a transaction. Scripts that mutate data at scale need the same discipline as application code — idempotent operations, a filter that can resume, batching, and a dry-run mode — but they should not become the permanent integration path. If a script is scheduled in cron and has error handling, it is application code that happens to be written in JavaScript.

How do you create a free Atlas cluster, and what does the free tier include?

In the Atlas UI choose Database → Build a Database, pick the M0 (free) tier, select a cloud provider and a region close to your users, name the cluster and deploy. Provisioning takes a few minutes and Atlas walks you through a security quickstart where you create the first database user and add your IP address.

An M0 cluster gives you about 512 MB of storage on shared infrastructure: no dedicated RAM or IOPS, so throughput is modest and noisy neighbours are possible. It is limited to one free cluster per project, has no automated cloud backups, and some features (dedicated tiers, certain backup and scaling options) require a paid tier such as M10 or higher. It is perfect for learning, demos and small prototypes, not for production.

What is the Atlas IP access list, and why does it block my connection?

The IP access list (formerly called the whitelist) is a set of IP addresses or CIDR blocks that Atlas accepts TCP connections from. It is enforced by the cluster's front end before authentication, so a correct username and password still fail if your address is not listed: you typically see a timeout or an error such as connection ... refused or not allowed to connect.

Add your current public IP under Network Access → Add IP Address. Cloud runtimes, CI agents and home connections change addresses often, which is the usual reason a working app suddenly cannot connect. You can add 0.0.0.0/0 to allow everything, but that exposes the cluster to the internet and should be limited to throwaway sandboxes.

How do you create a database user in Atlas, and which role should you give it?

Atlas database users are separate from your Atlas account: you create them under Database Access → Add New Database User, choosing password (SCRAM) or certificate authentication. Then you assign roles scoped to a database.

Give the application the smallest role that works: readWrite on the single application database covers normal CRUD, while read fits reporting or analytics services. Cluster-wide roles such as readAnyDatabase, dbAdminAnyDatabase or atlasAdmin should be reserved for operational tooling and humans, never for an app server, because a compromised process would reach every database in the cluster.

mongosh "mongodb+srv://cluster0.abcde.mongodb.net/" \
  --username appUser --authenticationDatabase admin

How do you connect Compass or mongosh to an Atlas cluster with the mongodb+srv string?

Open the cluster in Atlas, click Connect, and pick the tool: Compass gives you a paste-ready string, Shell gives the mongosh command with your cluster host. The string looks like this:

mongodb+srv://appUser:Secret123@cluster0.abcde.mongodb.net/shop?retryWrites=true&w=majority

Two practical details cause most failures. First, special characters in the password must be percent-encoded (@ becomes %40, : becomes %3A). Second, the path segment (/shop) is the default database, while authentication normally goes against admin. The +srv form resolves the replica set members from DNS, and TLS is enabled for you, so no extra options are needed.

Where do you find metrics and backups in the Atlas UI?

Select the cluster and open the Metrics tab: it charts operations per second, connections, network throughput, disk utilisation, query targeting and WiredTiger cache pressure, with a configurable time range. The Real-Time Performance panel shows currently running operations and slow queries, which is the fastest way to see what is happening right now.

Backups live in the Backup tab, where you can see snapshots, configure a backup policy and restore to a point in time or to a new cluster. Free and shared tiers do not include automated cloud backups, so on M0 you must export your own data with mongodump. Alerts can be wired to email or Slack from the project settings.

How do you list the indexes on a collection, and how do you read the output?

Use getIndexes(), which returns one document per index with the key pattern, the generated name and the options.

db.users.getIndexes()

[
  { v: 2, key: { _id: 1 }, name: "_id_" },
  { v: 2, key: { email: 1 }, name: "email_1", unique: true },
  { v: 2, key: { country: 1, createdAt: -1 }, name: "country_1_createdAt_-1" }
]

Read it left to right: key is the indexed field order (1 ascending, -1 descending, "text" or "2dsphere" for special types), name is what you pass to dropIndex(), and options such as unique, sparse, partialFilterExpression or expireAfterSeconds describe behaviour. v: 2 is the current index format version.

When should you drop an index, and how do you do it?

Drop an index when it duplicates the prefix of a longer compound index, when it is never used, or when a write-heavy collection pays more in maintenance than the index returns in reads. Check usage first with db.users.aggregate([{ $indexStats: {} }]): an accesses.ops counter that stays near zero after a full workload cycle is strong evidence.

db.users.dropIndex("email_1")
db.users.dropIndex({ country: 1, createdAt: -1 })

Do it in staging first, and remember that dropping frees disk and write overhead immediately but cannot be undone except by recreating it, which on a large collection is an expensive build. The _id index cannot be dropped.

How do you rebuild an index in MongoDB, and when is it worth doing?

MongoDB has no REBUILD INDEX statement like some relational engines. The reliable approach is to drop the index and create it again with the options you want; on a replica set the build is replicated to secondaries, and from 4.4 you can create an index as hidden: true first, then unhide it once it is built, so it never becomes visible half-ready.

db.users.createIndex(
  { email: 1 },
  { unique: true, hidden: true, name: "email_1_new" }
)
db.users.unhideIndex("email_1_new")

Rebuild only for a concrete reason: changing options (unique, partial, collation), suspected corruption, or a badly fragmented index. Routine rebuilding is not part of MongoDB maintenance and costs a full collection scan plus heavy I/O.

What does it mean when an index is "building"?

It means the server is scanning the collection to populate the index entries, and until that finishes the index exists in the catalog but the query planner will not use it. Builds run in a hybrid mode: they take a brief exclusive lock on the collection to start and finish, but yield to reads and writes in between, so the collection stays available.

You can watch progress with db.currentOp({ "msg": "Index Build" }), which reports the index name and a progress percentage, or through db.adminCommand({ currentOp: 1, $all: true }) on a replica set. A build that seems stuck is usually I/O bound or waiting for a long-running transaction to finish. Dropping the index while it builds aborts the build.

How do you check how much space the indexes on a collection take?

db.users.stats() reports indexSizes as a document mapping each index name to its size in bytes, plus totalIndexSize. db.users.totalIndexSize() returns just the total, which is handy in a script.

db.users.stats().totalIndexSize   // bytes
db.users.stats().indexSizes
// { _id_: 81920, email_1: 65536, country_1_createdAt_-1: 204800 }

For a single index on a large collection, the aggregation form with $collStats and storageStats avoids pulling the whole stats document. This matters because indexes live in memory as well as on disk: if total index size greatly exceeds the WiredTiger cache, every query risks disk reads, and an oversized unused index is a good candidate for dropping.

How do you check the server version and the mongosh version?

Inside the shell, db.version() returns the server version string such as 8.0.4; db.serverBuildInfo() adds the git commit, available storage engines and compile options, and db.hello() tells you whether you are connected to a primary or a secondary. The client version is not a shell method: run mongosh --version in your terminal, or check db.getMongo() in the shell for the connection object.

db.version()          // "8.0.4"  (server)
mongosh --version     // "2.3.1"  (client, from the OS terminal)

The distinction matters during upgrades and when a documented helper is missing: newer mongosh against an old server can behave differently, and features you read about may not exist on the server you reached.

How do you filter db.currentOp() to find long-running operations?

Pass a filter document instead of dumping every operation. The most useful fields are active, secs_running, ns and op.

db.currentOp({
  active: true,
  secs_running: { $gt: 5 },
  ns: { $ne: "" }
})

For each result read opid (needed for killing), op (query, update, command), ns, secs_running, planSummary (COLLSCAN on a huge collection is a red flag), numYields, waitingForLock and client. If nothing shows up, remember that idle connections and drivers' pooled sockets appear as inactive, and that the shell only sees operations on the node it is connected to.

How do you kill a long-running operation with killOp?

Find the operation id first, then kill it from the admin database. The id is an opid, not a session or thread id.

db.currentOp({ active: true, secs_running: { $gt: 30 } })
db.adminCommand({ killOp: 1, op: 123456 })

The server interrupts the operation at its next yield point, so a long index build or a large update may take a moment to stop, and the client receives an error such as operation was interrupted. Some internal operations cannot be killed safely, and killing a write mid-flight can leave partial work unless it was in a transaction. Always confirm with currentOp afterwards, and prefer fixing the query or index over killing operations routinely.

In db.serverStatus(), what should you look at first?

Start with three areas. Connections: compare connections.current with connections.available; being close to the limit means pool leaks or undersized limits. Queues and locks: non-zero globalLock.currentQueue.readers/writers shows contention. WiredTiger cache: check wiredTiger.cache["bytes currently in the cache"] against ["maximum bytes configured"] and watch the tracked dirty bytes, since a cache at capacity with high dirty pages turns reads into disk I/O.

db.serverStatus().connections
db.serverStatus().globalLock.currentQueue
db.serverStatus().wiredTiger.cache["bytes currently in the cache"]

Then glance at opcounters for traffic shape and asserts for errors. The document is huge, so query the specific path instead of printing all of it.

How do you rename a collection, and how do you rename a field?

Rename a collection with renameCollection, which needs the admin database and takes a lock; both names must be in the same database, and dropTarget: true overwrites an existing target.

db.adminCommand({
  renameCollection: "shop.orders_old",
  to: "shop.orders",
  dropTarget: true
})

Rename a field inside documents with the $rename update operator, using a dotted path for nested fields:

db.users.updateMany({}, { $rename: { "name": "fullName" } })
db.users.updateMany({}, { $rename: { "address.zip": "address.postalCode" } })

$rename is a per-document update, not an atomic schema change: it overwrites the target field if it exists, does not work on array elements, and on a large collection should be run in batches so you can throttle and resume.

How do you use $slice in a find projection to return only part of an array?

$slice in a projection trims an array after the document is matched, without changing which documents are returned. Three forms are worth memorising.

db.posts.find({}, { comments: { $slice: 3 } })     // first 3
db.posts.find({}, { comments: { $slice: -3 } })    // last 3
db.posts.find({}, { comments: { $slice: [10, 5] } }) // skip 10, take 5

It is the standard way to avoid shipping a 500-element array to a mobile client, and it can be combined with other projection fields. The catch: the filter runs first, so you cannot ask for documents whose sliced window contains a value; that needs $filter or an aggregation with $slice as an expression. Also remember the document on disk is still read in full.

How do you create a read-only view and control who can read it?

A view is a saved aggregation pipeline over a collection or another view. It stores no data, is computed on every read, and is inherently read-only: insert, update and delete are rejected against it.

db.createView("publicUsers", "users", [
  { $match: { active: true } },
  { $project: { name: 1, city: 1, email: 0, ssn: 0 } }
])

Grant privileges on the view's own namespace rather than the base collection, so a reporting user can read the projection but not the raw documents:

db.createRole({
  role: "publicUsersReader",
  privileges: [{ resource: { db: "shop", collection: "publicUsers" },
                 actions: ["find"] }],
  roles: []
})
db.grantRolesToUser("reporting", [{ role: "publicUsersReader", db: "shop" }])

Typical uses are hiding PII, freezing a stable field shape for consumers, and pre-filtering tenants.

What is a namespace in MongoDB?

A namespace is the fully qualified name of a collection or index in the form database.collection, for example shop.orders. It is the identifier the catalog, the query planner and every diagnostic surface use: you see it as the ns field in currentOp, in slow-query log lines, in profiler output, in lock reports and in error messages such as a duplicate key error naming shop.orders.

Namespaces matter operationally because MongoDB documents a length limit (120 bytes for a collection namespace, 255 for index namespaces), so extremely long database or collection names can be rejected. Views, time series collections and GridFS buckets all occupy their own namespaces, which is why a dump of a "single" logical dataset often shows several entries.

Why can't { field: { $exists: false } } use an index the way { field: null } can?

Because the two predicates are not the same. { field: null } matches documents where the field is explicitly null or missing, and a normal (non-sparse) index stores missing fields as null entries, so the planner can seek to them. $exists: false matches only missing fields, and those documents are precisely the ones a sparse index omits, so a sparse index cannot answer it and the server falls back to a collection scan.

db.users.find({ deletedAt: null })          // can use index on deletedAt
db.users.find({ deletedAt: { $exists: false } }) // usually COLLSCAN
db.users.find({ deletedAt: { $exists: true } })  // can use a sparse index

That asymmetry is a good reason to write explicit nulls instead of omitting fields when you plan to query on absence.

How should a UUID be stored: as BinData or as a string?

Store it as BSON binary with the UUID subtype (subtype 4 for a standard RFC 4122 UUID), using the driver's native UUID type rather than a hand-made buffer.

// mongosh
db.devices.insertOne({
  _id: UUID("3f2504e0-4f89-11d3-9a0c-0305e82c3301")
})

// Node.js driver
await devices.insertOne({ _id: new UUID("3f2504e0-4f89-11d3-9a0c-0305e82c3301") })

Binary form is 16 bytes against roughly 36 for the canonical string, so indexes are smaller, comparisons follow byte order, and there are no case or collation surprises. The string form is friendlier for debugging, URLs and CSV round trips, but it doubles storage and invites the classic bug of mixing uppercase and lowercase representations of the same identifier. Whichever you choose, keep one format for the field across the whole system.

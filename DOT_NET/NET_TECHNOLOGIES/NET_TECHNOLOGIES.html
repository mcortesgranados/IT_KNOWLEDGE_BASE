01.NET 8 platform essentials

The role asks for .NET 8 or later. The practical differences against older versions are the unified SDK, minimal APIs as a first-class model, performance work on JSON and LINQ, and a few features that change day-to-day code.

Keyed services remove the need for a factory when two implementations of the same interface must coexist; TimeProvider makes time injectable and therefore testable.

  • .NET 8 is LTS (support to November 2026); .NET 9 is STS. Say which one you ship and why.
  • Minimal APIs, TimeProvider, keyed DI and NativeAOT are the features worth naming in an interview.
  • CancellationToken on every async boundary is part of the platform contract, not an extra.

02Modern C#: records, nullable reference types, pattern matching

Most of what an interviewer hears as 'modern C#' is three things: immutable data with records, compile-time null safety with nullable reference types, and pattern matching instead of chains of if.

They matter because they remove whole categories of bug before runtime — a null that cannot reach production, an object that cannot be mutated by accident.

  • record gives value equality and with expressions; sealed stops inheritance surprises.
  • <Nullable>enable</Nullable> plus warnings-as-errors is what makes it a guarantee, not a suggestion.
  • Switch expressions over property patterns read better than nested if blocks and are exhaustiveness-checked for enums.

03Multi-layered architecture: API, application, domain, infrastructure

The posting is explicit about separation between API/presentation, business/application and data access. That is the classic layered model, and the interview question behind it is dependency direction: the domain knows nothing, the application depends on the domain, infrastructure implements interfaces declared inside.

One project per layer is the simplest honest structure; Vertical Slice is a defensible alternative if you can argue the trade-off.

  • Dependency inversion: interfaces live where they are consumed, implementations live outside.
  • The API project references Application only; Infrastructure is referenced at composition time (Program.cs).
  • Loose coupling and high cohesion are the criteria — say which layer owns validation and which owns persistence.

04Dependency injection and object lifetimes

Built-in DI is the default expectation. The trap interviewers look for is the captive dependency: a scoped service captured by a singleton, which then lives forever and holds a disposed DbContext.

Know the three lifetimes cold, plus when a scope must be created by hand (IServiceScopeFactory in background workers).

  • Singleton must be thread-safe and stateless; scoped is the default for anything touching the DbContext.
  • Injecting a scoped service into a singleton is a runtime InvalidOperationException, not a compile error.
  • Validate on startup (ValidateOnBuild, ValidateScopes) so misconfiguration fails in development, not in production.

06EF Core: modelling, tracking and query behaviour

EF Core is an ORM with a query pipeline, not a database. The questions that separate levels are about tracking, projections and the N+1 problem.

AsNoTracking for reads, projection into DTOs at the database level, and Include used deliberately rather than sprinkled.

  • Select before ToList means the filtering happens in SQL; ToList then Select means it happens in memory.
  • Lazy loading is off by default in EF Core — keep it off and load explicitly, or the N+1 problem comes back.
  • Migrations belong in source control; dotnet ef migrations add in the pipeline, database update in deploy.

07Dapper and raw SQL: when the ORM is the wrong tool

Dapper maps rows to objects with no change tracking and no query translation. It wins for reporting queries, bulk reads and anything where the generated SQL is wrong or slow.

A healthy codebase mixes both: EF Core for writes and aggregates, Dapper for read models.

  • Always parameterise; string concatenation in SQL is the vulnerability reviewers look for first.
  • CommandDefinition carries the cancellation token and command timeout.
  • Explain the trade-off: Dapper is faster and explicit, EF Core is safer and cheaper to maintain.

08Repository and Unit of Work — and when they are noise

A repository abstracts persistence behind a collection-like interface; Unit of Work groups changes into one transaction. With EF Core, DbContext already is a Unit of Work and DbSet already is a repository.

The defensible position: use repositories at the application boundary to keep the domain persistence-ignorant, and skip a hand-written UoW on top of EF Core.

  • Do not wrap DbSet in a repository that only forwards calls — that is abstraction theatre.
  • Repositories earn their place when the storage may change or when queries must be reused and tested.
  • Say out loud that EF Core's DbContext is scoped, so the UoW must be scoped too.

09Relational databases: SQL Server and PostgreSQL

Two years of relational experience is a must-have, and the questions are practical: indexes, execution plans, transactions and isolation.

Know how to read a plan, what a covering index is, and why a SELECT * on a wide table hurts.

  • @@ROWCOUNT = 0 is how you detect a lost update without a lock hint.
  • Read committed is the default; say when you would use snapshot isolation and what it costs.
  • PostgreSQL equivalents: EXPLAIN (ANALYZE, BUFFERS), partial indexes, ON CONFLICT DO NOTHING.

10NoSQL with MongoDB

One year of NoSQL is required. The point is not 'schemaless' but embedded versus referenced documents, and which one matches the read pattern.

Indexes, $lookup sparingly, and transactions only when a single-document write is not enough.

  • Embed what you read together; reference what changes independently or grows without bound.
  • Every query needs an index or it becomes a collection scan — check with explain().
  • Multi-document transactions exist in replica sets but cost more; design so you rarely need them.

11Authentication and authorization: JWT, OAuth 2.0 and OIDC

The must-have is implementing authn/authz with OAuth 2.0, OpenID Connect or comparable. In .NET that means JWT bearer validation plus policy-based authorization.

Explain the flow, not just the attribute: the API validates tokens issued by an identity provider; it does not issue them.

  • Authentication answers who; authorization answers what. Two registrations, two attributes.
  • Scopes for machine-to-machine, roles or policies for user permissions; keep the check server-side always.
  • Never validate a token by hand — signature, issuer, audience and lifetime are the library's job.

15Background work and the outbox pattern

BackgroundService is the built-in host for long-running work. The dangerous part is scope and idempotency: a message consumer will see the same message twice.

The outbox pattern is the standard answer: write the domain change and the outgoing message in one transaction, then publish from a worker.

  • Never inject a scoped service into a singleton worker — create a scope per iteration.
  • Idempotency key on the consumer side is what makes at-least-once delivery safe.
  • Task.Delay with the token, and catch OperationCanceledException on shutdown.

public sealed class OutboxPublisher(
    IServiceScopeFactory scopes, ILogger<OutboxPublisher> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<OutboxDbContext>();

            var batch = await db.Outbox.Where(m => m.PublishedAt == null)
                                       .OrderBy(m => m.CreatedAt).Take(50).ToListAsync(ct);

            foreach (var message in batch)
            {
                await Publish(message, ct);           // idempotent consumer side
                message.PublishedAt = DateTime.UtcNow;
            }
            await db.SaveChangesAsync(ct);
            await Task.Delay(TimeSpan.FromSeconds(5), ct);
        }
    }
}

18Microservices and resilience

Microservices are an organisational answer to independent deployment, not a performance trick. What gets discussed in interviews is failure handling: timeouts, retries with jitter, circuit breakers and idempotency.

IHttpClientFactory plus a resilience handler gives all of it in configuration.

  • Retry only idempotent operations; a retried POST without a key duplicates the order.
  • A timeout shorter than the caller's timeout, or the retry never happens before the caller gives up.
  • Service discovery, gateway and BFF are the other three words to be able to place on a diagram.

19Performance and caching

Most .NET performance problems are not micro-optimisations: they are sync-over-async, unbounded queries, missing indexes and chatty calls between services.

Caching is the cheapest win when the read pattern allows it — and the most dangerous when invalidation is unclear.

  • Async all the way: .Result and .Wait() burn threads and deadlock under load.
  • Measure with dotnet-counters, dotnet-trace or Application Insights before changing anything.
  • Name the invalidation strategy before adding a cache; a stale cache is a bug with a delay.

22The Angular-to-.NET contract

The role is full stack, so the seam matters: DTO shape, error format, CORS and the generated client. Angular interceptors and .NET middleware must agree on both success and failure.

// .NET: stable error shape for every failure
public sealed record ApiError(string Code, string Message, string? TraceId);

// Angular: one interceptor for auth + error mapping
export const errorInterceptor: HttpInterceptorFn = (req, next) => {
  return next(req).pipe(
    catchError((err: HttpErrorResponse) => {
      const problem = err.error as { title?: string; status?: number };
      return throwError(() => new AppError(problem?.title ?? 'Unexpected error', err.status));
    })
  );
};

    .WithOrigins("https://app.example.com")
    .AllowAnyHeader().AllowAnyMethod().AllowCredentials()));

23Security checklist before any release

A short list that catches most findings in a review of an enterprise API.

Say which of these you have actually implemented, with an example — that is what a technical interviewer listens for.

  • Parameterised SQL, least-privilege database users, and secrets outside the repository.
  • Authorization checked server-side on every endpoint, including the ones the UI hides.
  • Rate limiting and request size limits are part of the API, not an infrastructure afterthought.

24Mapping the must-haves to evidence

What the interview actually tests is whether each requirement has a story behind it. This is the table to keep in mind — one concrete example each, with a number when possible.

If a line has no evidence yet, that is the gap to close before applying.

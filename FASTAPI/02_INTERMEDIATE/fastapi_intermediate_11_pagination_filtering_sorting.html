Pagination, Filtering and Sorting Patterns

List endpoints live or die by their query ergonomics. This page assembles the standard FastAPI toolkit: a reusable pagination dependency, validated sorting, filtering, and a response envelope with total counts and navigation links.

A Reusable Pagination Dependency

from dataclasses import dataclass
from fastapi import Depends, Query

@dataclass
class Pagination:
    skip: int = Query(0, ge=0)
    limit: int = Query(20, ge=1, le=100)     # cap page size to protect the DB

def pagination_params(skip: int = Query(0, ge=0),
                      limit: int = Query(20, ge=1, le=100)) -> Pagination:
    return Pagination(skip=skip, limit=limit)

@app.get("/items/")
def list_items(page: Pagination = Depends(pagination_params), db=Depends(get_db)):
    total = db.scalar(select(func.count()).select_from(Item))
    items = db.scalars(select(Item).offset(page.skip).limit(page.limit)).all()
    return {"total": total, "items": items}
  • ge/le constraints stop clients from requesting limit=100000.
  • Every list endpoint reuses the same dependency → consistent query params across the API.

Generic Page Envelope (Pydantic v2 Generics)

from typing import Generic, TypeVar
from pydantic import BaseModel

T = TypeVar("T")

class Page(BaseModel, Generic[T]):
    total: int
    skip: int
    limit: int
    items: list[T]

@app.get("/items/", response_model=Page[ItemOut])
def list_items(page: Pagination = Depends(pagination_params), db=Depends(get_db)):
    total = db.scalar(select(func.count()).select_from(Item))
    items = db.scalars(select(Item).offset(page.skip).limit(page.limit)).all()
    return Page(total=total, skip=page.skip, limit=page.limit, items=items)

Page[ItemOut], Page[UserOut]... one envelope for every resource, fully documented by OpenAPI.

Sorting with a Whitelist

ALLOWED_SORT_FIELDS = {"name": Item.name, "price": Item.price, "created": Item.created_at}

@app.get("/items/")
def list_items(sort: str = Query("created", pattern="^(name|price|created)$"),
               order: str = Query("asc", pattern="^(asc|desc)$"),
               db=Depends(get_db)):
    column = ALLOWED_SORT_FIELDS[sort]
    stmt = select(Item).order_by(column.desc() if order == "desc" else column.asc())
    return db.scalars(stmt).all()
Never build ORDER BY (or any SQL) from raw client strings. Map allowed values to columns through a whitelist dict — the same injection discipline as parameterized values, applied to identifiers.

Filtering: Explicit Params Beat a Magic Dict

@app.get("/items/")
def list_items(
    name: str | None = None,
    min_price: float | None = Query(None, ge=0),
    max_price: float | None = Query(None, ge=0),
    owner_id: int | None = None,
    db=Depends(get_db),
):
    stmt = select(Item)
    if name:
        stmt = stmt.where(Item.name.ilike(f"%{name}%"))
    if min_price is not None:
        stmt = stmt.where(Item.price >= min_price)
    if max_price is not None:
        stmt = stmt.where(Item.price <= max_price)
    if owner_id:
        stmt = stmt.where(Item.owner_id == owner_id)
    return db.scalars(stmt).all()

Explicit optional parameters are self-documenting in /docs. A "catch-all filter dict" hides the contract and invites injection — avoid it in public APIs.

Offset vs Cursor Pagination

  • Offset (skip/limit): easy, jump to any page, shows totals — but slow on huge tables (OFFSET 100000 scans what it skips) and rows can shift between pages.
  • Cursor (keyset): ?after=last_seen_id, SQL is WHERE id < :after ORDER BY id DESC LIMIT :n — stable and fast at any depth; no page numbers or totals. Standard for feeds and infinite scroll.
  • Rule of thumb: admin tables → offset; high-volume feeds → cursor.

Quick Questions and Answers

Q: Should the response include "total"?

A: It costs one COUNT(*) per request — cheap on small/medium tables, expensive on huge ones. Include it for admin/paging UIs; omit it (or cache it) for cursor-paginated feeds where clients only need "is there a next page".

Q: How do I give clients ready-made next/prev URLs?

A: Rebuild the request URL with updated params: request.url.include_query_params(skip=skip + limit, limit=limit) and put it in the envelope ("next": str(url)). Clients then never construct URLs themselves.

Q: Where does pagination logic belong — endpoint, dependency, or CRUD layer?

A: Params parsing and constraints in the dependency, SQL application (offset/limit/where) in the CRUD/repository functions, envelope building in the endpoint. Each layer stays independently testable.

Conclusion

Standardize lists with a pagination dependency + generic Page[T] envelope, whitelist sort fields, keep filters explicit, and pick offset vs cursor by table size. Consistent list endpoints are the part of an API other teams consume the most — invest in the pattern once.
